# FW08 local health and control transport (design)

Status: design, written after FW07 closed. Nothing here is implemented or bench-tested yet. Choices marked **decision** are this design's; they can change before stage A, but not silently afterwards.

## Goal and non-goals

The replacement firmware reports who it is and how it is doing to the existing local server over Wi-Fi, so the owner no longer needs a UART capture to see build, bank, boot and fault state. The same channel carries a small, fixed set of diagnostic requests.

Non-goals for FW08:
- **No actuation.** Nothing reachable from the transport can dispense, run the motor, change emitters, write settings or flash, or start an update. Feeding requests are FW17 and updates are FW10. Both will need their own review against this channel.
- **No cloud.** The feeder talks only to the server on the isolated hotspot. The bench host's firewall keeps forwarding blocked.
- **No provisioning.** Wi-Fi and transport credentials stay build-time inputs from ignored private files until FW25.
- **No TLS in v1.** See [Authentication and exposure](#authentication-and-exposure).

## Shape

**Decision:** the firmware is an MQTT 3.1.1 client of the server's embedded broker. It opens the connection outbound and listens on no port.

Why this rather than an HTTP server on the feeder:
- The server already runs an authenticated, topic-scoped broker for stock firmware ([local server](../development/local-server.md)). FW08 adds a second, separate role to it instead of a second protocol.
- With no listening socket on the feeder, nothing on the network can make it accept a new connection, and the feeder needs no request router of its own.
- Retained messages and the last will give the server "last known health" and "went offline" without polling.
- The broker already speaks MQTT 3.1.1; it translates the stock device's legacy 3.1 CONNECT for it.

**Decision:** MQTT encoding and the client state machine live in `wellfed-core` (`no_std`), so they are host-tested against the server's real broker in an integration test. A small C shim in the KM4 port supplies a blocking TCP socket (lwIP sockets, as the FW07 DNS check does). The SDK's Paho `MQTTPacket`/`MQTTClient` stays unused; that keeps first-party protocol code in the Rust workspace, per AGENTS.md.

The client needs only a subset: CONNECT with will, CONNACK, PUBLISH (QoS 0, retained or not), SUBSCRIBE/SUBACK to one topic, PINGREQ/PINGRESP and DISCONNECT. Incoming PUBLISH is accepted only on the request topic, and only up to a fixed size. Anything else closes the connection.

## Identity, topics and roles

The server is configured for one device. FW08 adds a firmware role beside the existing `device` and `server` roles; it never shares the stock device's credentials or namespace.

| Item | Value |
| --- | --- |
| Client ID | `wellfed-fw-<device_id>` |
| Username | `wellfed-fw` |
| Password | Per device, random 32 bytes, generated by the server and stored only in the private server config and the private firmware credential file |
| Namespace | `wellfed/1/<device_id>/` (the `1` is the topic-layout version) |

| Topic suffix | Publisher | Subscriber | Retained | QoS |
| --- | --- | --- | --- | --- |
| `health` | firmware | server | yes | 0 |
| `request` | server | firmware | no | 0 |
| `reply` | firmware | server | no | 0 |

The broker's ACL lets the firmware role publish only `health` and `reply`, and subscribe only to `request`; the server role is the reverse. Neither role can reach the stock `dl/PLAF103/...` topics, and the stock role can't reach these. Stock and replacement firmware never run on the unit at the same time, but the separation holds even if both connected.

The will is a retained `health` message with `"online": false` and the boot's sequence fields, so a lost link replaces the last health with "offline" rather than leaving it stale.

## Health message

Compact JSON, one object, at most 512 bytes, schema `wellfed.health`, version 1. A consumer must ignore unknown fields and refuse an unknown major version. Field values come from data the firmware already has; nothing new is measured.

```json
{"schema":"wellfed.health","v":1,"online":true,"seq":12,"uptime_ms":61234,
 "build":"<startup identity hex64>","bank":1,"reset_flags":"00000000","boot_count":7,
 "outputs":"stopped","faults":[],
 "wifi":{"rssi":-20,"attempt":2,"losses":{"link":0,"dns":1},"last_loss":"dns"},
 "transport":{"connects":1,"last_error":null}}
```

| Field | Source |
| --- | --- |
| `build` | the embedded startup identity, as printed in `PLFW1 start build=` |
| `bank`, `reset_flags` | startup report (FW02) |
| `boot_count` | KM0 backup register 4 (FW06 peer; survives watchdog reset, not power loss) |
| `uptime_ms` | monotonic clock |
| `outputs` | `stopped` only after a fresh stopped-output readback passes, else `unverified` |
| `faults` | latched fault names, for example `watchdog`, `flash_hook`, `stopped_readback`; empty when none |
| `wifi` | the FW07 shim's event counters |
| `transport` | this client's own connect count and last error |

**Decision:** publish on connect, then every 30 s, and immediately when `faults`, `outputs` or a Wi-Fi loss counter changes. The keepalive is 30 s, and the server treats health older than 75 s as stale even if no will arrived.

The UART keeps the same information as `PLMQT1` records (connect, publish, request, reply, error). Bench audits work from UART captures as they do today, and a capture still shows what happened when the network didn't.

## Diagnostic requests

A request is `{"id":"<uuid>","op":"<name>"}`, at most 256 bytes. The reply is `{"id":"<uuid>","op":"<name>","ok":true|false,...}` on `reply`.

v1 allowlist:
- `health`: publish health now, then reply `ok`.
- `ping`: reply `ok` with `uptime_ms`.

Anything else gets `ok:false`, `error:"unsupported"`, and is logged. Requests carry no arguments in v1. Replays are harmless because both operations are read-only; the ID is only for correlation.

**Decision:** no reboot, no log dump and no settings read in v1. A remote reboot could make a fault hard to see, so it waits for FW11's boot policy. Log streaming needs a size and rate budget.

**Structural no-dispense rule.** The transport's code may depend on the health snapshot and its own socket, nothing else. It is a separate module that takes a read-only health snapshot type; it gets no reference to the owner, motor gate, outputs, settings store, flash authority or OTA code. Stage A adds a check that fails the build if the transport module imports any of those. FW16 will add the matching link check when a motor controller exists.

## Authentication and exposure

- The feeder authenticates to the broker with the per-device firmware password, compared in constant time as the existing roles are.
- The server authenticates to the same broker as its existing server role.
- The traffic is plaintext MQTT on the WPA2-protected bench hotspot, with no route out. Anyone holding the Wi-Fi password could sniff the firmware password and impersonate the feeder or the server on this channel. With the v1 allowlist that exposes health contents and read-only requests, nothing else. **Decision:** accept that for FW08, record it as a carried item, and require TLS (mbedTLS is in the SDK) or a per-message MAC before any channel carries feeding (FW17) or updates (FW10).
- The credential never appears in UART output, the build manifest (hash only, as with Wi-Fi) or tracked files.

The bench host's firewall needs one more input rule for the broker port from the hotspot subnet, for example `iifname "wlan1" ip saddr 10.42.103.0/24 tcp dport 1883 accept`. That is the owner's change, as before. Forwarding stays blocked.

## Server side

- **Config:** an optional `firmware` section (client ID, username, password). The config format stays version 1; a config without the section behaves exactly as today.
- **Init:** `wellfed-local firmware-credential --config private/server.json --output private/fw-mqtt.json` adds the section and writes the private file the firmware build reads. A second run is refused rather than rotating silently.
- **Broker:** the firmware role, its ACL, and a retained-message limit for its namespace.
- **API:** `GET /api/status` gains a `replacement` object: the latest health, its age, stale or online, and the last few request replies. Add `POST /api/replacement/request` with `{"op":"health"|"ping"}`; the server generates the request ID.
- **Compatibility:** stock handling is untouched, and the existing tests keep passing unchanged.

## Firmware build side

`build.py` reads `private/fw-mqtt.json` (broker address, port, device ID and password) into an ignored generated header, like the Wi-Fi credentials, and records only its hash in the manifest. A new startup policy `fw08-transport-v1` binds the `PLMQT1` record format both ways, as FW07's policies do.

## Stages and acceptance

**A, offline.**
- Core MQTT codec and client state machine. Host tests cover the encodings, malformed and oversized input, keepalive and timeouts, and every reconnect path.
- An integration test against the server's broker: the firmware role can connect, publish health and get a reply; it can't publish or subscribe outside its topics; the stock role can't reach the firmware namespace.
- Server config, credential command, ACL, API and docs.
- The structural no-dispense check.
- The UART auditor for `PLMQT1`.

**B, bench.** One boot on the FW07 bench. Pass criteria:
- The feeder connects within 15 s of its first successful DNS check.
- `/api/status` shows health with the build ID that UART printed.
- Periodic publishes arrive at 30 s (±5 s).
- A `ping` and a `health` request round-trip.
- Nothing resets, and UART shows no credential.

**C, bench recovery.**
- Restart the server while the feeder runs: the server sees the will or goes stale, then sees a reconnect within 30 s of the broker returning.
- A hotspot outage: reconnect after Wi-Fi rejoins.
- An unsupported request: refused and logged.
- Full-flash A/B reads across the boot are identical, as in FW07.

**Done when** A–C pass and the carried items below are on the board.

## Carried items (to record when FW08 closes)

- **Plaintext transport and shared Wi-Fi trust**, owned by FW10 and FW17. Either card adds authenticated or encrypted messages before carrying updates or feeding.
- **Credential provisioning without a rebuild**, owned by FW25.
- **Server-side multi-device support**, unowned. The server is single-device by design today.
