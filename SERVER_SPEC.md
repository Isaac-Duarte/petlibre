## Crate layout

The board's [target architecture](SERVER_BOARD.md#target-architecture) stands, with these settled:

| Topic | Decision |
| --- | --- |
| `wellfed-service` | One crate with a module per domain (accounts, household, commands and the journal, owner data, derived views, alerts, audit, export). Each domain has its own error enum, wrapped in the crate's `Error`. Derived views are a pure module inside it |
| Auth | The service owns the rules: argon2, issuing and verifying sessions and tokens, expiry, the login-limit state, and a `Permission` enum with one `can(role, permission)` table that holds the [matrix](#permissions). `wellfed-server` owns only the axum extractors that call it |
| Jobs | The supervisor lives in `wellfed-server` and schedules on the cancellation tree with the injected `Clock`. Each job's body is a service method that takes `now` (`run_retention`, `run_backup`, …) |
| Hub | **Changes the board:** the hub lives in the service, not the mirror. The mirror exposes a per-feeder broadcast of typed mirror events (events, gaps, samples, link state). The service merges command results, alerts and install progress into it and assigns the stream ids. The mirror knows nothing of alerts or users |
| Ingest | The mirror writes to the store directly: it decodes each event once and calls the store to record the raw row, its projections and the cursor in one transaction. The service reads projections |
| Store writes | Keep today's single writer connection beside the read pool. The API design's "writer task" wording is updated to match |
| `wellfed-server-client` | In `src/client/`, async over `reqwest` with rustls, including following the SSE stream. The CLI and the server's tests use it |
| Export format | The archive's manifest and row types live in `wellfed-formats`, since export writes the archive and import reads it. The manifest's hashes go through `wellfed_formats::canonical` |
| Release verifier | Reuse the verifier the feeder's own checks are tested against, never a copy. If it drags in firmware-only dependencies, split out a small host-safe crate and record it in the run log |
| Dependency rules | `cargo xtask check-repository` enforces the allowed edges from `cargo metadata`, with an error naming the edge: no `sqlx` above the store, no `axum` below the server, and the server crates' arrows as drawn |
| `wellfed-api` on Android | Enforced by an allow-list of its dependencies in the same check. No Android cross-compile in `make check` |

## API conventions

- `/api/v1` may change freely until the first server release; the `openapi.json` diff shows every change. Migrations squash until then too.
- Every list takes `?after=<opaque cursor>&limit=` (default 100, max 1000) and answers `{ items, next }`, with `next` null at the end: events, commands, audit, alerts and raw samples alike.
- New refusals are `ErrorCode` variants (`key_reused`, `install_running`, `account_disabled`, …), never a string.

## Accounts and auth

### Permissions

| Action | Owner | Member | Viewer |
| --- | --- | --- | --- |
| Status, history, samples, plans, food views | ✓ | ✓ | ✓ |
| Feed and cancel | ✓ | ✓ | |
| Settings, lock, play, a time sync that does not step the clock | ✓ | ✓ | |
| An invite for their own phone (one key per token) | ✓ | ✓ | |
| Their own commands and audit entries | ✓ | ✓ | ✓ |
| Everyone's commands and audit | ✓ | | |
| Users, others' tokens, household, time settings | ✓ | | |
| Pets, foods, refills | ✓ | | |
| Wi-Fi, reboot, listing and revoking clients | ✓ | | |
| Adopting and removing feeders | ✓ | | |
| Releases, installs, backups, export, import | ✓ | | |

Every account sees every feeder; there are no per-feeder grants. A member who cannot list clients still gets their own phone's key through the server, which records which account it belongs to (SV24).

### Sessions, tokens and passwords

- A browser session lasts 30 days from its last use. A phone token lasts until revoked unless it was given an expiry. An account's expiry overrides both.
- An account past its expiry is disabled, not deleted: its sessions and tokens stop, its name stays in the audit, and an owner extends or deletes it. The jobs mark it; nothing is removed.
- A password has at least 10 characters, with no other rules. An owner sets a temporary password for another user. A sole owner who is locked out runs `wellfed-server reset-owner` on the host.
- Failed logins are limited to 5 a minute per name and 20 a minute per address, in token buckets held in a bounded map (10,000 entries, least recently used evicted), answered `429` with `Retry-After`. No account is ever locked, and other sessions are unaffected.

## Commands and feeds

- **The journal row** is written before the command is sent: the idempotency key, user, token, feeder, kind, a canonical hash of the request body, the device request id, the feeder's boot count, the state (`sent`, `answered`, `unknown`, `resolved`), the outcome and, for a feed, its number.
- **A key reused with a different body** is refused `422 key_reused` and never sent.
- **`POST /feeders/{id}/feed`** answers `202` with the journal entry once the feeder answers `Feeding { feed }`. The `Fed` outcome arrives on the stream and at `GET /commands/{key}`. There is no long poll.
- **`GET /commands/{key}`** reads one entry (the caller's own; an owner's any). `GET /commands?feeder=&state=` lists them, so `state=unknown` is the uncertain list.
- **No server-side feed limits.** The feeder's own refusals are the policy.
- **The journal is kept forever.** It is the audit's source and part of the export.
- **Removing a feeder** revokes the server's key on it (or reports that it could not) and archives the feeder. Its events, samples and journal stay readable and exported. Adopting the same identity again un-archives it and continues its history.
- **Installs** are owner-only and one at a time per server: a second is refused `409 install_running`.

## Household and time

`POST /setup` requires the household's IANA zone, prefilled from the host's. `PATCH /household` changing the zone pushes the POSIX rule to every feeder; a feeder that cannot be reached gets it when it reconnects.

## Owner data and derived views

- **Pets:** name, species, birth date, a weight log and a daily calorie target. Photos wait for the UI.
- **Pets and feeders** are many-to-many. Intake from a feeder that several pets share is split evenly between them, and the view labels it an estimate, since the feeder cannot tell who ate.
- **Food:** each feeder has one current food, with a history of when each started, so a past feed's calories use the food it served.
- **Refills:** an owner records one with `POST /feeders/{id}/refills` (grams, or a full bag). A food-beam change from low or empty to ok with no refill recorded shows "refilled?" in the food view and does not reset the count.
- **Portion size** *(provisional; the owner reviews it in the morning):* a portion is 1/12 cup, taken as FW18's calibration. Each food carries `grams_per_cup` (default 110), so grams = portions × 1/12 × `grams_per_cup`.

## Data plane

- **Samples:** raw samples are kept forever by default, and the owner may set a raw retention in days. Hourly rollups are always kept.
- **Debug log (SV14):** an owner can follow it live on the stream. The mirror tails it only while someone is following, and none of it is stored.
- **Alerts (SV70):** a feeder offline for more than 10 minutes (the only setting), any feed that ends `Uncertain`, `Failed` or `Expired`, an empty hopper, a failed install, a clock invalid for more than an hour, and a feeder `Blocked` for more than 30 minutes. An alert clears itself when its condition ends, an owner may acknowledge it, and each change goes on the stream.

## Releases, data and operations

- **Releases:** fetching is off by default (`releases.fetch`). When it is on, a job checks the project's GitHub releases daily, and an owner can ask for a check at any time. Uploads always work. Nothing installs without an owner's `POST /feeders/{id}/install`.
- **Export:** a streamed tar with `manifest.json` (format version, server version, row counts, hashes) and a `.jsonl` per table, or `.csv` files with `?format=csv`. It carries no secrets, so after an import the feeders are archived and must be adopted again. Import runs only on a fresh server (no accounts), in one transaction.
- **Backups:** `VACUUM INTO data_dir/backups/` daily at 03:30 household time, keeping the last 7, plus `POST /backups` on demand. The key file is not copied into the backups; its place is documented beside them.
- **Configuration:** `data_dir/server.toml`, overridden by flags and environment variables. The sealing key moves to `data_dir/keys/server.key` (mode 0600), migrated from today's `config.json` on the first start.
- **CLI (`wellfed server`):** human-readable text by default, and with `--json` the API's bodies verbatim. It exits 0 on success, 1 on an error and 3 when an outcome is unknown.

## Open questions

Questions a parked card raises, for the owner.

- **Server-role keys can't run PutTime, invites, revoke, Wi-Fi, reboot or update ops (SV24, SV30, SV51).** The feeder lets only an owner's key run `PutTime`, `PutWifi`, `RevokeClient`, `Reboot` and the update operations (`allowed` in `wellfed-device-api` `server/request.rs`), and lets a `server` key create no invite at all (`Pairing::invite`, `Role::Server => false`); a member may invite members only. Adoption normally redeems an invite for the `server` role, so on most feeders the server cannot set the zone's rule, invite its phones, revoke their keys or its own, change Wi-Fi, restart the feeder or install: each is refused `feeder_refused` with `forbidden` (static analysis, and shown on the simulator by `a_server_role_key_is_refused_the_invite_and_records_nothing` and `a_removal_the_feeder_refuses_still_archives_and_says_the_key_stays`). Nothing is parked: the zone's rule is tried on every connect, time sync and zone change and the feeder stays online on the clock syncs' offsets; a phone invite records nothing when refused; a revoke the feeder refuses stays owed, with its last attempt shown; a removal archives the feeder anyway and says the key is left for the owner to revoke with `wellfed revoke`. Each works wherever the server holds an owner's key. The choice for the owner: adopt with an owner's invite (the server then holds the feeder's full authority, as the owner's CLI does), or a device-API change on the firmware board widening the `server` role, for instance `PutTime` with the zone alone (`ntp: None`), invites for members, and revoking the member keys the server itself invited. Until then an owner who wants these through the server adopts with an owner's invite, and otherwise uses the CLI at the feeder (`wellfed time --zone`, `wellfed invite`, `wellfed revoke`). For installs in particular, every release is signed and verified by the feeder itself and the owner approves each install on the server, so the `server` role could run the update ops (offer, chunks, state, cancel) while key statements and downgrades stay an owner's; until then `POST /install` on a `server`-role feeder is refused `409 feeder_refused` (`forbidden`).
- **An invite is not bound to a key (SV24).** The feeder's invite carries a role and a secret, not the key that will redeem it (`Pairing::invite`), so the server's record of whose phone a key is rests on the phone joining with the key it named. A phone (or anyone holding the invite text) can name key A and join with key B: B is then listed as unowned and A is never held, so B escapes the account's revocation until an owner revokes it by hand. The server cannot close this alone. The fix proposed is a device-API change for the firmware board: let `CreateInvite` name the key it is for, and refuse a handshake under that invite from any other key. With it, a revoke owed before the phone joins could also cancel the invite instead of waiting out its deadline.
- **Which key signs public releases, and how does a server get it? (SV50)** The firmware's built-in key is the bench key (`private/ota-key.json`, given to firmware builds only as `WELLFED_OTA_PUBLIC_KEY`), and the offline release key that feeders would hold in their release slot does not exist yet. Until it does, the server builds in no project key: the owner lists keys in `releases.project_keys`. Once the release key exists, should its public half be compiled into the server (and the packaging), shipped in its documentation, or stay a setting?
- **SV51 and SV52, which key installs.** The feeder lets only an owner's key offer an update, send chunks or read the update state, and adoption normally redeems an invite for the `server` role, so the server installs only on feeders adopted with an owner's invite; elsewhere `POST /install` is refused `409 feeder_refused` (`forbidden`). The same holds for SV52: reading bank 1 (`ReadBank1`) and the update state are an owner's too, so `POST /stock/read` and `POST /stock/restore` are refused the same way there (an uploaded copy is still kept and exported), and a stock restore always carries a downgrade statement, which stays an owner's in any case. Every release is signed and verified by the feeder itself, and the owner approves each install on the server, so should the firmware let the `server` role run the update ops (offer, chunks, state, cancel), keeping key statements and downgrades an owner's? Until then an owner who wants server installs adopts with an owner's invite.
- **When the login-limit map is full, refuse new clients or forget old buckets? (SV32)** Today it fails closed: while all 10,000 buckets still hold state, a login from a new name or address waits (`429`, at most a minute) until one refills, and a full map logs a warning once a minute. A flood of fresh names or addresses can then delay everyone else's first login by up to a minute, but never frees the name under attack. The alternative, dropping the least recently used bucket, never delays an honest login, but a flood of about 10,000 fresh keys between guesses pushes the target's bucket out and buys it five more guesses each round.
- **Should a user's own audit entries include what others did to their account? (SV33)** Today "own" means what the user did (and failed logins with their name): an owner resetting a member's password, changing their role or revoking their token shows in the owner's entries only. Showing changes made *to* an account in its holder's view too would tell a member when their access changed; it is one more filter column (the account a change names).

## Run log

Each deviation from the board's rules or this spec, with its reason.

- **SV01, arrows as a table.** The diagram's arrows are enforced as an explicit table of the workspace crates each server crate may take (in the API design), not their transitive closure, so the binary cannot reach past the service into the mirror. Edges the diagram leaves implicit are rows: the mirror takes `wellfed-api`, `wellfed-model`, `wellfed-client`, `wellfed-proto` and `wellfed-session`; the service takes `wellfed-store`, `wellfed-api`, `wellfed-model` and `wellfed-formats` (export); the test kit takes what it builds. The service also keeps `wellfed-client`, `wellfed-connect`, `wellfed-proto` and `wellfed-session` until SV07 moves the feeder tasks, which then removes them from the table.
- **SV01, rule scope.** Dev-dependencies are exempt from the arrows (tests build simulated feeders and whole servers) but not from the sqlx rule. "Below the server" for axum includes `wellfed-server-client`. The `wellfed-api` allow-list covers its direct dependencies; a new one needs an Android build check by hand, since `make check` builds no Android target.
- **SV01, the app's bridge crate.** The arrows name it `wellfed-app-bridge` (the crate map gave it no name), allowed into `wellfed-api` only; FP19 keeps that name or changes the table with it.
- **SV02, scope.** Only the server crates' pins moved. Host tools that pin the same versions (`wellfed-stock`'s `reqwest` and `tracing`, the tools' `sha2` 0.11) keep their own lines, to stay out of the firmware run's manifests; they can take the workspace entries later with no version change.
- **SV04, header order and the required key.** The header extractors run before the JSON body, so a request with a bad body and a missing or bad `If-Match` or `Idempotency-Key` now gets the header's problem first; a request with one fault gets the same answer as before. A route that requires `Idempotency-Key` refuses a request without one as `invalid` (400): `precondition_required` stays the code for a missing `If-Match`.
- Foundations SV01+SV02, SV03 and SV04 ran in parallel branches (different crates) rather than one at a time, to fit the night; each rebased on master before merging.
- **SV03, the epoch migration's test.** The squash removed the epoch migration, so its upgrade test (`the_epoch_migration_keeps_the_history_under_epoch_zero`) went with it; every other store test asserts what it did. A development database made before the squash no longer opens (its applied `0001` checksum differs and `0002` is unknown to the build): delete it and adopt again.
- **SV06, scope of the rule.** Clippy reads only the nearest `clippy.toml`, so the server's rule lives in `src/server/clippy.toml`, which repeats the root file's settings (`cargo xtask check-repository` refuses it when one is missing). Besides `Timestamp::now` and `SystemTime::now` it refuses `Zoned::now`, `SystemTime::elapsed`, `Uuid::now_v7` and `uuid::Timestamp::now` (each reads the clock), and std's `Instant::{now, elapsed}`. User and feeder ids stay UUIDv7, built from the `Clock`'s time and the injected `Random`. Log line timestamps (`tracing_subscriber`) are not time the server keeps and stay on the host clock. Monotonic deadlines stay, on `tokio::time::Instant`: they are not wall-clock time and a paused test runtime controls them, so they are not routed through `Clock`. `TimeZone::system()` reads no clock and stays in `main.rs` until SV30.
- **SV05, the server's tests over real HTTP.** The API tests drove the router in process (`oneshot`); they now run against the server on a localhost port through `wellfed-server-client`, so a request carries the address as its `Host` (an IP the server always answers to) rather than a configured name. Every test now runs on the kit's one config (sealing key, a one-hour session) with `FixedClock` and a seeded `Random`, where the API and end-to-end tests used the system's: nothing they assert depends on either.
- **SV05, requests the typed client cannot make.** A malformed request (no `If-Match`, a malformed key, a body missing a field) goes through `Client::request`, with the client's base, origin and credentials; one that must leave out the origin or name another host goes through `Client::http`. Their answers are read with the client's own `expect_status` and `decode`, so a refusal is still the typed `Problem`. Where a test checks the `Set-Cookie` header itself, it makes that call this way too.
- **SV05, the client's choices.** The session cookie's name moved into `wellfed-api` (`SESSION_COOKIE`), which the server and the client share. The client sends the server's own `Origin`, since the server's CSRF check refuses a cookie write without it. TLS is reqwest's `rustls` feature with its aws-lc provider: `rustls-no-provider` on ring was tried, but features unify across the workspace and every other reqwest client (wellfed-stock's) then panicked on build with no provider installed. Writes take a required `Idempotency-Key`, though the routes accept a write without one.
- **SV05, rustls with two providers.** The workspace now builds rustls with both ring (`mqtt5`) and aws-lc (reqwest's `rustls`), so rustls cannot pick a process default from its features: any code that builds a rustls config itself uses `ClientConfig::builder_with_provider` (or `ServerConfig`'s) with the provider named, never `builder()`. reqwest names aws-lc itself.
- **SV60, the old key file is deleted.** After `keys/server.key` (the key's 32 raw bytes) is written and synced, `config.json` is deleted rather than renamed, since it held only the key and a renamed copy would leave the secret in a second file; the server logs the move. A start interrupted between the two finds one key in both and finishes; two different keys are refused, and so is a `server.db` with no key file (a backup restored without its key), rather than making a new key that cannot open the stored feeder keys.
- **SV60, settings beyond the list.** `backups.keep` (default 7) joins the spec's settings, so SV64's count is the owner's; the 03:30 time stays fixed. `trusted_proxies` takes single addresses, not CIDR ranges; SV32 widens it if a proxy needs a range. A flag or `WELLFED_SERVER_*` variable replaces the file's value whole (`--host` given once replaces `hosts`), and `--no-discovery` stays as the short form of `--discovery off`, winning over `--discovery` and its variable (clap counts a set variable as given, so the two cannot be a clap conflict). A list override cannot clear the file's list. An existing loose `keys` directory is tightened to 0700 with a warning rather than refused, since the server's own user owns it. The file is parsed with `toml` and `serde_path_to_error` (both now workspace dependencies), so a refusal names the key's path and its line.
- **SV60, the key needs hard links.** The key file is linked into place (`hard_link`, which never replaces an existing file), so the data directory must be on a filesystem with hard links; SV62's packaging docs say so (a volume without them, such as some network or FUSE mounts, fails the first start with a write error). A staged `server.key.new` left by a crash between the link and its removal is removed on the next start.
- **SV22, pipelining, one request in flight per lane.** The feeder serves several requests outstanding per client: each pass a slot reads one frame, only once its last answer is out and any write it started has finished, from a one-frame buffer the driver fills only as far as there is room, so later requests wait in the TCP stack and are answered in the order sent (static analysis: `wellfed-device-api` `server/session.rs:149-193`, `server/mod.rs:277-286`, `server/wire.rs`; `wellfed-feeder` `feeder/serve.rs:499-517`, which the simulator runs too). So the feeder task pipelines rather than interleaves: a short command goes out while a step is in flight, and the operation's next step waits while a short command is in flight or queued. Each lane keeps one request in flight, so a cut session leaves at most two writes unknown and a queued command stays unsent until its turn (a caller that left is still dropped unsent); a command under an id already in flight on the other lane is held until that answer, so one answer never settles two. The task's own requests (clock, zone, the connect sequence) go out between commands and answer the lanes while they wait. `wellfed-connect` gains `Connection::request` (queue without waiting) and `Connection::receive` (the next answer or pushed message), additive beside `ask` and `next`. SV07's `a_short_command_queued_during_a_step_runs_before_the_next_step` now asserts only that the next step comes last: the read goes out beside the first step, so their two answers can arrive in one read and wake their callers in either order.
- **SV07, the mirror's edges.** Adoption's network steps moved with the sessions: `Mirror::locate` (the address, or mDNS) and `Mirror::enroll` (redeem the invite) hold the only `wellfed-connect` calls, and the mirror re-exports `wellfed-client`'s `Invite` and `InviteText` for the service to parse an invite. The service seals and unseals the feeder key, and hands the mirror the unsealed secret. `Clock`, `Random` and `RandomFailed` live in the mirror (the lowest server crate that needs both), re-exported by the service. The stored event body's decoder (`stored_event`) is the mirror's, beside its encoder. The service's hex for session tokens comes from `wellfed-formats` (already on its row), with the same lowercase-only rule, so the service row drops `wellfed-session` too.
- **SV07, the forwarder.** The service forwards each feeder's broadcast into the hub with a task per feeder, and keeps each feeder's link from that forward rather than reading the mirror's: the list then never shows a link the stream has not sent (reading the mirror's would let a test see `online` before the stream did). A forwarder that falls behind the broadcast (1024 updates) drops its backlog (resubscribes), publishes `resync`, then the link read after resubscribing, where the old in-line publish could not lag; when the broadcast closes and the mirror no longer holds the feeder, the forwarder drops its link entry. `Mirror::start` on a running id and `Mirror::stop` wait for the old task to end, and a task ends by sending `offline`, so a stopped feeder's last update is never `online` and two sessions never overlap.
- **SV07, the long-operation turn.** `Mirror::operation` waits for the feeder's one long-operation turn and returns an `Operation` whose `step` goes through the same queue as `ask`, with the same answer deadline and the same unknown and unsent rules. Nothing uses it yet; SV13, SV22 and SV51 do.
- **SV07, error domains.** `Error` wraps `Store`, `Invalid` (field checks, shared by every domain), `Account`, `Feeder` (adoption and the stored history), `Command` (anything sent to a feeder) and `Random`. A feeder's refusal of an invite is `FeederError::Refused` and of a command `CommandError::Refused`; both answer `feeder_refused`. Three internal failures that reused the command's "unexpected answer" are now named (`AccountError::Hashing`, `AccountError::Expiry`, `FeederError::Lookup`); each still answers `internal` with no detail. The mirror's refusals (`AskError`, `ConnectError`) map onto these variant by variant, so no HTTP code changed.
- **SV08, what the guard counts.** Rust sources only: the generated `openapi.json` (about 2,200 lines) and the sqlx metadata follow what they describe and cannot be split, so they are out of scope by type, not exempt by name. "Under `tests/`" means any `tests` directory in the path (an integration test and its modules, or a `src/tests/` module tree); a `tests.rs` file beside the code it tests keeps the 400 limit. Nothing was over when the guard landed.
- **SV63, the readiness route.** `GET /api/v1/status`, under the API's prefix like every authenticated route (the session cookie's path covers it either way), with the existing `Owner` extractor until SV30 moves it onto the `Permission` table. A failing store is reported in the body (`store: failing`, the error logged under the request's id) rather than as a `500`, so the view answers what it can; the feeder list comes from the store, so it is empty then. `jobs` is a list of `JobRun` (`retention`, `rollups`, `expiry`, `backup`; started, finished, outcome) that stays empty until SV12's supervisor records runs; SV12 may reshape `JobRun` freely (no release yet).
- **SV63, the request id.** tower-http's `SetRequestIdLayer` with random UUIDs, outside the trace layer so the `request{id, method, path}` span carries it, and `PropagateRequestIdLayer` inside it, so a refusal from the host, origin or size checks carries `x-request-id` too. A request that brings one `x-request-id` of at most 64 bytes of `[A-Za-z0-9._-]` keeps it (a reverse proxy's, so both logs share it); any other id, or several, is dropped before the id layer and replaced with a fresh UUID, so a client cannot fill or garble the log with it. The span leaves the query string out. The service's per-feeder forward runs under the same `feeder{id}` span as the mirror's task. Both spans are roots (`parent: None`), so a feeder adopted over HTTP does not log under that request's id for as long as it runs.
- **SV20, one key, one request, server-wide.** `GET /commands/{key}` names an entry by its key alone, so a key is unique across the server, not per user: a key reused by another user, for another feeder or kind of write, or with another body (the If-Match base included) is `422 key_reused`, unsent. Before, the device request id kept two users' same key apart and both ran. Keys are UUIDs, so only a buggy or hostile client meets this. The device request id keeps its hash (user, feeder, kind, key), stored in the entry and reused by a retry.
- **SV20, the send runs in its own task.** A journalled write is sent from a task on the service's tracker, and the request awaits it, so the entry reaches `answered` or `unknown` even when the HTTP caller hangs up; before, a write whose caller left was dropped unsent if still queued. Reads keep the old rule. A server that stops before recording leaves the entry `sent`, and every start marks what is left `sent` as `unknown`.
- **SV20, an unsent write leaves no entry.** When the mirror says a first attempt never left (the feeder offline, unsendable), its entry is deleted so the key is free for the same write later; a retry's entry is kept as it was. An answer that fits no write marks the entry `unknown`. A write without a key is journalled under a random (v4) key the server draws, so it is listed but cannot be retried.
- **SV20, outcomes and pages.** The recorded outcome is `done`, `settings` (the settings read back after a change, so a settings retry returns its first answer) or `refused` with the feeder's reason; a stale refusal replays as `412` with the settings read now. The list is oldest first, its opaque cursor the entry's row number, and it reads a member's own entries only (another's is `404`, not `403`). The token column exists, always null until phone tokens. The boot count is the one the server last read from the feeder's status. The tests of a member's view are at the service level: no route creates a member until accounts land.
- **SV20, migration file.** The journal is `0002_commands.sql`, per the run's migration rule; the store test of the pre-migration copy now names the newest pending migration rather than `1`.
- **SV20 review, retries and resends.** Inside a running server a `sent` entry is in flight (each start marks leftovers `unknown`), so only the attempt that made it sends it: a retry meanwhile is answered `outcome_unknown` unsent, rather than waiting on the first attempt's result. That also keeps a first attempt that never left from deleting an entry a retry is using. An `unknown` entry is resent under its device id only by its kind's rule, an exhaustive match: settings and lock resend; `feed` (a `CommandKind` now, though no route sends one yet) never does, so the feed route cannot resend by accident. The store's answer and unknown updates report whether a row changed, and the service logs one that did not. A settings change resent after the ring moved comes back stale though it ran, and a replayed stale refusal needs the feeder online to read the current settings; both are documented rather than worked around.
- **SV30, accounts.** Owners never expire (an expiry on an owner, or promoting an expiring account to owner, is `400 invalid`), so time cannot remove the last owner either. Expiry is checked on every request (no jobs exist yet to mark it): a disabled account's login is `403 account_disabled` once its password matches (a wrong one stays `bad_credentials`), and a session of its that is presented is deleted and refused the same way, so extending the account lets it log in afresh but never revives an old session (extending also ends any it still has). Setting a password ends the account's sessions: all of them when an owner sets someone else's temporary one, all but the one asking when a user sets their own. Any role changes its own password with `PATCH /session` (`{current, password}`), under the `OwnAccount` permission every role holds; a wrong current password is `401 bad_credentials`. Changing a role leaves sessions alone, since each request reads the role afresh.
- **SV30, sessions.** A session lasts 30 days from its last use; a request records its use when the last one is over a minute old, so a busy page does not write on every request. The cookie's `Max-Age` is 400 days, the most browsers keep, since a cookie that ends 30 days after login would cut a sliding session short; the server decides when a session ends. The migration (`0003_accounts.sql`, its own file under the run's migration rule) recreates the sessions table, so an upgrade logs everyone out, and gives a server set up before the household the defaults (`Home`, grams, 24-hour, `UTC`).
- **SV30, the household and its zone.** `GET /household` is every role's (the pages show units and the time format to all); `PATCH` is an owner's. Setup makes the household `Home` in grams and 24-hour time, in the zone the request names; `GET /setup` carries the host's IANA zone for the page to prefill (`TimeZone::system()` is read for that alone). The zone is stored by its canonical name. The mirror holds it for every feeder task: each sets the clock in it, then reads the feeder's time settings and writes the rule only when it differs, on every connect, every time sync (6 h) and every change, so a write the feeder refused as busy or stale is retried at the next. The rule comes from the tzdb bundled with `wellfed-client` (as the app's and the CLI's do) and is checked against that bundled zone only, the one the syncs' offsets come from too; `jiff-tzdb` joins the workspace for the mirror. Household changes run one at a time, so the stored zone and the mirror's are always the last change's. A stored zone that a newer tzdb no longer describes with a rule still sets the clock syncs' offsets, with no rule pushed; a name the tzdb no longer knows leaves the clocks in UTC, logged. An unknown name is `400 invalid` and a real zone with no rule `422 zone_unsupported`, both naming it.
- **SV30, permissions.** `Permission` has a variant per row of the matrix (`Read`, `Feed`, `Control`, `InviteOwnPhone`, `OwnHistory`, `AllHistory`, `Users`, `Household`, `OwnerData`, `FeederAdmin`, `Adopt`, `ServerData`), plus `OwnAccount` (one's own password, every role's); SV63's readiness view `/status` moved from its `Owner` extractor to `ServerData`, and SV20's `/commands` routes to `OwnHistory`, with everyone's entries under `AllHistory` rather than a role check, and `can` matches every role against every variant with no wildcard. The server's extractor `Allowed<P>` takes the permission as a type (`Allowed<need::Control>`), so a route's signature names what it needs; it runs before the path, so a refused role learns nothing about which ids exist.
- **SV30, `reset-owner`.** `wellfed-server --data DIR reset-owner [--name NAME]` prints a generated temporary password (20 hex characters) rather than reading one, so no password passes through a shell's history; it picks the only owner, or the named one when there are several, and ends that owner's sessions. It runs on the database with or without the server running.
- **SV50, the verifier.** `wellfed-core`'s offer check is host-safe (`no_std` with `ed25519-dalek` and `sha2`), so no crate was split out. The releases crate may not take `wellfed-core` (its arrows), so `wellfed-client` gained `release::verify`, which calls `admit_offer` with the project's keys as built-in and the owner's as enrolled, no retired keys, floor zero and no running build, then checks the image's length and SHA-256. A stock image and a version-0 one need a feeder-bound statement, so neither is a release.
- **SV50, the release file and its asset name.** Nothing defined a release file, so it is the 160-byte version 2 manifest followed by the image it names (the bank's contents, as `update::Image` offers them), and a GitHub release offers one as an asset ending in `.plota`. Drafts and pre-releases are skipped. The GitHub repository and API base are `wellfed-releases` defaults (`Isaac-Duarte/wellfed`, `https://api.github.com`), configurable in the crate for tests but not in `server.toml`.
- **SV50, the keys.** Both lists are new settings: `releases.project_keys` (`--release-project-key`), since the only key built into firmware today is the bench key and the release slot's key does not exist yet (see Open questions), and `releases.owner_keys` (`--release-owner-key`), since the server cannot read them from a feeder. The listing shows a release only while its key is listed, with its signer as today's keys say.
- **SV50, failures per asset.** An asset that fails to download is reported in the check's `failed` and tried again next time; only a release list GitHub does not serve ends the check. A record that does not parse or has lost its release file is skipped and logged, never fatal to the listing.
- **SV50, no `releases` table.** The cache directory is the index (a record file beside each release), so the card adds no migration while other cards add theirs; a table can replace it when installs need to join on releases.
- **SV50, error codes.** New: `release_refused` (422, with `Problem.release` naming the typed reason), `fetch_disabled` (409), `releases_unreachable` (502) and `too_large` (413, the upload's body limit; every other route keeps its 64 KiB limit). Releases are owner-only for reading too, per the permissions table; the routes take `Allowed<need::ServerData>` from SV30's permission table.
- **SV10, where the projection lives.** The store maps an `EventBody` (a `wellfed-api` re-export, inside its arrows) to its rows, so the SQL and the mapping sit together; the mirror hands it the event it already decoded beside the raw bytes (`NewEvent { body, raw }`; the kind now comes from the body). The store has no decoder of the feeder's encoding (no `wellfed-proto` edge), so a rebuild takes one: `Store::refresh_projections(decode)`, called through `Mirror::refresh_projections` by `Service::start` before any feeder task starts. `PROJECTION_VERSION` lives in the store beside the mapping.
- **SV10, no food level and no request or start times.** No event carries the food level, so there is no food-level projection. Today the food reading reaches a client only through the `Stats` op's `Food` page (`present`, `emptied`, `refilled`, `feeds_since_refill`), which SV13 pulls and keeps as samples, and through the feed traces' beam entries. SV41's refill count and "refilled?" hint and SV70's empty-hopper alert therefore read SV13's stats samples, and both cards now list SV13 as a prerequisite. If FP07 later adds a food-level event, its table and a version bump rebuild it from the history already held. A `Fed` event carries its feed number, source, portions, outcome, reason and the feeder's time when it ended, not when the feed was requested or started; the `feeds` row keeps the end (`at`) and the received time. The request time is the command journal's (SV20), joined to `feeds` on (`feeder_id`, `feed`), and the start the trace's (SV13); those cards join them rather than writing into a projection a rebuild would clear.
- **SV10, what projects.** Feeds, lock changes, boots (bank and reset flags), clock syncs (validity begins at one; an event's absent `at` marks an invalid clock) and `FeedingBlocked` changes. Settings and Wi-Fi changes, enrolments, revocations, lost-event counts and supply changes project nothing yet; the match names each, so a new event kind needs a decision. `FeedOutcome`, `FeedReason` and `Blocked` gained `code`/`from_code` in `wellfed-model` (their JSON spelling, tested) for the stored text.
- **SV10, migration file.** The projections are `0004_projections.sql`, per the run's migration rule (SV20 and SV30 took `0002` and `0003`).
- **SV10, the rebuild.** One writer transaction: clear every projection, read the raw events in batches of 512 in key order, project each, write the version. Readers keep seeing the old projections until it commits, and ingest waits behind it. A body that does not decode projects nothing and is counted (logged as a warning). Reads take a received-time window (`from` inclusive, `to` exclusive) with no limit, since a household's feeds and changes are few; a paged read joins when a route needs one.
- **SV31, the secret and its hash.** A token's secret is `plt_` and 64 lowercase hex digits (32 random bytes), stored as the SHA-256 of the bytes like a session's: 256 bits of entropy need no argon2, and a lookup by hash needs no per-token salt. The prefix tells a token from a session and lets a leak scan find one. The secret is in the `201` (with `Cache-Control: no-store`) and nowhere else; `CreatedToken` and `BearerToken` print no secret. Tokens live in their own table (`0005_tokens.sql`, the run's migration rule; SV10 took `0004`): name (1-64 characters), created, last use (recorded when over a minute old, as a session's), an optional expiry that must be in the future, and the user, whose deletion cascades.
- **SV31, only a login makes a token, sets a password or adds an account.** `POST /tokens`, any password change (`PATCH /session`, and `PATCH /users/{id}` with a password, one's own or another's) and `POST /users` from a token are `403 session_required` (a new `ErrorCode`), so revoking a leaked token is enough: it cannot have minted other tokens, nor a password or an owner account to log in with and mint them (review finding). A token's other writes, an owner's role and expiry changes included, go through. Tokens are made for oneself only; an owner lists and revokes anyone's (`GET /tokens` is everyone's for an owner, one's own for the others, oldest first, unpaged like `/users`). Another user's token is `404` to a member or viewer. Every role holds its own tokens under `OwnAccount`; others' are `Users`.
- **SV31, a disabled account keeps its tokens.** The spec's "nothing is removed": a token of an account past its expiry is refused `403 account_disabled` and kept, so extending the account brings the phone back without pairing it again. Sessions differ (SV30 ends them at the extension). A token's own expiry is `401 unauthenticated` and stays listed until revoked. A password change (from a login), the user's own or an owner's reset, leaves the account's tokens; each is revoked on its own.
- **SV31, `Authorization` is the whole credential.** A request that carries `Authorization` is authenticated by it alone: a malformed one, or another scheme, is no credential, never a fall back to the cookie beside it. So skipping the `Origin` check for a `Bearer` write cannot let a cookie through unchecked (a page cannot send the header cross-site anyway, as the server grants no CORS). Unauthenticated writes (`/setup`, `/session`) skip the check under a bearer header too, which only a non-browser client can send. The stream rechecks its token every minute, as it does a session.
- **SV31, the caller.** The service's writes take a `Caller` (the user and the token they came through, `None` for a session) instead of a `User`, so the journal records the token; a retry through another token of the same user is the same request (the key's check compares the user, not the token). Reads keep `&User`. The command view gains `token`.
- **SV12, the mechanism.** `Clock` (in the mirror) gained `sleep_until(at)`, a provided method that sleeps on tokio's timer and reads the wall clock again at least each minute, so a stepped clock is noticed; the test kit's `ManualClock` overrides it to wake when the test moves the clock. Tokio's paused time was rejected: its auto-advance fires sqlx's pool timeouts and the mirror's timers while SQLite works on its own threads. The supervisor works its schedule out again at least hourly, so a change of zone or of `releases.fetch` moves the times within the hour.
- **SV12, the schedule.** `expiry` and `rollups` hourly, `retention` 03:00, `backup` 03:30 (the spec's time) and `release_check` 04:00, in the household's zone (UTC before setup); `Job` gained `release_check`. The next time follows the job's last recorded run (`0006_jobs.sql`, one row per job, after SV10 and SV31 took `0004` and `0005`): a job missed while the server was down runs once at the next start, an hourly job that never ran runs at once, a daily one at its next time. A failed run waits for its next time too; nothing retries sooner. Jobs due together run in `Job::ALL`'s order. A job cut short by shutdown is not recorded.
- **SV12, "the jobs mark it".** Disabled stays derived from `expires_ms`, which every request already checks, so there is no column to mark: the expiry job deletes the sessions of expired accounts and the idle ones (login no longer does). Tokens are left alone: SV31 keeps a disabled account's tokens, refused while it is disabled, so extending the account brings them back. The account is never deleted.
- **SV12, stubs that would mislead.** `retention` and `rollups` run and succeed with nothing to do until SV11 gives samples values. `backup` is in the enum and the schedule but `Service::job_scheduled` returns false for it until SV64 fills its body, so readiness never shows a backup that was not taken.
- **SV12, no trigger route.** `POST /jobs/{job}` was left out: SV50's `POST /releases/check` and SV64's on-demand backup already cover what an owner would trigger, and a trigger would need the supervisor in the router's state.
- **SV12, turning fetching on.** `releases.fetch` is read at start, so it is turned on by a restart. Its schedule follows the last recorded check, so a server that checked once, had fetching off for more than a day and is turned back on checks at once (within the hour, if what is scheduled ever changes while the server runs: `a_release_check_turned_on_is_picked_up_at_the_next_wake`). A server that never checked waits for 04:00. Either way an owner can check at once with `POST /releases/check`.
- **SV40, photos deferred.** Pets carry no photo: the spec's "Photos wait for the UI" overrides the board's photo files, so no upload route, size or type limit, or data-directory files exist yet.
- **SV40, owner data's shape.** Species is a closed enum (`cat`, `dog`, `other`). Energy is integer kcal per kg (labels print it so, and integers keep calories exact), the bag size is required (a full-bag refill needs it) and `grams_per_cup` defaults to 110; ranges are checked (`400 invalid`). Pets and foods list whole (a household has a handful); weights, refills and the food history page as `{ items, next }` with the spec's `?after=&limit=`. A weight may be backdated (`at`, a vet's reading) but not set in the future (`400 invalid`), so its log is ordered by reading time with a `<ms>.<id>` cursor; every time the server stores is whole milliseconds, and a write answers with the stored value, so a returned `at` matches the log and its cursor; refills and the food history page by row number. Weights and refills can be deleted, for a mistaken entry. Store modules are `pets`, `foods` and `refills`, not one `owner` module; the migration is `0007_owner_data.sql`, after SV10, SV31 and SV12 took `0004` to `0006`.
- **SV40, the food history's time semantics.** `PUT /feeders/{id}/food` starts a period now; the food at a time is the last change made by then, the change's own instant included. A change is never dated before the one it follows (a clock that stepped back dates it with the last), so the newest change is always current, and every "now" (the food view, a full-bag refill) reads the newest change rather than the history at the clock's time, which a clock that stepped back would read too early. Choosing the food already served keeps its period. History periods carry `from` and `to` (the next change). `Service::feeder_food_at` is the lookup SV41 uses for past feeds' calories. A feed maps to a period by the feeder's own clock (the projection's `at_s`) when it was valid, else by when the server received it (`received_ms`): `at_s` is when the food dropped, and `received_ms` can lag by a whole offline spell. A food a feeder's history or a refill names cannot be deleted (`409 food_in_use`); editing a food applies to the past too, so a new recipe is a new food.
- **SV40, refills and the food view.** A refill is recorded now (no backdating, and never before the feeder's last refill, should the clock step back, so recording order is time order), as `{"kind":"grams","grams":N}` or `{"kind":"full_bag"}`; a full bag is the current food's bag size then, and on a feeder with no food it is `409 no_current_food`. Each refill keeps the food and the user it was recorded under. `GET /feeders/{id}/food` answers the current period and the newest refill now; SV41 adds the derived fields (remaining, estimate) to that body. The history is at `GET /feeders/{id}/food/history`. Pet-to-feeder links are `PUT`/`DELETE /pets/{id}/feeders/{feeder}`, idempotent to add; the pet's body lists its feeders now.
- **SV40, pet-to-feeder links keep their history.** A link runs from its assignment to its unassignment, so SV41 splits a past day's intake among the pets the feeder served then, not the ones it serves now. A pair has one open link at most, and a new one never starts before the pair's last ended (a clock that stepped back starts it there), so a pair's links never overlap. `Service::feeder_pets(feeder, from, to)` lists the links overlapping a window; a link that began and ended at one instant served no time and overlaps nothing. There is no HTTP route for the history yet: SV41's intake view is its reader.
- **SV21, settling a feed by number, not boot count.** A `Fed` event carries no boot count, and the feed number is the feeder's journal id, which counts on across restarts (a restart mid-feed resolves it as `uncertain` under that same number), so an answered feed is settled by the `Fed` event with its number alone. A feed whose answer was lost has no number: it is settled by the one `Fed` event after the history the server held when it was sent (two new journal columns, `history_epoch` and `history_seq`, in `0008_feeds.sql`), by the server's key, or by the feeder with outcome `uncertain` (the only `Fed` event the feeder names itself in: an interrupted feed resolved at boot), that no other entry claims, and only while it is the feeder's one unknown numberless feed with none in flight; anything ambiguous stays `unknown`. The history position is the newest event held, or the start of the live session's epoch when none of it is held yet (a session's replay may still be arriving as it goes online), so a feed's scan never reaches back past what the server held. The boot count decides only when the history can no longer settle it.
- **SV21, `unrecorded`.** "A boot-count change with no record" is a resolution of its own, `resolved` with outcome `unrecorded` ("it never ran, or its record was lost; whether food was dispensed is not known"), reached only once the boot count changed, the feeder's readiness is past `starting`, `resolving` and `feeding`, the server holds its history through the live status's newest event in the live session's epoch (`Mirror::epoch`), and no gap or `lost` event follows the feed: the feeder's event queue is RAM, so a reset can lose a `Fed` event whose result the journal kept, and `unrecorded` must not claim the motor never ran. A `Fed` event found later replaces it. An answered feed also ends `resolved` (with outcome `fed`), not only an uncertain one.
- **SV21, no resend of a feed at all.** The device API doc allowed a same-boot resend of an unknown feed after comparing boot counts; the server never resends one (SV20's rule), since no check can rule out a restart between it and the resend. A retry of an unknown feed is `504 outcome_unknown` until the history settles it, and the doc now says so.
- **SV21, settling driven off the broadcast.** The service subscribes a second receiver to each feeder's mirror broadcast and settles that feeder's open feeds on every event, gap and link change (and after a lag), and once more after a feed's answer is recorded (its `Fed` event may be stored first). Ingest is untouched. A live `Status` is read only when the cached status already shows a restart and its newest event is held. Each feeder settles under a lock of its own. The history is read from SV10's feeds projection (`Store::feed_result` by number, `Store::feeds_after` by position; its read of a time window now shares their row type), not by decoding raw events.
- **SV21, the stream's journal updates.** Every change to a journal entry (answered, unknown, resolved), not only a feed's result, is a `command` stream event carrying the entry; each user is streamed their own, an owner everyone's, as `GET /commands` shows them.
- **SV21, cancel.** `CommandKind::Cancel` is resent under its device id when unknown (a repeat stops nothing new and is refused `not_found` once the feed ended); its `Idempotency-Key` is optional like the other non-feed writes.
- **SV21, the simulator feeds.** `wellfed-feeder-sim` gained a feeding owner on the real feed journal (`wellfed_core::store::feed_journal`) in the storage region's journal sectors, a fixed 200 ms per portion and no motor, so it now claims `Capabilities::FEED`; `Control::StallFeeds` holds a feed in flight, and the harness relay can hold back only the feeder's answers (`hold_answers`) or cut every session (`cut`). A feed is queued and reserved at the owner's next step, as the firmware's owner reserves on its own turn, so `Feeding` is answered only after the reservation; the simulator resolves an interrupted feed as it opens and records its `Fed` event at its first step, where the firmware resolves it once its owner opens and queues the event. A relay cut wins over bytes it held back, which are dropped. The device conformance suite still drives the loop with no feeding owner.
- **SV21, guards without a test.** Two of the `unrecorded` guards are pinned by reasoning only: the live-epoch check (the held history must be in the live session's epoch) needs a simulator scenario that re-creates the event ring mid-session, and the `lost`-event half of the incomplete-history check needs the simulator to record a `Lost` event, which its platform never does (`take_lost` is 0). The gap half is tested (`a_feed_stays_unknown_after_a_gap_in_the_history`).
- **SV21, a feed number per epoch.** Whether a `Fed` event's number is already claimed is asked within the epoch the lost feed was sent in (`Store::feed_claimed`), since a ring a storage wipe re-created counts its feeds from 1 again.
- **SV21, migration file.** `0008_feeds.sql`, per the run's migration rule (`0005`-`0007` were taken).
- **SV34, the token file.** `wellfed server login` reads the password from standard input, opens a session, makes a token (`wellfed-cli` unless `--token-name`), writes `private/wellfed-server.json` (`--token-file`; the server's URL, the account's name, the token's id and secret) through `wellfed_formats::private::write_json`, mode 0600, and ends the session, so only the token outlives the command. A second login over a kept file is refused until `logout`, so no token is orphaned. `logout` revokes the token and deletes the file; a token the server answers `unauthenticated` or `not_found` counts as already revoked, and any other failure keeps the file. The `--json` body of a login is the `Token` without its secret, which goes to the file alone. The file is the CLI's own (only it reads it), so its type stays in the CLI rather than `wellfed-formats`.
- **SV34, `--json` bodies.** The client decodes each answer into `wellfed-api`'s types, and the CLI prints them re-serialized, one compact JSON document per line (a feed prints two: the reserved entry, then the settled one). The types are the server's own, so this is the server's body less whitespace. A refusal's `Problem` and a stale edit's current settings print as bodies too, before the exit 1.
- **SV34, which failures are unknown.** A keyed write is unknown (exit 3, its key and `wellfed server command <key>` printed, never sent again) on `504 outcome_unknown`, a `500 internal` (the server may have failed after sending), a lost or garbled answer (`reqwest` errors other than a refused connection, an unexpected status, an undecodable body). A refused connection and every other problem ran nothing and exit 1. A feed whose result does not reach the stream within 120 s, or whose stream ends first, also exits 3 with its key. `command <key>` exits as its write settled: 0 for done (or a feed `done`), 1 for a refusal or a feed that ended `failed`, `cancelled` or `expired`, 3 while it is sent, unknown or still feeding, and for an `uncertain` or `unrecorded` feed.
- **SV34, the verbs that wait.** `clients`, `revoke` and `reboot` over the server waited for SV24's routes (added with SV24), `install` for SV51's and `export` for SV42's; none was on master. `users` lists, changes a role or an expiry and deletes; adding an account needs a login (`session_required` from a token), so it stays the web page's. The CLI reaches `wellfed-api`'s types through `wellfed_server_client::api`, a re-export, since the layer check lets the CLI depend on the client alone.
- **SV34, exit 3 is for keyed feeder writes.** Only the writes sent to a feeder under an `Idempotency-Key` (settings, lock, feed, cancel) can end unknown and exit 3. Account and token writes (`users set`, `users delete`, `tokens revoke`, `login`, `logout`) carry no key and touch no feeder: any failure there exits 1. A login whose token file cannot be written revokes the new token through its still-open session and logs out before failing.
- **SV11, one number per sample.** Each metric is charted by one figure, picked here: `power` and `supply` the battery's millivolts, `rssi` dBm, `heap` free bytes, `loop` the 99th-percentile pass, `gateway` the round trip, `wifi` the access-point changes (`wellfed_api::sample_number`). A sample without its figure (power on the adapter with no battery, which is every simulator sample) has no number and is left out of the rollups, so an hour with none is not listed. The mapping is versioned (`SAMPLE_NUMBER_VERSION`), and a new version renumbers the stored samples at start from their bytes, as the projections do.
- **SV11, rollups folded by id, not at ingest.** The hourly `rollups` job adds every sample stored since the last one it folded (`sample_marks.rolled`; ids are AUTOINCREMENT, so never reused after retention empties the table) into its UTC hour, so ingest's batches stay a plain insert, the job is the catch-up after downtime, and a sample that arrives late for an hour joins it. An hourly read adds the unrolled tail from the raw rows (by id, so it scans only that tail), so it is whole between runs. Hours are UTC, so a zone with a half-hour offset sees its local hours split; charts in local time read raw or accept that.
- **SV11, samples broadcast before they are written.** Events and gaps are still stored before they are broadcast; a sample goes on the broadcast as it arrives and into a batch written when it holds 32, `Timing::sample_wait` (10 s; the test kit's 100 ms) after the first, or at the session's end, so the live view is not held up. A batch whose write fails ends the session like any store failure; the feeder never replays samples, so that batch is lost.
- **SV11, retention in whole rolled-up hours.** `retention` rolls up first, then deletes raw samples received before the start of the hour `raw_sample_days` back, and only those already rolled up, so an hour's rollup never sits beside part of its raw rows and a renumbering can rebuild exactly the hours whose raw rows remain. Hour pages take the same `{ items, next }` as raw ones.
- **SV64, the backups' choices.** The copy runs on a read connection (`VACUUM INTO` needs no write lock), so ingest and requests go on. The daily and on-demand copies share `backups.keep`. A copy is named by the second it was taken, with `-2`, `-3`, … for more in one second, rather than refusing a second request. `POST /backups` takes no `Idempotency-Key`, since a repeated copy only pushes out the oldest. `Timing` gained `sample_wait` and the service `Config` gained `raw_sample_days` and `backups`.
- **SV51, where the driver lives.** The board put the install driver in `wellfed-connect`, the API design in `wellfed-releases`. It is `wellfed_connect::update::push`, generic over a `Steps` trait (send a step, reopen and read the bank and build, tell an activation whose answer was lost, report progress), so the CLI keeps its own sessions and the server's steps are `wellfed-mirror`'s `Operation::install` on the long lane; `wellfed-releases` only verifies, and the service hands the mirror the release's bytes. No crate's arrows changed but the test kit's, which takes `wellfed-core` to sign test releases (the arrows table and the API design together).
- **SV51, only an owner's key installs.** The feeder takes update requests from an owner's key only, and adoption normally redeems a `server` invite, so `POST /install` on such a feeder is refused `409 feeder_refused` (`forbidden`) before anything is sent: see the open question.
- **SV51, reading an install.** `POST /install` is `ServerData` (owners), `GET /feeders/{id}/install` is `Read`, since the stream already carries every install's progress to every account and a failed install is an alert everyone sees (SV70).
- **SV51, state and the claim.** One slot in the service holds the running install: the one-at-a-time claim and its live progress. The `installs` table (`0010_installs.sql`, renumbered after SV21's `0008_feeds.sql` and SV11's `0009_samples.sql`) keeps each install when it starts and ends, not each chunk; each start marks a row left `running` as `failed`/`interrupted`, so nothing is half-claimed after a crash. On shutdown the task stops without writing, the same path a crash takes. An end the store refuses is tried once more; if that fails too, the service keeps it in memory and `GET` answers it over the row's `running`, until a restart marks the row interrupted. The latest install is the one started last (by time, then by insertion order), not by id, since two can start in one millisecond. A feeder the server has no session with is refused `503 feeder_offline` rather than waited for.
- **SV51, the CLI verb.** `wellfed server install [--feeder X] <release>` starts an install and follows it on the stream (opened first) to its end, printing each change; it exits 0 on `activated` or `already_running` and 1 with the reason on `failed`. Without a release it reads the feeder's running or last install. It is not a keyed write, so it never exits 3.
- **SV52, the server signs nothing.** "Restore stock" needs the stock image signed by an update key the feeder trusts, with a downgrade statement for the feeder at its floor, and the server holds no signing key (releases are verified with public keys only). So `POST /feeders/{id}/stock/restore` takes the manifest and the statement the owner signed on their computer (`wellfed server stock restore --version <n>` downloads the server's copy, checks it with `Frozen::stock` against the pinned container, signs with the update key and reads the floor from `GET /feeders/{id}/stock`), and the server sends them only after checking that the manifest is a stock-kind offer of exactly the copy it keeps. A web UI's "Restore stock" needs the same signature from the owner's key; where it signs is the app's and web UI's question when they land.
- **SV52, where the copy comes from.** The bank-0 role serves bank 1 only before promotion, when the installer (the CLI or the app) is the feeder's only client, so beside the server's own read (`POST /stock/read`, for a feeder the server reaches on bank 0) an owner uploads the copy the installer kept (`POST /stock/upload`, a path apart from `GET /stock/backup` so the upload alone takes the release upload's size limit). The read is answered when it ends, rather than streamed, and claims no slot: the long lane already runs one operation per feeder, and a read while an install runs on the feeder is refused `409 install_running`, as the feeder would answer `busy`. A verified copy kept already is answered without reading.
- **SV52, storage.** The copy lives in `wellfed-releases` (`Stock`, `stock/<identity>/stock-1.1.15.bin` and its record), the CLI's layout, keyed by the feeder's identity so a re-adopted feeder finds it. The pins are a field of the releases' config, `StockPins::STOCK` in the binary with no setting, and a synthetic stock's in the test kit; `StockBackup::verified()` became an `Option`, `Some` only for the real pins, so no other pins can let an installer promote.
- **SV52, promotion waits for the backup.** As the installer's promotion waits for a `VerifiedBackup`, `POST /feeders/{id}/install` reads the feeder's update state first and, on a feeder idle on bank 0 with no install stopped there after writing a byte (bank 1 may hold stock, its only copy), is refused `409 stock_backup_needed` until a verified copy is kept; an install already writing bank 1, or one that stopped after writing some of it, has overwritten it and goes on. The kept copy counts once it verifies against the server's pins, which a real server fixes to stock's own, so there it is a `VerifiedBackup`; the test kit's synthetic pins never give one by design, so the gate asks for the kept copy, not for `verified()`. A feeder back on bank 0 after a failed trial of a replacement also reads as over stock; its owner installs with the CLI until the firmware tells the two apart.
- **SV52, `GET /stock` asks the feeder for owners only.** Its `feeder_state` is a live update-state read; members and viewers see `null`, so the page they poll never reaches the feeder.
- **SV52, a restore is an install.** It shares the installs' one slot, their table (`0013_stock_restores.sql` adds `target`; `release_id` holds the backup's SHA-256 for a restore), their driver on the long lane and their `install` updates, so `Install.release` became `Install.target` (`release` with its id, or `stock` with the backup's SHA-256). Like a release's install it carries no idempotency key and is never re-offered; once activated the feeder runs stock and the server's task keeps trying to reach it.
- **SV51, no idempotency key.** An install is not a journaled write: a retry while it runs is `409 install_running`, and one after it activated finds bank 1 already running the build on its first status read and ends `already_running` with nothing sent (written 0), so nothing installs twice. The driver tells that apart from an activation whose answer was lost by whether the offer went out: the same check, before the offer, is `already_running`, after it `activated`. The feeder's `same` refusal answers an offer of the build bank 1 runs, which the driver never sends. The driver's pace is the CLI's: 200 ms between state reads while bank 0 writes a sector, and 5 s after bank 1 gives way before looking for bank 0's session.
- **SV32, the limits.** The buckets are a generic cell rate: each name and address keeps the time it is next full, on the service's `Clock`, clamped to a minute ahead so a clock stepped back never refuses longer than a full bucket would. An attempt spends from both buckets before its password is checked (a check-then-spend after the hash would let a concurrent flood all pass), and a successful login gives it back; a disabled account's right password does not. A refused attempt spends nothing. One map of 10,000 holds names and addresses together; how it stays bounded is the next entry. A name counts trimmed, lowercased and cut to 64 characters (longer than any account's, and a 64 KiB body cannot make a large key); an IPv6 address counts by its /64 and an IPv4-mapped one as its IPv4 address. `Retry-After` is whole seconds, rounded up. The code is `login_limited` (429), and `wellfed-server-client`'s `Error::Problem` now carries the `retry_after` it named.
- **SV32, the proxy.** `trusted_proxies` now takes CIDR ranges as well as addresses (flags and file alike, logged at the start), since a proxy in a container has no fixed address. The client's address is read from `X-Forwarded-For` when present, else `Forwarded`, right to left, skipping trusted hops; mixing the two is not attempted, since a proxy that sets one passes the other through from the client untouched. The scheme is the last `X-Forwarded-Proto` value, else the last `Forwarded` `proto`. The app is served with its connections' addresses (`into_make_service_with_connect_info`), which `app()` documents; `app()` takes the `TrustedProxies`. The request-id rule is unchanged: a proxy's id is kept when it is plain, as anyone's is (Caddy's `{http.request.uuid}` is), so the docs show `header_up X-Request-ID` rather than adding a second rule for trusted peers.
- **SV33, one table and a trigger.** The log is one `audit` table (`0011_audit.sql`, after `0008_feeds.sql`, `0009_samples.sql` and `0010_installs.sql`; none rebuilds `commands` (SV21's only adds columns), so the trigger stands): an account change stores its typed `AuditAction` as JSON, and every journal row adds a row pointing at it through an `AFTER INSERT` trigger on `commands` (with `ON DELETE CASCADE`, so an unsent write that the journal drops leaves the log too), and existing journal rows are backfilled. So the log has one order and one cursor, a command entry reads its state and outcome from the journal as they stand, and no journal write can miss its entry. Account changes are recorded after they are made, outside their transaction: a recording failure is logged and the request still succeeds, rather than telling the caller a change failed that was made. A failed login is recorded only when its name is an account's (as that account's entry, with the client's address), so failures add at most 5 rows a minute per account and a flood of invented names writes nothing. That write is the one difference left between a wrong password and an unknown name (well under a millisecond beside the argon2 hash every failure costs, at 5 tries a minute per name), so it is made before the answer rather than in a detached task a reader could race. Owner-data writes and adoptions are not recorded yet: their service methods take no caller, and threading one through every owner-data route and test was not cheap. `delete_user`, `update_household` and `revoke_token` now take the `Caller`, and `reset_owner` takes `now` and records the reset as the host's (no user). A disabled-account login is `login_failed` with reason `disabled`.
- **SV32 review, eviction (changes the spec's plain LRU).** A least-recently-used map let a flood of about 10,000 fresh keys between a target's attempts push the target's bucket out and buy it five more guesses. The map now drops only a bucket that is full again (it holds nothing an attempt could miss), kept in order of that time so one is found at once; while every bucket still holds state, an attempt that needs a new bucket is refused `429` until the first refills (at most a minute: fail closed). A flood can therefore delay other clients' logins by up to a minute, never free the name under attack. Sessions and tokens are untouched either way.
- **SV32 review, forwarded headers.** The address header is chosen by presence (`X-Forwarded-For` whenever it is sent, else `Forwarded`), never by whether anything parsed, and each entry is split on the raw bytes and parsed alone: before, one non-text byte in a forwarded line made the whole line unreadable, the header read as absent, and a client's own `Forwarded` was believed behind nginx's `$proxy_add_x_forwarded_for`. The proxy must set `X-Forwarded-For`. An IPv4-mapped range (`::ffff:10.0.0.0/104`) is stored as its IPv4 range. `reset-owner` logs an audit-write failure and still prints the password it set.
- **SV13, the collector and what it keeps.** The mirror reads traces and statistics in a collector task beside each feeder task, on the long lane through the same `Operation` the other long work uses, one trace or one statistics round per turn. It looks for untraced feeds among the session epoch's 16 highest-numbered only (the feeder's ring keeps 8–12), so a feeder adopted with a long history is not asked for traces it cannot have; a feeder's refusal is stored as the feed's record, so no feed is asked twice. Statistics keep the latest read of each section (JSON of the model's `Stats`) rather than a history, and every food read as a typed row for SV41 and SV70; besides the connect's and the hourly rounds, the food section alone is read after each `Fed` event, ahead of its trace, so an emptied or refilled hopper shows one feed late at most; a history of the other sections can come with FP22 if its page wants one. The trace body is kept in the feeder's encoding (`Pages::take_raw`, added to `wellfed-client`) and decoded on read. `Diagnostics::Read { stats_every }` (hourly) is the server's default; the test kit, the lanes' tests and every other test run `Diagnostics::Off`, so the collector's steps and ids never mix into what they assert, and the diagnostics' own tests turn it on. The test kit takes `wellfed-proto` (a new arrow, and a new `deny.toml` wrapper of it) to put a trace in the simulator's ring, since the simulator records none of its own.
- **SV14, a session of the log's own, owners only.** The feeder has no op that ends a tail, so tailing on the feeder task's session would run for that whole session; the log gets a second session with the same key, opened by the first follower and closed within a second of the last leaving, when the feeder's task stops or when the feeder drops it, and the stream then ends. The feeder serves four sessions at once (`SESSIONS`), so a followed log costs one: with the CLI and a phone connected beside the server, the feeder is full. The server's own session goes first: when the feeder task's reconnect is refused `Full` while a tail runs, the task ends the tail (its followers' streams end) and connects at its next try. The tail's task owns the only strong sender of its lines and the feeder's handle a weak one, so a tail that ends for any reason ends every follower's stream, and a later follower starts a new tail; a first follower holds only that feeder's lock while the tail's session opens. A dedicated SSE route (`GET /feeders/{id}/log`) rather than the hub's stream, since nothing of it is stored or replayed. The permission is `FeederAdmin` (the owner's feeder-level row), not a new one. The feeder serves the log only to an owner's key, so a server enrolled as `server` gets `409 feeder_refused` `forbidden`. `TailLog` is not a remembered write, so a tail takes none of the 32 ids the feeder keeps for the server's key (static analysis: `wellfed-device-api` `server/request.rs` `Action::writes`).
- **SV62, the build.** The release binaries and the image come from one `Containerfile` (`src/server/wellfed-server/packaging/`): a `rust:1.99.1-alpine3.24` stage on the build platform links both musl targets with zig (`cargo zigbuild`, Alpine's packages), so the aarch64 binary and the arm64 image need no emulation, and the image is `FROM scratch` (the binary, CA certificates, `/tmp`; uid 65532, data in `/data`). `make server-dist` and `make server-image` run it under docker or podman; neither is in `make check`. rustls with aws-lc and the bundled SQLite built for both targets with no changes (October 27).
- **SV62, the release check is a test.** It is `wellfed-server`'s `tests/release.rs` rather than an xtask command, so it reuses the test kit's in-process simulator, invites and typed client, and `make check` runs it against the debug binary. `WELLFED_RELEASE_SERVER` points it at a release binary; the image's run is an ignored test (`WELLFED_RELEASE_IMAGE`, host networking), which `make check-server-release` runs with both. It stops the server with `kill -TERM`, since the workspace has no signal crate.
- **SV62, addresses under `--no-discovery`.** Adoption and reconnection by address already worked with discovery off (the mirror's `Discovery::Off`); the release check and the docs now cover them. The address is an IP address or `IP:port`: `wellfed_connect::parse_address` resolves no DNS name, and `AdoptFeeder::address`'s doc (and `openapi.json`) now says so rather than `host`. Nothing changes a stored address, so a feeder that moves stays offline under `--no-discovery` until it is back; the docs ask for a DHCP reservation. A route to change a feeder's address (and DNS names) would close that, if the owner wants it.
- **SV24, routes.** Clients: `GET /feeders/{id}/clients` (each with its `owner`: the server, a phone with its user and token, kept, or unowned), `DELETE /feeders/{id}/clients/{key}` through the journal (the server's own key is `400 invalid`: removing the feeder revokes it; a client the feeder no longer holds counts as revoked) and `POST /feeders/{id}/clients/{key}/keep` (nothing sent). Phones: `POST /feeders/{id}/invites` (`201`, the invite text shown once and never journalled) and `GET /phones`. Admin: `PUT /feeders/{id}/wifi` with `If-Match` on the status's `wifi_generation`, `POST /feeders/{id}/reboot`, `POST /feeders/{id}/play` and `DELETE /feeders/{id}`. New codes: `feeder_archived` (409), `client_key_taken` (409), `token_required` and `direct_key_refused` (403). Needs: `InviteOwnPhone` (owners and members) and `FeederAdmin` (owners); play is a member's (`Control`), removal an owner's (`Adopt`).
- **SV24, the invite for another client is the caller's own phone's.** The card's "an invite for another client" is an invite only for the calling token's phone, which names the public key it will join with, so the server records whose key it is before the invite exists and attributes it even when the answer is lost, provided the phone joins with the key it named: the feeder does not bind an invite to a key ([open question](#open-questions)). Only a token (not a browser session) gets one, of an owner or member whose account and token have no expiry (`403 token_required`, `403 direct_key_refused`); the key must be new to the feeder and to the server or already that token's (`409 client_key_taken`). One key per token: a new invite revokes the token's other key on that feeder (reason `replaced`). A member's phone joins as a member, an owner's as an owner.
- **SV24, revocation without the journal.** A phone key's revoke is idempotent, so each attempt takes a fresh request id and the `phone_keys` row is the record: its reason, since when, and its last attempt (`offline`, `unknown`, `invite_live`, or the feeder's refusal). Deleting, demoting or giving an expiry to an account, revoking a token, or a token's new invite marks its keys and revokes them at once on online feeders; each feeder's reconnect, each client joining it (an `Enrolled` event) and each gap in its history revokes what it still owes. The feeder has no way to cancel an unredeemed invite and does not bind one to a key, so `not_found` settles a revoke only once the key's invite can no longer be redeemed: the row keeps `invite_until_ms` (the deadline the feeder answered, plus 60 s for the feeder counting from when it made the invite and for clock drift between the two, or 65,535 s, the longest an answer can state, while the answer is unknown; the answer moves the deadline only from the bound this request recorded, so a concurrent request for the same key never has its bound lowered), and before then the attempt is `invite_live` and the feeder is tried again at that deadline. A key the account lost while its invite was being made gets no invite (`403 direct_key_refused`) and is revoked should it join. A reconcile at start and on each connect marks any key whose account or token is deleted, is a viewer's, is an owner's key on a member's account, or has an expiry, so a key recorded while its account changed is still revoked (review finding). The keys' user and token columns have no foreign key, so a deleted account's keys stay listed (to an owner) until revoked. The account hooks are two calls in `users.rs` and one in `tokens.rs`.
- **SV24, the server's own key.** The feeder ends a revoked key's session before its answer goes out (`clients_changed` runs first in the loop's pass), so a removal never hears the answer to revoking the server's own key. It is confirmed instead by the feeder refusing the server's reconnect within an answer's time (`Link::Refused`); otherwise the removal reports the attempt `unknown`. A removal first tries the phone keys still owed a revoke on the feeder (the server's key is the last that can revoke them) and lists those still owed in `phones_owed`; it then archives the feeder (`feeders.archived_ms`) and stops its mirror whatever the revokes came to; its history, samples and journal stay readable, a write to it is `409 feeder_archived`, and adopting the same identity again un-archives it under its id with a new key. Removal and adoption share one lock.
- **SV24, Wi-Fi and the journal.** The passphrase is never stored: the journal hashes a Wi-Fi change's body with the passphrase replaced by its HMAC-SHA256 under a subkey derived from the server's sealing key (`HMAC(key, "wellfed-server wifi v1")`, with `wellfed-session`'s HMAC, which the mirror re-exports since the service may not take `wellfed-session`), so a retry under the same key still matches and an export carries nothing to search for a weak one. A change whose answer was lost is resent under its write id, which the feeder remembers only until it restarts, so a resend after a restart can be recorded `stale` though the change ran; the status's `wifi_generation` says which. `PhoneInvite` and `WifiCredentials` print no secret.
- **SV24, play is unavailable.** The firmware's loop does not step the speaker (only setup mode does: `wellfed-feeder` `feeder/serve.rs`, `play` answers `None`), so `POST /play` is answered `409 feeder_refused` with `unavailable` on the current firmware and the simulator; the route passes the feeder's reason on, as it will `muted`. Static analysis and simulation.
- **SV24, parity.** `wellfed_service::parity` matches every `Op` with no wildcard, giving a route or a `NoRoute` reason (the clock kept by the server, an install's steps, operations at the feeder, diagnostics, calibration). `PutTime` maps to `PATCH /household`, which sets the zone every feeder keeps. The test `every_routed_operation_is_served_by_the_api_document` checks each route against `openapi.json`, from one sample per operation (an exhaustive match in the test keeps the samples complete).
- **SV24, migration file.** `0014_phones.sql`: `feeders.archived_ms`, `phone_keys` and `kept_clients`, per the run's migration rule (`0009`-`0013` were taken). `journal.rs` stayed under the size guard by moving the write id to `journal/id.rs`.
- **SV25, what was left.** SV20 and SV21 already gave the server its half (an unknown write answered `outcome_unknown` and kept under its key, a feed settled from its `Fed` event, readable by key and streamed). SV25 adds the rule to the device API doc and the API design, and an HTTP test of the whole half through a relay that loses the answer (`a_feed_whose_answer_is_lost_is_unknown_never_resent_and_settled_from_its_fed_event`). Its "a write's answer says whether its outcome is known" is the status and code: `202`/`200`/`204` known, `504 outcome_unknown` not.
- **SV42, the store reads and writes the archive's rows.** The archive's row types live in `wellfed-formats` as the spec says, one per table with the database's columns, so `wellfed-store` takes `wellfed-formats` (a new arrow, in the API design's table and `cargo xtask check-repository`) and reads (`Snapshot::rows`) and inserts (`Import::insert`) them with checked queries itself. The alternative, a store row type per table mapped to the format's in the service, was two copies of 23 tables' columns.
- **SV42, what an archive holds.** Every table but `sessions`, `tokens` (each a credential or its hash) and `job_runs` (this server's schedule), and every column but `users.password_hash` and the feeder's sealed key. The projections and their version and the sample marks are exported though they can be rebuilt, so a CSV archive has the feeds and an import needs no rebuild of the same build's rows. Closed sets stay their stored spelling, and the import checks the manifest's counts and hashes, not each value: a hand-made archive with matching hashes can hold a value the server reads back as corrupt.
- **SV42, hashes over the files.** Each table's SHA-256 is over its file's bytes as written; a JSON archive's rows are canonical JSON (`wellfed_formats::canonical`), and the manifest is too. A CSV archive's hashes are over its CSV bytes, and only a JSON archive imports (`422 archive_invalid` for a CSV one).
- **SV42, two passes over one snapshot.** A tar header needs its file's size and the manifest goes first, so the export reads one read transaction twice (count, then write) rather than spooling to disk; the second pass checks it wrote what the first counted. Chunks of 64 KiB through a queue of four bound the memory.
- **SV42, import's auth is setup's.** `POST /import` takes no login: it runs only while no account exists (`409 import_closed` otherwise, for an owner too), checked again inside its transaction on the one writer so a racing setup cannot interleave, and it logs no one in. It has no body limit, since it runs only on a fresh server.
- **SV42, passwords after an import.** Imported accounts get an empty password hash, which no password matches (`bad_credentials`). The host's `wellfed-server reset-owner [--name]` gives an owner a temporary password, and that owner sets the others' through `PATCH /users/{id}`, as for a locked-out household.
- **SV42, feeders after an import.** Each imported feeder is archived as of the import (a zero nonce and an empty sealed key stand in for the key) and adopted again under its id, continuing its history. `archived_ms` is not in the archive: every feeder in one is unadopted, and leaving it out keeps the round trip byte-identical.
- **SV42, the audit log as it was.** The audit table is exported after the journal; importing a journal entry fires the journal's audit trigger, so that row is deleted at once and the archive's own row for it goes in with its number. The import itself writes no audit entry, and neither does an export, so a round trip stays byte-identical; the owner's `reset-owner` after an import is audited as usual.
- **SV42, imported feeders use SV24's archive.** Import sets SV24's `feeders.archived_ms` on every feeder it restores, so the start skips them and adoption brings each back under its id, its history continuing.
- **SV42, review: bounds on an import.** An upload that goes `timing.upload_idle` (30 s) without a byte ends the import (`400 invalid`), since it holds the one writer; one that runs past the archive length its manifest declares is refused as it arrives (`422 archive_invalid`); the reader requires both closing zero blocks. Export and import both end on the server's shutdown token, so neither holds up a graceful stop.
- **SV42, review: a cut export is an error.** An export the server's shutdown cuts ends its body with an error item (`ExportError::Stopped`), so hyper aborts the response and the client sees an error, not a clean end; `wellfed server export` also keeps the file only once it ends in the tar's two empty blocks. An import has the idle limit but no overall deadline or minimum rate: it runs only on a fresh server, and a slow but steady upload of a large archive is legitimate.
- **SV42, review: one export at a time.** Exports take one slot, held by the task writing the archive: a second while one runs is `409 export_running` (a new `ErrorCode`), so exports hold at most one reader and one snapshot.
- **SV42, review: logins with no password.** A stored hash that does not parse (an imported account's empty one) is verified against the decoy, so the login costs what an unknown name's does, and fails.
- **SV42, SV24's and SV52's tables.** `phone_keys` and `kept_clients` are exported as they are (public keys, never a secret): a phone keeps its key on the feeder and needs a new token from the imported server, since tokens are not exported. An import revokes nothing on its own; a revocation pending in the archive stays pending, as the phone-key code left it. `installs.target` comes along with each install.
- **SV42, SV13's tables.** `feed_traces`, `feeder_stats` and `food_readings` are exported after the projections. `food_readings` has no key, so it is exported in insert order (`rowid`), which an import keeps.
