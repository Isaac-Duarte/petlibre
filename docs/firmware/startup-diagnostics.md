# Startup, stopped outputs, and indicator diagnostics

Every boot runs the same startup before any firmware code: stopped outputs with readback, the synthetic feeding-core diagnostic, and every indicator verified LOW. The runtime then starts Wi-Fi, the transport and the firmware's tasks; probes open the board's sensors and ADC only in the firmwares that run them, and nothing opens the feeding owner. An unopened feeding backend does **not** mean that startup has no electrical side effects.

Much of this page is the bring-up record of FW02–FW15: each probe's records, startup policy and bench result, kept because `wellfed-audit startup` still checks those policies.

## Build-bound startup reports

The SDK wrapper hashes canonical JSON containing the profile and complete root-relative source-input hash map. This becomes `startup_identity` in the manifest and `WELLFED_BUILD_ID` in the firmware. It excludes timestamps; the final OTA hash remains a separate artifact identity. Target compilation of the port requires a lowercase 64-digit ID; host tests use `host`.

```text
PLFW1 start build=<64 lowercase hex digits> bank=1 reset=00000000 mmu=00000003,0c000000,03e7a000
PLFW1 result diagnostic=pass backend=unopened
```

Live RSIP mapping entry 0 identifies bank 0 or 1 when virtual `0x0c000000` maps to `0x08006000` or `0x08186000`; other mappings report unknown. Raw mapping and factory-preserved reset flags remain in the report. A zero reset word does not establish a particular physical reset cause.

`wellfed-audit startup` ([src/tools/wellfed-audit](../../src/tools/wellfed-audit), a port of the former `audit-firmware-startup.py` with the same outcomes and report fields) verifies the frozen OTA/manifest, embedded identity, finalized receive-only capture hashes, event coverage, actual bank mapping, ordering, and observation interval. Missing/wrong build, faults, incomplete or malformed records, repeated startup, and policy-specific failures are distinct failing outcomes. It emits fixed fields rather than arbitrary device text. Example using your own complete evidence bundles:

```sh
cargo run --locked -p wellfed-audit -- startup \
  --capture private/captures/normal-boot \
  --manifest private/verification/review/build-manifest.json \
  --image private/verification/review/image.bin \
  --minimum-seconds 60 \
  --output private/verification/startup-result.json
```

FW02 passed artifact-bound physical startup verification. This evidence does not establish long-term uptime, persistent boot counters, or a verified physical reset cause.

## Stopped-output startup

The initializer explicitly enables/checks LP GPIO clock/function bits while preserving unrelated controls. With the interrupt mask held/restored, it preloads motor PA13/PA14 HIGH/HIGH and infrared PA15/PB3 LOW/LOW before output direction. It verifies masked values and directions before scheduling diagnostics. Infrared OFF requires LOW output latches as well as LOW pad inputs, because a pad with a dead input path reads LOW whatever is driven (as PA0–PA7 do on the tested unit). PB3 is also SWD_CLK, so it first clears `REG_SWD_PMUX_EN` bit 0, as stock does before configuring PB3, and stopped readback requires that bit clear. Before FW13 this step was missing: PB3 was never driven, and its LOW readback was the pad's pull-down ([details](optical-inputs.md#pb3-is-swd_clk)). Failure logs an error and does not start the diagnostic task. This requests the stock-derived STOP/off state; physical polarity and startup transients remain acceptance work.

`PLCLK1` records before/after clock/function words. `PLFW1 outputs` reports PA/PB values and directions before the startup banner. Manifest policies must match record formats in the hashed image. An output mismatch cannot be hidden by a synthetic diagnostic PASS.

FW03 has exact GPIO readback, artifact-bound normal boot, and operator-reported no-motion evidence. Independent voltage/infrared-off measurements, repeated measured resets, and transient checks were deferred to FW30 (electrical output verification, required before supervised motion). The inspected CON3 harness carries both motor leads and board power; disconnecting it is not an established way to isolate the motor while retaining board power.

## Bounded indicator probe

The controller preloads indicator latches LOW and selects stock-derived GPIO/no-pull configuration. It changes only PA0, PA2, PA4, and PB22. Every request requires valid indicator directions and stopped-output readback. Requests yield for 10 ms before observing the output latch, input, pad control, and direction state. Timing requests include the settle interval.

**Since October 22 (policy `low-only-v1`, with GPIO routing `read-only-v3`)** startup no longer pulses the indicators. After startup and diagnostic PASS, it verifies every indicator LOW with stopped outputs, prints `PLLED1 begin low_only` and `PLLED1 done low=all`, and starts the role's tasks at once. The FW04 probe had already proved the pins, and it cost every boot about 15 s before Wi-Fi, the transport and the OTA watcher could start. FW23 will give the indicators meaning. The startup audit accepts the new policies, and routing has only the `startup` stage.

Before that (`bounded-probe-v3`, kept for older captures), the sequence waited nominally 3 seconds, then gave each pin two HIGH pulses in PA0/PA2/PA4/PB22 order: HIGH 1 s, LOW 0.5 s, HIGH 1 s, LOW 1 s. All lines were then requested LOW and the task ended. There was no indefinite blinking, feeding request, or autonomous retry.

The 64 extra input samples distinguish a dead input path (0/64) from a marginal threshold (a partial count). They are informational: verification still uses the single input read, so a high count cannot verify a failed step.

PA0, PA2 and PA4 are **output-only** on the tested unit (owner scope decision after the Port A traces below). Their steps report `status=output` when latch, pad control, directions and stopped state agree, and the begin line names them (`PLLED1 begin output_only=PA0,PA2,PA4`). `output` is never `pass`: it does not establish an electrical level, which rests on the operator's visual observation. PB22 keeps full input verification. Policy `bounded-probe-v3` expects exactly this sequence. The auditor's sequence outcome is `pass`, but `led_probe_verified` stays `false` whenever output-only pins are present; `led_input_verified_pins` (`PB22`) and `led_output_only_pins` (`PA0`, `PA2`, `PA4`) state what was read back.

A HIGH input mismatch remains a failed observation while permitting only the already bounded visible interval; a LOW mismatch, changed latch/mux/direction, or lost stopped state aborts. Terminal `finish=input_mismatch low=all` is a failure, never a verified success. Loss of stopped readback requests STOP/off again.

## FW05 supervision probe capture

Policy `fw05-probe-v1` binds `PLTMR1`/`PLWDG1` records in the image; the startup auditor refuses a mismatch either way and still treats a two-boot capture as `repeated_startup`. After the LED probe, a cold boot opens the stopped board and TIM2, logs 13 `PLTMR1 sample` snapshots (SYSTIMER raw, supervision ms, accepted TIM2 interrupts, ready/healthy/stopped), a 2 s busy stall, then arms the watchdog (`PLWDG1 arm`), feeds it for 15 s (`fed`), and withholds progress (`stall_begin`, `stalled`) until one watchdog reset. The following boot repeats startup and the LED probe, then prints only `PLWDG1 skip`.

Motion stays disabled. The probe opens only the board's outputs (motor STOP, emitters OFF); it never configures sensor inputs, reads efuse calibration or touches the LP-domain ADC. No drive or emitter is requested. Before arming, it writes a marker to SDK user backup register 1 and reads it back. Any boot that sees a nonzero marker or boot reason clears the marker and skips the probe, so a reset cannot repeat the watchdog test until power is removed. Whether the marker survives the platform reset, and which boot-reason bits the reset sets, are bench observations. If both were lost, the board would repeat the probe on each boot, roughly every 100 s, until power is removed. The UART loader remains available at power-on. Clock values are nominal: SYSTIMER and TIM2 at 32 768 Hz (SDK: 31 µs ticks) and a watchdog of 4095 × 32 counts at about 33.3 kHz (`WDG_Scalar`), bounded to 2.9–5.3 s by 25–45 kHz limits. The capture measures them.

Per-card auditors (removed October 22, 2026). The FW05, FW06, FW07, FW08, FW13 and FW15 auditors described below closed with their cards and were removed; their reports remain the evidence, and every startup policy they relied on is still checked by `wellfed-audit startup`. The descriptions record what each checked. `audit-firmware-supervision.py` took the same `--capture/--manifest/--image/--output` arguments as the startup auditor. It splits the capture at the second `PLFW1 start`, runs every declared startup policy on both boots, checks ms/irq consistency against SYSTIMER ticks, the stall, the watchdog vendor word and marker, and the 2.5–7 s reset interval, and estimates SYSTIMER and watchdog clock rates from host receive times. Failures have distinct outcomes (`wrong_boot_count`, `boot1_*`/`boot2_*`, `supervision_sequence`, `timer_clock`, `timer_open`, `timer_samples`, `timer_consistency`, `systimer_rate`, `stall_failed`, `watchdog_arm`, `watchdog_feed`, `watchdog_stall`, `watchdog_no_reset`, `reset_timing`, `boot2_skip`). Host timestamps carry USB latency; the estimates are UART timing evidence and do not establish electrical outputs or the physical reset cause.

### FW05 bench result

One physical receive-only capture of a cold boot passed the supervision auditor, and the operator saw the LED sequence twice. Both boots passed every startup policy.

- **SYSTIMER:** about 32 752 Hz against host receive times over 60 s. That is −475 ppm from 32 768 Hz, within the host timestamp uncertainty of roughly ±0.1%. It only moved forward.
- **TIM2:** a 10.015 ms period, against 10.010 ms nominal for 328 ticks.
- **Stall:** a 2 s busy stall (65 536 ticks) kept TIM2 interrupts running, and supervision stayed ready, healthy and stopped.
- **Watchdog:** armed with vendor word `5601001f` and fed for 15 s with 60 checkpoints, without a reset. The loop that stopped making progress latched fault 4 (PROGRESS) and never refreshed again.
- **Reset timing:** the reset followed about 3.0–3.1 s after the last refresh. A `stalled ms=3015` line arrived in the same receive chunk as the next boot's ROM output. That implies an effective watchdog clock near 43 kHz rather than the nominal 33.3 kHz. This is inside the configured 25–45 kHz bounds but close to the upper one, so tighten the clock bounds and counter choice before any production configuration relies on them.
- **Next boot:** reported boot reason `00100000` (`BIT_BOOT_KM4WDG_RESET_HAPPEN`) and the surviving marker, then skipped the probe. Both reset-loop guards worked on this unit.

Not yet exercised on hardware: owner-lease expiry while a task stalls. The probe never ran owner-side processing, so `owner_ready` was never established. Motion-path stop timing belongs to FW19.

## FW06 boot handshake

After `PLLED1 done low=all`, KM4 prints `PLFLS1 hello authority=<16 hex> count=<n>`: its authority session is the boot count in the high word and a fresh low word. KM0 answers READY with its own session, and KM4 binds a flash coordinator only while outputs are stopped, printing `PLFLS1 ready peer=<16 hex> reply=0 phase=1 fault=0 inactive=1` (ACCEPTED, IDLE, no fault). The test build's KM0 republishes a new session about 10 s later to simulate a rebooted peer. KM4 then reports `PLFLS1 peer peer=<16 hex> reply=5 phase=8 fault=7 blocked=1` (FAILED, FAULT, PEER_LOST), with the new session's high word one above the first. After a 30 s watch from READY it prints `PLFLS1 done phase=8 fault=7 blocked=1`. One `PLFLS1 foreign` line may appear after HELLO. Failures print `PLFLS1 error timeout ms=<n>` or `PLFLS1 error clock`. Policy `fw06-hello-v1` is bound to the HELLO record format in the image both ways. It requires the LED probe policy and exactly one fully parsed HELLO, READY, peer and done record, in that order. It checks the session and field values, and the host receive times: READY within 2.5 s of HELLO, the peer change 9–12 s after READY, and done 29–32 s after READY. Outcomes are `flash_handshake_missing`, `flash_handshake_malformed`, `flash_handshake_failed`, `flash_handshake_order` and `flash_handshake_timing`. The session values are reported as fixed hex fields. This is UART protocol evidence: it does not show that any flash write path is safe.

## FW06 park round trip

Policy `fw06-park-v1` is bound both ways to the `PLPRK1 start mode=` record format in the image, and still requires the HELLO record format. Under it the startup auditor checks only the handshake part of each boot: one HELLO and one READY (one `PLFLS1 foreign` allowed), after `PLLED1 done low=all`, with the `fw06-hello-v1` field values and READY within 2.5 s of HELLO. It refuses `PLFLS1 peer` and `PLFLS1 done` records and requires a `PLPRK1 start` record after READY.

After READY, KM4 prints `PLPRK1 start mode=<0|1|2> marker=<hex8> watchdog=<pass|fail>` and four `PLPRK1 batch leases=<n> park_max=<ticks> release_max=<ticks> frozen=<n> alive=<n>` records at 25, 50, 75 and 100 leases. Park and release maxima are 32 768 Hz ticks, bounded by the 40 ms exchange limit (1310). A passing capture is one power-on with exactly three startups:

- **Boot 1** (mode 0) injects `PLPRK1 inject mode=0 lease=101 begin=0 ... ms=0`: KM4 stops acknowledging a park, and the watchdog resets 2–6 s later.
- **Boot 2** (mode 1) injects `inject mode=1 lease=101 begin=1 ... ms=0` and withholds the release. KM0 publishes TIMEOUT (`peer=504b0081`) after its 700 ms park budget, reported as a second inject line with `ms` within 650–760. The watchdog resets 2–6 s after the first inject line.
- **Boot 3** (mode 2) prints `PLPRK1 done leases=100 marker=00000002`, then nothing more from `PLPRK1`/`PLFLS1` for at least 20 s.

Every batch needs frozen equal to leases and alive at least leases − 1. HELLO counts must be 1, 2 and 3, and the KM0 peer session high words must be nonzero and strictly increasing. Failures print `PLPRK1 error lease=... stage=... reply=... phase=... fault=...`, `PLPRK1 error no_reset ms=<n>` or `PLPRK1 skip marker=<hex8>`.

`audit-firmware-park.py` takes the same `--capture/--manifest/--image/--output` arguments as the supervision auditor and requires `fw06-park-v1`. It splits each boot after its last `PLPRK1` line before the next `PLFW1 start` and runs every declared startup policy on each segment. Outcomes are `wrong_boot_count`, `boot1_*`/`boot2_*`/`boot3_*`, `park_sequence`, `park_start`, `park_batches`, `park_inject_ack`, `park_inject_release`, `park_reset_timing`, `park_done`, `park_sessions` and `pass`. It reports reset flags, HELLO counts, session high words, batch values, both reset intervals, the release timeout and the clean tail. This is UART timing evidence: host timestamps carry USB latency, and it does not establish the physical reset cause or that flash access was excluded during parks.

## FW06 mediated flash read

Policy `fw06-read-v1` is bound both ways to the `PLRDS1 start marker=` record format in the image and still requires the HELLO record format; a read image cannot be audited under `fw06-hello-v1` or `fw06-park-v1`, nor the reverse. It is a single-boot policy for the startup auditor: a reset shows up as `repeated_startup`. HELLO and READY are checked as under `fw06-park-v1` (one `PLFLS1 foreign` allowed, READY within 2.5 s of HELLO). No `PLPRK1`, `PLFLS1 peer` or `PLFLS1 done` record may appear.

After READY, KM4 prints `PLRDS1 start marker=<hex8> watchdog=<pass|fail> installed=<0|1>`, four `PLRDS1 batch reads=<n> id=<6 hex> mismatches=<n> park_max=<ticks> release_max=<ticks> frozen=<n> alive=<n>` records at 25, 50, 75 and 100 reads, and `PLRDS1 done reads=<n> leases=<n> phase=<n> fault=<n>`. A pass needs `marker=00000000 watchdog=pass installed=1`, every batch with JEDEC ID `c84017` (the research unit's GigaDevice part), no mismatches, frozen equal to reads, alive at least reads − 1, and park/release maxima in 1–1310 ticks, then `done reads=100 leases=100 phase=1 fault=0`. Done must arrive within 30 s of start, and the capture must continue at least 30 s after done with no further `PLRDS1` or `PLFLS1` output. Failures print `PLRDS1 skip marker=<hex8>` or `PLFLS1 error ...`.

Outcomes are `flash_read_missing`, `flash_read_malformed` (unparsed or repeated `PLRDS1` records, any `PLPRK1`), `flash_read_failed`, `flash_read_order` and `flash_read_timing`; HELLO/READY problems keep the `flash_handshake_*` outcomes. The report adds `flash_read_verified`, `flash_read_id`, `flash_read_reads`, `flash_read_leases`, `flash_read_park_max`, `flash_read_release_max`, `flash_read_frozen`, `flash_read_alive`, `flash_read_seconds` (start to done) and `flash_read_tail_seconds`. This is UART protocol and timing evidence for the mediated read; it does not show that any flash write path is safe.

## FW06 scratch-sector write

Policy `fw06-write-v1` covers one owner-approved 4 KiB scratch sector at flash offset `0x185000`. It is bound both ways to the `PLWRS1 start marker=` record format in the image and still requires the HELLO record format; a write image cannot be audited under `fw06-hello-v1`, `fw06-park-v1` or `fw06-read-v1`, nor the reverse. It is a single-boot policy: a reset shows up as `repeated_startup`. HELLO and READY are checked as under `fw06-read-v1`. No `PLPRK1`, `PLRDS1`, `PLFLS1 peer` or `PLFLS1 done` record may appear.

After READY, KM4 prints `PLWRS1 start marker=<hex8> watchdog=<pass|fail> installed=<0|1>`, `PLWRS1 preimage id=<6 hex> blank=<n>`, three `PLWRS1 cycle n=<n> erase_ticks=<ticks> blank=<n> program_max=<ticks> errors=<n>` records, `PLWRS1 restore erase_ticks=<ticks> blank=<n>` and `PLWRS1 done cycles=<n> leases=<n> phase=<n> fault=<n> park_max=<ticks> release_max=<ticks> frozen=<n>`. Ticks are 32 768 Hz. A pass needs `marker=00000000 watchdog=pass installed=1`, a preimage with JEDEC ID `c84017` and all 1024 sampled words blank, cycles 1, 2 and 3 in order, each with `blank=1024`, `errors=0`, erase in 1–16384 ticks (the 500 ms lease active budget) and program maximum in 1–1638 ticks (50 ms), a restore erase in 1–16384 ticks leaving `blank=1024`, then `done cycles=3 leases=53 phase=1 fault=0 frozen=53` with park/release maxima in 1–1310 ticks. Done must arrive within 60 s of start, and the capture must continue at least 30 s after done with no further `PLWRS1` or `PLFLS1` output. Failures print `PLWRS1 skip marker=<hex8>` or `PLFLS1 error ...`.

Outcomes are `flash_write_missing` (no start, preimage, restore or done), `flash_write_malformed` (unparsed or repeated `PLWRS1` records, any `PLPRK1` or `PLRDS1`), `flash_write_failed` (skip, error or any field outside the bounds, including a non-blank preimage or wrong ID), `flash_write_order` and `flash_write_timing`; HELLO/READY problems keep the `flash_handshake_*` outcomes. The report adds `flash_write_verified`, `flash_write_id`, `flash_write_preimage_blank`, `flash_write_cycles`, `flash_write_restore_erase_ticks`, `flash_write_restore_blank`, `flash_write_leases`, `flash_write_park_max`, `flash_write_release_max`, `flash_write_frozen`, `flash_write_erase_ms_max` (largest cycle or restore erase), `flash_write_seconds` (start to done) and `flash_write_tail_seconds`. This is UART protocol and timing evidence for one scratch sector. It does not show that writes elsewhere, or under power loss, are safe.

## FW15 journal on NOR

Policy `fw15-journal-v1` covers a journal in the owner-approved 64 KiB region `0x340000`–`0x350000` (16 sectors). It is bound both ways to the `PLJNL1 start mode=` record format in the image and still requires the HELLO record format; a journal image cannot be audited under any `fw06-*` policy, nor the reverse. Under it the startup auditor checks only the handshake part of each boot, as under `fw06-park-v1` (one HELLO and one READY, one `PLFLS1 foreign` allowed, READY within 2.5 s of HELLO), and requires a `PLJNL1 start` record after READY. No `PLPRK1`, `PLRDS1`, `PLWRS1`, `PLFLS1 peer` or `PLFLS1 done` record may appear.

After READY, KM4 prints `PLJNL1 start mode=<0|1|2> marker=<hex8> watchdog=<pass|fail> installed=<0|1>`, in mode 0 `PLJNL1 preimage id=<6 hex> blank_sectors=<n>`, then `PLJNL1 op kind=<n> id=<n> ok=<0|1> error=<n> ticks=<n>` records (kind 0 create, 1 reserve, 2 finish, 3 open, 4 torn, 5 wipe), `PLJNL1 view sequence=<n> high_water=<n> pending=<0|1> result=<n> outcome=<n> slot=<n>`, in modes 1 and 2 `PLJNL1 refuse id=<n> reserved=<0|1>`, and `PLJNL1 end mode=<n> reset=<0|1> leases=<n> frozen=<n> erases=<n> phase=<n> fault=<n>`. Ticks are 32 768 Hz. Every boot needs `watchdog=pass installed=1` and its mode as the marker. A passing capture is one power-on with exactly three startups:

- **Boot 1** (mode 0) finds JEDEC ID `c84017` and all 16 sectors blank, then creates the journal, reserves and finishes ids 1 and 2 and reserves id 3. It prints the view `sequence=6 high_water=3 pending=1 result=3 outcome=0 slot=1` and `end mode=0 reset=1 erases=5 phase=1 fault=0`; the watchdog resets 2.0–6.5 s later.
- **Boot 2** (mode 1) opens the journal and prints the same view, refuses id 4 (`reserved=0`), tears the pending record and ends `mode=1 reset=1 erases=1 phase=1 fault=0`; the watchdog resets 2.0–6.5 s later.
- **Boot 3** (mode 2) opens the journal, prints the same view and refusal, wipes the journal and ends `mode=2 reset=0 erases=2 phase=1 fault=0`, then nothing more from `PLJNL1`/`PLFLS1` for at least 30 s.

Every operation needs `ok=1 error=0`. Reserve, finish and wipe need nonzero ticks; reserve and finish are bounded by 26214 ticks (800 ms: one journal write is an erase, two programs and verify reads, each in its own lease). Each end needs nonzero leases with frozen equal to leases. HELLO counts must be 1, 2 and 3, and the KM0 peer session high words must be nonzero and strictly increasing. Failures print `PLJNL1 skip marker=<hex8>` or `PLFLS1 error ...`.

`audit-firmware-journal.py` takes the same `--capture/--manifest/--image/--output` arguments as the park auditor and requires `fw15-journal-v1`. It splits each boot after its last `PLJNL1` line before the next `PLFW1 start`, runs every declared startup policy on each segment, and times each reset from the end line to the next boot's first receive chunk. Outcomes are `wrong_boot_count`, `boot1_*`/`boot2_*`/`boot3_*`, `journal_sequence` (unparsed, repeated or out-of-order `PLJNL1` records, skip or error lines), `journal_start`, `journal_preimage`, `journal_ops`, `journal_view`, `journal_refuse`, `journal_end`, `journal_reset_timing`, `journal_tail`, `journal_sessions` and `pass`. It reports reset flags, HELLO counts, session high words, per-boot operations, views and ends, both reset intervals, `journal_write_ms_max` (largest reserve or finish) and the clean tail. This is UART protocol and timing evidence: host timestamps carry USB latency, and it does not establish NOR data retention or behaviour under power loss.

## FW15 settings power-cut test

Policies `fw15-settings-v1` and `fw15-settings-v2` are bound both ways to the `PLSET1 start marker=` record format in the image and still requires the HELLO record format; a settings image cannot be audited under any other flash policy, nor the reverse. Under it the startup auditor checks only the handshake part of a boot, as under `fw15-journal-v1`, and requires a `PLSET1 start` record after READY. No `PLPRK1`, `PLRDS1`, `PLWRS1`, `PLJNL1`, `PLFLS1 peer` or `PLFLS1 done` record may appear.

After READY, KM4 prints `PLSET1 start marker=<hex8> watchdog=<pass|fail> installed=<0|1>`, `PLSET1 open status=<n> generation=<n> volume=<n> lights=<0|1> slot=<n> consistent=<0|1>` (status 0 LOADED, 1 EMPTY, 2 RECOVERED, 3 CORRUPT, 4 FUTURE, 5 IO, 6 WORN), then saves settings at about 8 per second (back to back under `fw15-settings-v2`, about 35 per second), printing `PLSET1 batch saves=<n> generation=<n> ticks_max=<n>` after every 25 completed saves and, in place of the batch at the 300th (1500th), `PLSET1 end saves=<n> generation=<n> leases=<n> frozen=<n> phase=<n> fault=<n>`. Under `fw15-settings-v2` the open record carries `other=<n>` before `consistent`: the state of the slot not loaded (1 ERASED, 2 VALID, 3 FUTURE, 4 DIRTY, a prefix of our record without its commit, 5 INVALID). Failures print `PLSET1 error save generation=<n> status=<n>`, `PLSET1 skip marker=<hex8>` or `PLFLS1 error ...`.

The capture is one receive-only recording while the operator repeatedly cuts and restores feeder power at moments of their choosing. `audit-firmware-settings.py` takes the same arguments as the journal auditor and requires either settings policy, applying the save count of the one in the manifest. Each later boot begins at the receive chunk that follows the last reception gap of at least 0.5 s before its `PLFW1 start`, so a cut boot's final partial line stays with that boot and is ignored; only complete `PLSET1` lines are parsed. Every `PLFW1 start` must report reset flags `00000000`. A boot cut before its open contributes nothing; every boot that opened is checked as one startup up to its last complete `PLSET1` line. A pass needs:

- at least three opened boots, each with `marker=00000000 watchdog=pass installed=1`, `consistent=1` and status LOADED or RECOVERED (EMPTY with generation 0 only for the first opened boot);
- each later open generation between the previous opened boot's highest reported generation and 25 more (up to 24 saves after its last batch plus one interrupted save);
- batches at 25, 50, ... in order with generation equal to the open generation plus saves and `ticks_max` nonzero and at most 26214 (800 ms); an end needs every batch before it (11 or 59), generation equal to the open generation plus the save count, `phase=1 fault=0` and nonzero leases equal to frozen;
- no error or skip line anywhere, and at least two boots cut after their open, before an end, and followed by another startup;
- under `fw15-settings-v2` only, `other` on every open and agreeing with its status (LOADED: ERASED or VALID; RECOVERED: DIRTY or INVALID; EMPTY: ERASED), and at least one opened boot after the first finding it not VALID: a cut inside a save. Under `fw15-settings-v1` no open may carry `other`.

Outcomes are `settings_sequence` (unparsed, repeated or out-of-order records, foreign stage records, error or skip lines, or no power-off gap before a startup), `wrong_reset`, `boot<N>_*`, `settings_boots`, `settings_open`, `settings_recovery`, `settings_batches`, `settings_end`, `settings_cuts`, `settings_midsave` and `pass`. The report lists per-boot reset flags, opened flags, startup checks, open records, last reported generations and ends, the recovery deltas, the largest `ticks_max` (also in ms), the cut count and, under v2, the mid-save cut count. This is UART evidence: host timestamps carry USB latency, the cut instants are chosen by the operator and not measured, and flash retention beyond the capture is not established.

## FW14 power-input probe

Policies `fw14-adc-v1` and `fw14-adc-v2` are bound both ways to the `PLADC1 open outputs=` record format in the image (v2 also to its ` supply=` field) and require the LED probe policy. After the LED probe completes, KM4 opens the board's outputs (motor STOP, emitters OFF, no flash authority, so every drive is refused) and then its sensors. `PLADC1 clock function_before=<hex8> clock_before=<hex8> function_after=<hex8> clock_after=<hex8> status=<pass|fail>` reports `REG_LP_FUNC_EN1` and `REG_LP_CLK_CTRL1` around the explicit ADC enable (bit 8 in each, clock first, no other bit changed). `PLADC1 open outputs=<0|1> efuse=<hex8|none> offset=<n> gain=<n> default_offset=<0|1> default_gain=<0|1> status=<pass|fail>` gives the efuse bytes 0x1d0..0x1d3 in read order and their decoding (erased halves default to 2480 and 12050, as stock). Then, once a second without end, `PLADC1 sample n=<n> ticks=<n> food=<0|1> outlet=<0|1> dc=<0|1> stopped=<0|1> current=<min,max,mean,scaled> battery=<min,max,mean,scaled>`, with ` supply=<min,max,mean,scaled>` appended under v2, where `ticks` times the whole capture (32 conversions, 48 under v2) against the SYSTIMER. A capture timeout or failed stopped readback prints `PLADC1 error n=<n> ticks=<n> stopped=<0|1>` and ends the probe with the board tripped.

`wellfed-audit adc` (formerly `audit-firmware-adc.py`) takes the usual arguments and requires one passing startup, the clock and open records after `PLLED1 done low=all`, a verified enable, efuse bytes that decode to the reported calibration, and at least 30 samples numbered from 0, about a second apart (mean host spacing 0.8–1.5 s), each with `stopped=1`, `ticks` in 1–3277 (100 ms), `min <= mean <= max <= 4095` and the scaled value equal to the stock formula on the mean. Under v2 every sample must carry the supply channel, and its mean must differ from both external channels' means by at least 1000 raw, evidence that the channel select takes effect. Outcomes are `startup_*`, `adc_sequence`, `adc_clock`, `adc_open`, `adc_samples`, `adc_values`, `adc_channels`, `adc_timing` and `pass`. The report lists the registers, whether startup had already enabled the ADC, the calibration, the levels seen on each GPIO input, and per-channel ranges. The values are observations: voltages, divider ratios, current units and the PA19 polarity need measurements.

So the stock scaling gives millivolts, within about 1%, at least for this channel; the external channels' dividers remain unmeasured. Each 48-conversion capture took at most 15.1 ms.

## FW07 scan probe

Policy `fw07-scan-v1` is bound both ways to the `PLWIF1 start created=` record format and requires the LED probe policy. After the LED probe, KM4 starts the Wi-Fi shim in `example_entry.c`. One task runs `LwIP_Init()` and `wifi_on(RTW_MODE_STA)`, then three scans 5 s apart, each waiting at most 10 s and keeping the 32 strongest networks. The probe polls it and prints `PLWIF1 start created=<0|1>`, `PLWIF1 on result=<n> ms=<n>`, then per scan `PLWIF1 scan n=<n> result=<n> ms=<n> count=<n> dropped=<n> stopped=<0|1>` followed by `PLWIF1 ap n=<n> i=<n> ssid_crc=<hex8> rssi=<dBm> channel=<n> security=<hex8>` for each of up to 32 networks, and `PLWIF1 done scans=3`; a stalled shim prints `PLWIF1 error timeout stage=<n> ms=<n>`. Networks are identified only by a CRC-32 of the SSID, and the build holds no credentials; nothing joins a network. KM0 did not run `wifi_FW_init_ram()` in these builds.

The build overrides `CONFIG_EXAMPLE_WLAN_FAST_CONNECT` to 0, because fast connect saves reconnect data to `FAST_RECONNECT_DATA` (0x105000) inside the application bank. The write-reachability audit (`wellfed-build`'s `audit/writes.rs`) then fails the build if any eFuse or flash writer is linked (`rtw_efuse_boot_write`, `wifi_set_mac_address`, the fast-connect and FTL writers, the mbed flash write API, any shell entry), or if any reference to a ROM or RAM eFuse/flash write entry differs from its pinned set. Those are the RAM `*XIP` wrappers, the unreferenced `FLASH_EreaseDwordsXIP`, the driver's private-command eFuse path (`rtw_private_handler`, then `rtw_ex_set`, then `rtw_config_map_write`), and the vendor shell command table, which no linked code starts. It sees direct and stored-address references only.

`audit-firmware-wifi.py` takes the usual arguments plus an optional private `--ssid-file`. It requires one passing startup, the records after `PLLED1 done low=all`, `wifi_on` success within 30 s, and three successful scans of at most 10 s each, each with stopped outputs and exactly one record per kept network, RSSI in −127–0 dBm and a 2.4 or 5 GHz channel. With `--ssid-file` it reports whether that network's CRC was seen, and at what RSSI, without writing the name. Outcomes are `startup_*`, `wifi_sequence`, `wifi_start`, `wifi_on`, `wifi_timeout`, `wifi_scan`, `wifi_networks` and `pass`. `count` is the networks kept (at most 32) and `dropped` those beyond; the report's network maximum is their sum.

KM4 log lines print with the scheduler suspended when called from a task, so another task's print cannot split them (the SDK driver did, in the first capture); interrupts still run.

### FW07 bench result

Two cold boots on adapter power (physical, UART). In both, `wifi_on(STA)` succeeded in 234–236 ms and all three scans completed in 4.0–4.3 s with stopped outputs, hearing 51–63 networks. The driver printed `FW Enable failed` up to three times per boot. The suspected cause is the skipped KM0 `wifi_FW_init_ram()`, which would leave power-save unavailable; that is unconfirmed. In the first boot, that print split the `PLWIF1 start` line, and the auditor rejected the capture (`wifi_sequence`). The second boot, with scheduler-suspended logging and strongest-32 retention, passed. The owner's configured hotspot was not among the networks kept in either boot; whether it was broadcasting was not recorded.

## FW07 join probe

Policy `fw07-join-v1` is bound both ways to the `PLWIF2 start created=` record format and requires the LED probe policy. The KM4 shim in `example_entry.c` runs `LwIP_Init()` and `wifi_on(RTW_MODE_STA)`, then repeats one attempt: scan for the configured SSID (learning its security and RSSI), `wifi_connect`, then `LwIP_DHCP(0, DHCP_START)`. Any DHCP state other than assigned, including the SDK's static 192.168.1.80 fallback, stops DHCP, releases the address and disconnects. A joined link is polled every 500 ms; when it drops, the shim records the loss, stops DHCP and releases the address. Between attempts it waits 1 s, doubling to 30 s, and resets to 1 s after a join. Nothing resets, writes flash or registers the SDK's own reconnect. Events go to a 16-entry numbered ring that the Rust probe drains, printing `PLWIF2 ev seq=<n> kind=<on|scan|connect|dhcp|lost|backoff> attempt=<n> result=<n> value=<hex8> rssi=<dBm> security=<hex8> ms=<n> stopped=<0|1>`, or `PLWIF2 error overrun seq=<n>`.

The SSID and password come from the ignored `private/hotspot.json`, which `wellfed-build` turns into an ignored generated header in the SDK worktree. Only the file's hash reaches the manifest, and our records never print either value. The SDK driver does print the SSID (`set ssid [...]`), so join captures stay private.

`audit-firmware-wifi-join.py` requires one passing startup, events numbered from 1 with stopped outputs and no overrun, and `wifi_on` success. Each attempt must be scan, then connect only if found, DHCP only if connected, a loss only if assigned, then a backoff; only the last attempt may be cut off by the capture end. It also checks the backoff sequence and that an assigned address is neither 0.0.0.0 nor the static fallback. A pass needs a join, a loss after it, and a rejoin after the first loss. The address stays in the private report.

The vendor makefiles track no header dependencies. Objects compiled before the platform options override still linked `restore_wifi_info_to_flash`, which the link audit caught. The build now records the override digest and deletes every KM4 object when it changes.

### FW07 join bench result

One cold boot on adapter power, with the owner's NetworkManager hotspot (physical, UART plus the host's hotspot journal). Startup passed and `wifi_on` took 234 ms. The first attempt found the network at -21 dBm. SAE authentication, association and the 4-way handshake completed, and the hotspot logged the station connected. But dnsmasq logged no DHCP request from the feeder. `LwIP_DHCP` waited 44.6 s until the operator turned the hotspot off. After it came back, the handshake completed again (after one association reject, status 53, on a cached PMKSA), and DHCP again got nothing. The auditor outcome was `wifi_no_join`. The same hotspot leased addresses to this feeder under stock firmware.

The driver printed `fw cmd fifo full` 98 times, as well as `FW Enable failed`. On AmebaD the WLAN firmware runs on KM0, from `lib_wifi_fw.a` through `wifi_FW_init_ram()`: `TaskInit_8721D` and the IPC command task `TaskFW_IPCMD_8721D`. Our KM0 main never starts it, so the driver's firmware commands are never consumed. The vendor KM0 main starts it when `BKUP_Read(0) & BIT_WIFI_ENABLE`, which `app_start` sets from `ps_config.km0_config_wifi_enable`. Review 01 took no packet capture, so whether its DHCP requests left the feeder is unknown.

Review 02 starts the WLAN firmware on KM0. `wellfed_wifi_fw_start()` calls `wifi_FW_init_ram()` when `BKUP_Read(0) & BIT_WIFI_ENABLE`, the same gate the vendor main uses, before `km4_boot_on()`; the first-boot main audit (`audit/mains.rs`) pins the new call. It creates three KM0 tasks (about 6 KB of stack from the 20 KB KM0 heap). An FW06 park runs with interrupts masked, so none of the firmware's code runs while KM4 holds a flash lease, though the WLAN firmware then stalls for up to the park budget. The write audit now covers KM0 too. `lib_wifi_fw.a` imports no flash, eFuse or shell symbol, every KM0 reference to a flash or eFuse write entry is pinned (the SDK's boot-time flash setup and the shell table), and nothing references the ROM shell entries. The firmware's ROM half is not covered.

With review 02, `FW Enable failed` and `fw cmd fifo full` no longer appear, and the feeder's DHCP DISCOVERs reached the hotspot interface: a host packet capture showed them well formed, with valid checksums. dnsmasq still answered nothing, because the bench host's own nftables input policy dropped all inbound traffic on the hotspot interface. A host firewall is part of the bench setup to check before blaming the firmware.

After the owner allowed DHCP from the hotspot interface, one cold boot passed `fw07-join-v1` (physical, UART plus the dnsmasq journal). `wifi_on` took 149 ms. The first association was rejected with status 30 (try again later), because the access point still held the previous boot's protected association. One 1 s backoff later, attempt 2 joined 24.3 s after radio on: connect took 5.9 s, and DHCP took 3.8 s with a dnsmasq-acknowledged lease. The operator outage was seen as a loss after 30.5 s connected. Backoffs ran 1, 2, 4 and 8 s, and the feeder rejoined 41.7 s after the loss, renewing the same lease in 39 ms. The password never appears in the UART output; the driver prints the SSID. DNS and traffic beyond the hotspot are untested, and the bench host's firewall still blocks them.

## FW07 DNS probe

Superseded on October 25 by the [gateway watch](#link-liveness-without-internet-dns): a feeder without a route to the internet churned rejoins under it. Kept as the record of what ran.

Policy `fw07-dns-v1` is bound both ways to the `PLWIF3 start created=` record format and requires the LED probe policy. The shim joins as under `fw07-join-v1`. Once it holds a lease, it sends its own A query for `example.com` to the DHCP-provided DNS server (`dns_getserver(0)`) every 5 s, over a UDP socket with a 3 s timeout. It doesn't use lwIP's resolver, whose cache answered the first build's lookups without any network traffic. A lookup succeeds on a response with the query's ID, no truncation, rcode 0 and an A record. Failures are -1 (no server), -2 (socket), -3 (send), -4 (timeout), -5 (mismatch or truncation), -6 (rcode) and -7 (no address). Two consecutive failures are a DNS loss (`lost` with result 1): the shim stops DHCP, releases the address, disconnects and rejoins. A link drop is a loss with result 0, as before. The backoff resets only after a successful lookup, so a network that leases addresses but has no working DNS backs off to 30 s. Records are the `PLWIF2` set under the `PLWIF3` prefix, plus `kind=dns`.

`audit-firmware-wifi-join.py` handles both policies. Under `fw07-dns-v1` a joined attempt is DHCP, lookups, then a loss. A DNS loss must follow exactly two trailing failed lookups. A link loss, or an attempt still joined at the capture end, may not have two. A pass needs a successful lookup, a DNS loss after it, and a successful lookup after that loss. The operator blocks DNS at the access point and then unblocks it; the report gives the loss and recovery times.

### FW07 DNS bench result

Three cold boots on adapter power, with the owner's hotspot (physical, UART plus the bench host's `sudo` journal for block and unblock times).

- The first build, using lwIP's resolver, passed every lookup through a 51 s DNS block, each in 0 ms from its cache.
- With the explicit query, a boot with no block made 27 lookups in 1–63 ms. One spontaneous 3 s timeout was absorbed, because the next lookup succeeded.
- The passing boot joined 21.5 s after radio on (the first association was rejected, as before), and three lookups succeeded. The operator blocked DNS on the host. Two timeouts later, 11 s after the block, the feeder declared a DNS loss and rejoined. Each rejoin got a lease and then failed DNS twice, with backoffs of 1, 2 and 4 s. The operator unblocked DNS 50 s after blocking it. The next attempt resolved 10 s later, 48.4 s after the first DNS loss, and the backoff reset; 14 more lookups succeeded. Nothing reset, and the password never appears in the UART output.

DHCP-server loss and lease expiry are not exercised; the lease is 1 h. Traffic beyond the access point is still blocked by the bench host's firewall.

### FW07 runtime flash check

A full 8 MiB flash read in loader mode, one boot of this build, then a second full read (physical, UART loader reads). The boot ran for 3 minutes with a hotspot outage (24 s) and a DNS block (41 s), and passed `fw07-dns-v1`. The outage surfaced as a DNS-cause loss before the driver's beacon-loss detection, and backoffs ran 1, 2, 4 and 8 s, then 1 and 2 s. The two reads were byte-identical, so nothing wrote to flash during that boot by any path, whether hooked, ROM or indirect. This covers one boot of a few minutes, not long-running operation or other Wi-Fi events such as lease renewal.

## Link liveness without internet DNS

The feeder is a local device, so a joined link is judged only by what the LAN shows: the association, the DHCP lease and the gateway that lease named. Nothing in the firmware looks up a name: the shim's lookup is gone and it calls no resolver. lwIP's resolver is still linked (the vendor `ping` console command reaches `lwip_gethostbyname`, `netconn_gethostbyname` and `dns_gethostbyname_addrtype`) and takes the DHCP server's address, but it sends only when asked, and no firmware path asks. Policy `wifi-gateway-v1` (static analysis and host tests, October 25; not yet run on hardware).

- **Who decides.** The C task samples the link every 500 ms and calls `wellfed_wifi_watch(associated, leased, probe)` (`wellfed_hal::link`), the one export this added; its answer is `wellfed_core::liveness::Verdict::code`: hold, probe now, settled, or leave with a cause. The machine (`Liveness`) is pure and host-tested (`wellfed-core/tests/liveness.rs`); `wellfed_wifi_outcome` starts a fresh one after every successful join. The C task is outside the stack audit, as the select and outcome already were.
- **Association** (`wifi_is_connected_to_ap`) lost: leave at once, cause 0, as before.
- **Lease** (`dhcp_supplied_address` and a nonzero address): lwIP renews and rebinds by itself and gives the address up only when the whole lease ran out unanswered; then leave at once, cause 2.
- **Gateway.** One ICMP echo to the lease's gateway every 5 s, over a raw socket (`LWIP_RAW` is on in the SDK's options) with a 1 s timeout; the reply is matched by source, type, identifier and sequence. Once the gateway has answered this join, three unanswered probes in a row (11–16 s of silence) are a loss, cause 3: the association looks up but nothing gets through, which the driver's beacon-loss detection misses. A gateway that has never answered this join is taken to refuse echo, since DHCP has just worked over the same link, and the link rests on association and lease alone. ARP was the other candidate, since no router can refuse it; it was not used because lwIP 2.0.2 here runs without core locking, so a request must be posted to the stack's thread, and its table offers no way to tell a fresh reply from a cached entry.
- **Settled** once per join, on the gateway's first answer or after three probes without one: the shim resets its rejoin backoff then, so a network that drops the feeder right after DHCP backs off to 30 s instead of rejoining every second.
- **Live** (`net_status::Status::live`, written only by the watch): settled, and, once the gateway has answered, its latest probe answered too. Trial confirmation waits for it. A leave clears it before the loss event is drained.
- **Records.** `kind=gateway` events: `result` 0 answered, `-1` no gateway in the lease, `-2` socket, `-3` send, `-4` timeout (only a timeout is silence: a probe that could not be sent, as when the device API's sessions and mDNS hold every connection, is no observation); `value` the gateway, `ms` the round trip. `kind=lost` with `result` 0, 2 or 3. The device API's `dns_losses` and the health record's `"dns"` keep their names on the wire and now count causes 2 and 3.
- **Restart** (cause 4): see [below](#leaving-before-a-restart); it ends the task's joins rather than starting a backoff.
- **On the bench hotspot** (static analysis): the hotspot has no forwarding, and the old check passed there only because the hotspot answers DNS locally. The watch never asks beyond the gateway, so the feeder stays joined. The host's firewall accepts ICMP on every interface, so expect `kind=gateway result=0` every 5 s: the gateway arms on the first probe and the join settles at once; a hotspot outage then shows as an association or gateway loss. A bench run with forwarding blocked is still to come.

### Leaving before a restart

Static analysis and host tests, October 25; not yet run on hardware. Every intentional restart (an activation, a give-way, `request_reset` for a reboot the API or setup asked for, or a trial variant's hang) is a watchdog reset with nothing sent to the access point first, so it still holds the old boot's PMF-protected association. The next boot's WPA3 SAE authentication succeeds and the association is rejected with status 30. After that reject the vendor's `wifi_connect` sometimes never returns and the whole KM4 stalls into a silent reset 4 s later (physical: 24 of 441 status-30 rejects on our builds, 17 of 35 on the October 25 evening builds, 8 of 8 on stock; status 53 never did). A trial boot right after an OTA restart nearly always meets status 30, so this could spend a good build's three trial boots.

- **Order.** The runtime's `restart()` first calls `wellfed_hal::supervision::stopping()`, which sets `wellfed_hal::link`'s restart flag and marks the breadcrumb, then stops the watchdog feeder as before. The feeding never waits for the leave: if the disconnect hangs or the task is busy, the reset comes when it always did.
- **Supervision stops too, once certain.** A stop `supervise::feed` decides (a trial's 10-minute deadline, a hung task) is no latch: feeding resumes if it turns true within the watchdog's 1 s progress gap, so a sub-second false costs nothing and must not take the network down. `supervision::supervised` calls `stopping()` only once the stop has lasted the whole gap, when the next checkpoint is refused anyway and the reset is certain; a refused checkpoint calls it at once. An unconfirmed trial boot then leaves, and its next trial boot does not meet status 30.
- **Time left for a supervision stop's leave.** The decision comes on the feeder pass 1 s after the stop began, about 1.25 s after the last refresh (passes are 250 ms apart). That leaves about 2.75 s at the measured 4.0 s expiry, but only about 1.2 s at the clock's 54 kHz bound (2.43 s shortest). A leave takes a 50 ms wake plus the disconnect, up to about 2 s with a gateway echo in flight, so it fits the measured expiry and may not fit the bound: there the disconnect is best effort.
- **The Wi-Fi task.** The shim checks `wellfed_wifi_restarting()` every 50 ms of its watch wait, and the next `wellfed_wifi_watch` answers leave with cause 4 (`Cause::Restart`) whatever the link shows. The task then stops DHCP, calls `wifi_disconnect()` from its own context (the driver queues a protected deauthentication), waits up to 1 s for `wifi_is_connected_to_ap` to report the association gone, logs `kind=leave`, and parks. Between attempts, and after a join's turn waited, it joins no more. Inside an attempt it checks twice more: after the scan (up to 10 s), so a restart asked for meanwhile never calls `wifi_connect`; and right after a successful `wifi_connect`, so an association made while the restart was asked for is left at once (the same disconnect, bounded wait and `kind=leave` event) and DHCP never runs. From the request to the end of the wait is at most about 2 s (a gateway echo in flight, 1 s, then the 1 s wait), inside the watchdog's shortest expiry less a feed period: 2.18 s at the clock's 54 kHz bound (`config::WATCHDOG`), about 3.75 s at the measured 4.0 s expiry.
- **Not covered.** A restart while `wifi_connect` or `LwIP_DHCP` runs waits for that call to return; if the reset comes first, the association it was making may outlive the boot.
- **Callers.** Every reboot the device API or setup asks for already waits for its reply to go out (`reboot_at`, `Setup::reboot_due`), and the update stage waits for its answer (`LEAVE_MS`), so disconnecting at the request loses no answer.

## Silent watchdog resets

Static analysis and host tests, October 25; not yet run on hardware. A hang that stops the watchdog feeder task itself prints nothing: no `PLSUP1 stop`, just the ROM banner about 4 s later and `reset=00100000`. The status-30 hang above was one. So the FreeRTOS tick hook (the builder sets `configUSE_TICK_HOOK`; `vApplicationTickHook` in the shim calls `wellfed_tick_hook`, `wellfed_hal::supervision::crumb`) leaves a breadcrumb every tick in backup register 2, which survives the reset, and the next boot prints it before anything else runs, once:

```text
PLSUP1 hang kind=spin task=wellfed-wif since_ms=3968 suspended=0
```

- **`task`:** the task the last tick interrupted, as its first three characters in lower case, or the three after the shared `wellfed-` (or `wellfed_`) prefix: `wellfed-svc` the service task, `wellfed-wdg` the watchdog feeder, `wellfed-loo` the feeder's loop, `wellfed-wif` the Wi-Fi task, `wellfed` the diagnostic task, `tmr` the timer service, `idl` idle, `cmd` and `rtw` the Wi-Fi driver's threads, `none` none yet. The vendor's `configMAX_TASK_NAME_LEN` of 10 cut every runtime task's name to `wellfed-`, so the first hardware crumbs all read `task=wellfed-`; the builder raises it to 16 (October 26).
- **`since_ms`:** how long since the watchdog feeder task last ran, in 128 ms steps (8064 means that long or longer). The feeder runs every 250 ms.
- **`kind`:** `spin` when `since_ms` is 2048 or more: the tick kept running without the feeder, so a task kept the CPU (`suspended=1`: with the scheduler suspended), and `task` names it. `masked` when it is less: the tick stopped while the feeder was still running, so interrupts were masked (or the tick itself stopped), and `task` names the task that was running then. `stopped` when the feeder had stopped feeding on purpose (it printed `PLSUP1 stop` then, or was restarting); the line says what ran until the reset. A `spin` naming `idl` (idle) means the CPU was free: the feeder task was blocked rather than starved, so look for what it waits on, not for a busy task.
- **Only after a KM4 watchdog reset** (`BOOT_KM4_WATCHDOG`): any other boot clears the register silently. A cold boot finds it zero.
- **Register 2.** The SDK leaves registers 1–5 to the application, and the others are taken (1 the flash attempt and update bits with the lease fault, 3 and 4 the two cores' boot counts, 4 also the trial, 5 KM0's heartbeat). Register 2 held KM0's park-handler diagnostics, which nothing ever read; KM0 no longer writes it. The word is a 3-bit tag, the name in 6-bit characters, the two flags, `since` and a 2-bit check, so a stray value is rarely taken for a crumb.
- **Tickless idle.** The SDK runs with `configUSE_TICKLESS_IDLE` 1: while every task sleeps, the idle task stops the tick and FreeRTOS steps the count afterwards without calling the hook, so suppressed ticks are not counted and `since_ms` can read short when the system was mostly idle. A spin keeps the CPU busy, so it never suppresses ticks.
- **Cost.** A few loads and one backup-register write per 1 ms tick. No tick runs while a flash lease holds interrupts masked; a hang inside a lease is the lease fault's line.

## FW08 transport records (deleted)

Policy `fw08-transport-v1` is bound both ways to the `PLMQT1 start created=` record format, and requires `fw07-dns-v1`. After the LED probe, KM4 starts a second task beside the Wi-Fi probe; it connects to the local server's broker once DNS works and reports health. The formats, timing and pass criteria are in [the transport design](local-transport.md). `audit-firmware-transport.py --stage b|c` checks a capture against them: grammar and ordering, connect within 15 s of the first good DNS lookup, ready within 10 s of a connect, contiguous publish numbers, period publishes 30 ± 5 s apart, and a publish after each health request. Stage b also needs no close, two period publishes and an answered ping and health request. Stage c needs a close and a reconnect. It does not establish what the server received; that is read from the server's status.

## Shared-pad prerequisite and current physical findings

The minimal KM0 main omitted a stock prerequisite for audio-shared pads used as GPIO. The port restores AMACRO and analog pad enables plus the SDK's calibrated `SOCPS_AudioLDO(ENABLE)` helper before entering the scheduler. It does not initialize audio playback.
Stock and the SDK run this after booting KM4; source after review 06 runs it
before `km4_boot_on()` so the pads are powered before KM4 configures them and
`PLPWR1` completes before KM4 logs. A bench capture of that order showed an
intact `PLPWR1` ahead of KM4 output, with `after_pad=00000301`: the LDO is
powered, but its voltage trim (bits 7:1) is zero. `SOCPS_AudioLDO(ENABLE)`
restores a trim saved only by its disable path, so a cold start gets zero. Stock
KM4 `CODEC_Init` and the SDK's `CODEC_Init` write 0x2A, or 0x68 on a 1.8 V supply.
The port now writes that trim after the enable, and policy `before-km4-v2`
requires it. With the trim applied, Port A inputs
still read LOW. A later build sampled raw Port A input after each KM0 supply step
and got the same word every time, with PA0–PA7 already reading 0 before the first
step. The shared-pad supply therefore does not explain the readback. PA13/PA14
and PB22 read back correctly; the low Port A pads appear to have no usable input
readback on the tested unit. `trace-stock-pad-power.py` (removed October 22, 2026; in Git history) executed the stock initializer and LDO instructions against modeled registers/delays; its fixture tests distinguished LDO power from the separate pad-enable bit. This is instruction-level evidence, not an electrical supply measurement.

With that prerequisite restored, the operator observed all four indicators blink twice and finish dark: **PA0 Wi-Fi, PA2 low food, PA4 locked, PB22 warning**. The sequence establishes HIGH-on/LOW-off on the tested unit; only the warning's red color is recorded.

Review 06's earlier capture (HIGH latch with LOW Port A input, two intentional operator boots, interleaved KM0/KM4 reports) keeps its failing verdicts; do not reconstruct a clean stream or relabel them. The output-only build later passed the auditor on a single boot: intact `PLPWR1` before KM4 output with trim 0x2A, PA0/PA2/PA4 `status=output`, PB22 `pass`, terminal LOW. **FW04 is Done within this output-only scope** (physical capture plus operator observation); see the [feature board](../../FIRMWARE_BOARD.md).

### FW06 bench results

These are physical results on the research unit; they concern UART-visible protocol and timing, with nothing written to flash.

- **Boot handshake (`fw06-hello-v1`).** Passed on one cold boot. KM0 answered within one receive chunk. A deliberately changed KM0 session latched PEER_LOST 10.0 s later, with outputs blocked.
- **Park round trip (`fw06-park-v1`).** One power-on produced three boots, as designed:
  1. The withheld ACK reset 3.91 s later.
  2. After the withheld RELEASE, KM0 published TIMEOUT at 705 ms, and the platform reset.
  3. A clean run followed.

  All 300 leases showed a frozen KM0 heartbeat while parked and an advancing one between leases. The worst park took 6 SYSTIMER ticks; release took 2.
- **KM4 SysTick CLKSOURCE.** It reads 1 whatever is written, so park and hook context checks test only ENABLE and TICKINT.
- **Watchdog clock.** The reset came about 4.0–4.2 s after the last rate-limited refresh, an effective clock near 31–33 kHz. FW05 measured about 43 kHz with the same counter. **October 25 (physical):** five resets from the `feeder` runtime's watchdog came 3.97–4.05 s after the logged last refresh (`PLSUP1 stop … fed_ms=`), timed by the host's UART chunks: about 32.8 kHz, the SDK's SDM 32.768 kHz clock, which KM0 calibrates on every boot (static). FW05's figure is most likely its probe's report granularity: it printed `stalled` once a second, so `ms=3015` bounds the reset only between about 3.0 and 4.3 s.
- **Mediated flash read (`fw06-read-v1`).** Passed on one cold boot. With the lease provider installed in the SDK flash-lock hooks, 100 SDK `FLASH_RxCmdXIP` JEDEC reads all returned `c84017`, each inside its own lease, and KM0 was frozen for every one. The worst park took 4 SYSTIMER ticks and the worst release 2; the reads took 2.06 s in total. The coordinator ended idle and unfaulted, and no reset followed. This shows one read-only SDK path working through the hooks. It does not prove exclusive flash ownership for every SDK user.
- **Scratch-sector write (`fw06-write-v1`).** Passed on one cold boot, on the owner-approved scratch sector `0x185000`. The ID read `c84017` and the preimage was fully blank. Three erase, program and verify cycles had zero errors, and a final erase restored the sector to blank. Every one of the 53 leases froze KM0. Erase took 27–35 ms, including the lease; a page program took at most 0.7 ms. This covers the hooked read, sector-erase and page-program paths only. KM0's own SDK flash users and other KM4 users (Wi-Fi, OTA) are not yet mediated.
