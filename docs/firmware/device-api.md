# Device-hosted API (FW47)

Status: physical (October 24, 2026), LAN recovery with the owner at the panel. The feeder serves its own Noise-encrypted API over TCP from the firmware's loop task. Every request, the event history and the live samples go over it, and the normal role no longer opens an MQTT session. The wire contract is in [API design](../api/README.md#device-protocol); this page records how the firmware serves it and what has run on the feeder.

## In the firmware

- **One loop task.** The feeder runs two tasks, the button service and the loop ([task slots](../../src/firmware/wellfed/README.md#what-the-sdk-runtime-guarantees)), and `wellfed-fw-feeder`'s `api` module steps the API inside the loop, after the panel's owner. Every socket call is non-blocking (`wellfed_api_*` in `example_entry.c`): the loop takes what is ready and moves on.
- **Sans-IO server.** `wellfed_feeder::api::Server` holds four session slots. The firmware's driver copies received bytes in and sends what a slot holds; the server never touches a socket, so host tests drive it with `wellfed-client` directly.
- **One handshake operation per pass,** across all slots, and none while the loop holds the outputs for a feed (from its claim to its release). Besides the beat, that keeps an invite's join and a LAN recovery from running during a feed: both end in an enrollment, a store write that would wait for the feed, so the invite is redeemed (and the recovery code taken) only once the key can be written. A handshake held off this way waits; it is not refused, and an invite or recovery window can still expire meanwhile. The hold lasts at most the claim's `FEED_BOUND_MS`, as a join's wait does, so a claim never released cannot keep new sessions out until a reset.
- **Feeds.** `Feed` goes to the feeding owner in the same loop (`feeding::Feeding`) under the next journal id; the answer waits until the owner has reserved it, then names it. When the owner reports the result, the loop logs `PLOWN1 fed …` with what the drive measured, records a `Fed` event and acknowledges the result, so the owner takes the next. One feed at a time: a second is refused `Busy`. A faulted owner refuses `Fault`. A feed is also refused `Busy` while a Wi-Fi join attempt runs (from its scan through association to DHCP) or waits for the outputs: an association holds every task for up to 0.72 s ([scheduling gaps](scheduling-gaps.md#result-october-25-2026-physical)), so feeds and joins take turns (`wellfed_hal::interlock`). Like every refusal it is final for that write id, and nothing moved, so trying again is a new feed the user asks for; the loop logs `PLOWN1 feed portions=… held=…` (1 a join runs, 2 one waits, 3 a storage write ran past the claim's wait). A join that comes while a feed holds the outputs waits in the Wi-Fi task until the owner is at rest with its outputs stopped, and at most `FEED_BOUND_MS` (the owner's own cap on a feed's emitters-on time plus 2 s, about 9 min 40 s for 48 portions); `PLOWN1 interlock …` counts waits and joins forced past that bound. A feed that finds a storage write running (see below) waits for it in the loop, at most `WRITE_WAIT_MS` (3 s: one record's erase and two programs at their whole lease budget, after the writer's 200 ms poll); a write still running, or a client's change still queued for the writer, then refuses it `Busy` (`held=3`). A feed a reset interrupted (power cut, watchdog, fault) is resolved when the owner next opens: the journal records it as uncertain under its own id, the loop records its `Fed` event with outcome `Uncertain`, `completed` 0, reason `Output` (a distinct reason would be a later wire change) and source `Feeder` (the requester is not journaled), and the owner then takes feeds again, from the next id. It is never retried, and its id is never handed out again; a `CancelFeed` for it answers `NotFound`, and its `Fed` event in the history says how it ended. Until that event is recorded, a new feed is refused `Busy`. A power cut at any point of the resolution leaves it to resolve at the next boot, once; only flash corruption of a committed result beside its own reservation (a bit flip that fails the result's checksum) makes the next boot resolve that feed again, so its id can then carry a second, uncertain `Fed` event after its first. A slot reads one frame per pass and writes again only once its last frame is out, so a flooding client costs its own turn.
- **No flash write while the motor may move.** Every flash lease checks that the outputs are stopped, and fails closed when they are not: the lease hook halts and the watchdog resets the board mid-feed. So every store write outside the feed journal (the event ring, settings, the client and key stores, the Wi-Fi store, the seed, the build confirmation and the update stage's records and bank-1 writes) first takes the write turn in `wellfed_hal::interlock`, which it gets only while the loop holds no claim on the outputs. A write that comes during a feed waits: the settings writer leaves it queued and asks again every 200 ms, still answering event reads, and counts itself among the waiting writers, so the next claim lets it go first. It runs once the owner is at rest with its outputs stopped. Only a claim that outlives `FEED_BOUND_MS`, timed from when the writer first saw that same claim (a writer that misses the gap between two feeds starts again on the second), lets a write go ahead with the outputs claimed, counted (`PLOWN1 interlock … writes_forced=`), and only while they read stopped: a write never starts into moving outputs. The update stage never takes that forced path: an update request waits in its mailbox, unanswered, until the outputs are free; an install holds the turn from its first write until it stops, so every feed meanwhile is refused (`held=3`), and a give-way or an activation keeps it until the restart. The confirmation takes the turn before arming the hooks, and the update stage before it sets the attempt marker, so the marker is never left set through a wait. Queued writes complete after the feed in their usual order: the events in the order queued, each mailbox's single change once. The feed journal's own records take no turn: the owner reserves and finishes a feed only after `quiet()` has stopped the outputs, and opens (creating the journal or resolving an interrupted feed) before any feed is claimed. On a trial boot no feed is claimed before the confirmation is written: the owner opens only once the hooks are armed, the confirmation is that boot's first arming (the settings writer starts after it), and it holds the write turn from arming to its write, so a feed cannot push the confirmation towards the trial deadline. `PLOWN1 interlock …` counts `writes_deferred`, `writes_forced`, `write_waited_max_ms` and `feeds_delayed` (claims that waited for a write).
- **A client's store write during a feed is refused `Busy`.** A write would wait for the feed's end, longer than a client waits for its answer (10 s), and a slot waiting on an answer reads no frames, so the client would end the session unsure of the write's fate. So while the outputs are claimed the loop refuses a settings change, a Wi-Fi change and a revocation `Busy` before queueing anything: nothing changed, and the client may send it again after the feed. Reads still answer. An enrollment asks again each pass until the feed ends, as it does when the keys mailbox is taken. A change queued before the claim goes first: the claim also waits, within its `WRITE_WAIT_MS`, while a settings, Wi-Fi or keys change waits in its mailbox, so the writer writes it and the client is answered before the feed starts. A change still in its mailbox at the end of that wait (a stalled writer) refuses the feed `Busy` (`held=3`) instead, so a change is never written after a feed it was queued before. BLE setup's Wi-Fi save, which waits for its own answer, waits out a feed. New sessions are held off during a feed, so the `wellfed` CLI cannot reach this path; the bench's `itest` scenario `feed-writes` (`--feeds`) does, from a session opened before the feed (host-tested against the scripted feeder; not yet run on hardware).
- **Sessions are Noise IK** under the feeder's identity: the client's key travels encrypted in the first message, and the feeder checks it against the enrolled clients the settings writer publishes (`wellfed_hal::keys::publish_clients`). When the table changes, every session whose key is gone closes.
- **Writes are remembered per client key**: the last 32 write ids and their compact outcome, so a retry after a reconnect gets the first answer. A settings or Wi-Fi write names the generation it was based on and is refused `Stale { current }` when the store has moved. The loop is the only requester since the MQTT path went, so the check and the queueing cannot interleave with another writer.
- **Roles.** An owner does everything. A member, or the server, may feed, change settings and the lock, play, sync the clock, list clients and invite members; not Wi-Fi, revocation or reboot. An update-signer key never opens a session.
- **Events.** The loop queues records in `wellfed_hal::events` (16 in RAM, the last kept for a feed's `Fed` event, since appends wait out a feed and its events pile up meanwhile; overflow is counted and recorded as a `Lost` event). The settings writer appends them to the ring in storage sectors 13–24 (`wellfed_feeder::store::events`: 32-byte records, 1,408 kept at least) and answers the API's reads. It polls every 5 ms while either waits; while a feed holds the outputs an append waits at the head of the queue (above). A ring created empty draws a random epoch from the generator and every record repeats it in bytes 4–7, the high half of the old 64-bit sequence field, so a ring written before epochs reads as epoch 0 and the layout is unchanged. The welcome carries the epoch, and the feeder welcomes no session until the writer has opened the ring and published it. Recorded now: boot, lock changes (panel, idle relock, or which client), settings and Wi-Fi writes with their client, clock syncs, invites redeemed, recovery and revocations.
- **Samples** go only to subscribers: power every 5 s, Wi-Fi signal every 30 s. A sample not sent before the next is replaced.
- **mDNS.** `wellfed_core::mdns` answers `_wellfed._tcp` on one UDP socket in the loop: PTR, SRV (port 4747), TXT (`v=1`, `id=` the identity key) and A, for host `wellfed-<first 4 key bytes>.local`. It announces twice on every address change and answers legacy unicast queries. The vendor responder (33.5 KB and its own task) stays unlinked.
- **Updates** (`Capabilities::UPDATE`, owner sessions only): `OfferUpdate`, `UpdateChunk`, `UpdateState`, `CancelUpdate`, `EnrollUpdateKey` and `UpdateKeyStatement`, answered `Outcome::Update` or `Refusal::Update`. The loop never verifies a signature: it copies the request into the update mailbox and answers from what the service task's update stage publishes ([OTA design](ota-design.md#updates-over-the-device-api)). An offer is refused `Busy` while a feed is queued or driven, and a feed while an install holds the flash. A chunk is idempotent by its offset, so it is not a remembered write and is not logged one by one. An update key is enrolled only once someone at the feeder presses Dispense; the session's answer waits for it (the client's answer time is longer for this op), and a session that leaves cancels the offer.
- **Invites and recovery** (from FW45). `CreateInvite` mints a secret, which is the PSK of the new client's XXpsk3 handshake. Its third message carries the label, and the key enrolls through the keys mailbox. The recovery window runs FW45's setup exchange (XX plus the code proof) over the stream, so the owner keys the client's code in before it becomes an owner. A LAN neighbour cannot slip in while the window is open, and the window closes at the first offer. Recovery takes no Wi-Fi.

## Evolution

Major version 1 is frozen: every client lives in this repository, and the event epoch (rule 4) was its last change to existing bytes (October 25, before any outside client). From here on:

1. **The prologue never changes.** `wellfed-api-v1` is bound into every handshake. A new major is negotiated in `Hello.major`, and a feeder that does not serve it answers with the typed `OpenRefusal::Version { supported }`, so a client can say which side to update. A changed prologue would instead fail the handshake with no reason. Enforced: `the_prologue_never_changes` (`wellfed-proto/tests/fixtures.rs`) and `a_major_2_hello_gets_the_typed_version_refusal` (`wellfed-client/tests/api.rs`).
2. **Every new op, event body, outcome or refusal is gated by a `Capabilities` bit both sides claim**, as `FEED` gates feeding and `UPDATE` updates. `Op::capability` and `EventBody::capability` name each variant's bit with no wildcard, so a new variant does not compile without its decision. The feeder serves an op only when the session's hello and the feeder both carry its bit (otherwise `Unavailable`), and pushes an event only when the hello carries its bit (otherwise the session's cursor moves past it). Enforced: `a_v1_only_session_never_receives_a_body_outside_v1` records one event of every body, an exhaustive match keeping the list whole.
3. **Existing messages never gain, lose, reorder or retype a field.** Postcard is positional, so an old peer would misread every byte after a new field. New data is a new variant behind a bit. Enforced: `tests/fixtures/v1.txt` pins every v1 message's bytes, and `WELLFED_BLESS=1` only appends fixtures for new variants; it refuses to rewrite a pinned line.
4. **The event history carries an epoch.** `Welcome::Open.epoch` is drawn at random when the ring is created and kept with it. Event numbers count within an epoch, so a cursor from a re-created ring (a storage wipe, which restarts the numbers at 1) is recognized rather than freezing a mirror that waits for numbers it already has. `wellfed-client`'s `Connection::subscribe` resumes after a cursor only in the feeder's current epoch and otherwise starts from the oldest event kept (`Resume::Restarted`). The server keys events and gaps by (feeder, epoch, seq) and keeps an older epoch's history readable (`?epoch=`). Enforced: `a_cursor_resumes_in_its_epoch_and_restarts_from_another`, the event ring's epoch tests, and the store's `a_new_epoch_keeps_its_own_history_and_restarts_the_cursor`.
5. **Clients adapt to the feeder's capabilities indefinitely.** An owner may hold an update forever, so there is no "N and N−1" window: a client claims every bit it knows (`Capabilities::KNOWN`), runs on the intersection the welcome gives it (`Opened::capabilities`), and keeps speaking every older major it ever spoke. A feeder keeps serving every bit it ever shipped within its major.

## What went away

- **The MQTT offer watch, bank 0's updater and its recovery-role health** (October 25): offers ride the device API, and bank 0 runs the feeder. No build opens an MQTT session; the broker stays for stock.
- **Requests over MQTT.** The firmware's request parser, its reply writers, request signing (`request_auth`) and the health nonce are deleted. The normal role starts no `wellfed-net` task.
- **Confirmation.** FW11 confirmed a trial once the MQTT session was ready. It now confirms on a live link: associated, leased, and its gateway answering (or never having answered this join); no internet is involved ([link liveness](startup-diagnostics.md#link-liveness-without-internet-dns), October 25; until then a DNS lookup of `example.com`). Since offers moved to the API, a build that confirms takes its next offer over the same API.
- **The MQTT transport itself** (October 25): the core's MQTT codec and health writer (`wellfed_core::transport`; the request and reply types the API fills moved to `wellfed_feeder::mailbox`), the HAL's transport task, the broker credentials and request key as a build input (`private/fw-mqtt.json`, which the builder no longer reads), the version 1 manifest and the server's replacement broker role. The speaker firmware's network audio stream went with the request key, its only key and a feature with no client since `wellfed-local speak` was removed. The startup audit still requires no transport policy and no `PLMQT1` start record. A stock-to-replacement install now closes on the bench's device-API check of the new build on bank 0 (`POST /api/ota/trial/answered`), not on its MQTT health.

## Recovery with the owner at the panel (October 24)

- **`fw47-recover-05`, passed:** the owner unlocked the panel and held Lock and Dispense (6.3 s): `pair recovery state=opened`. `wellfed recover` connected, the window closed at its offer (`pair confirming path=recovery`), and the owner keyed the six presses in: `pair recovery state=entered`, `PLCFG1 keys change=enroll result=done enrolled=2`, the session ended `joined`. The new key opened an Owner session and listed both clients; the bench key then revoked it.
- **`fw47-recover-04`, refused as it should be:** only five presses registered (one of two Dispense presses in a row never reached the button service, `dropped=0`), and 60 s after the offer the feeder refused it as `unconfirmed`, enrolling nobody.
- **Earlier tries:** a 4.9 s hold, under the 5 s threshold, opened no window, and the connection was turned away (`ended reason=recovery`), as it is for a closed window.
- **Fixed from these runs:** presses taken by a code are now panel activity, so the panel no longer relocks 30 s after the unlock while the code is keyed in (it did in `fw47-recover-04`, harmlessly). Code presses are logged under their path (`pair recovery keyed=N`); they were all labelled `setup`.

## Host-tested only

- **Recovery:** a wrong code is refused and enrolls nobody; one owner per window (`wellfed-client/tests/api.rs`).
- **The rest of the suite:**

## Left

- **Bank-0 Wi-Fi faults (open, parked).** Bank 0's recovery role sometimes crashes in a Wi-Fi driver thread and then skips the update until a power cycle, as the no-retry rule requires.
  - **Rate** (physical, every capture to October 24): 3 crashes and 1 silent watchdog hang in 157 bank-0 boots that started Wi-Fi; none in 199 bank-1 boots, including the same build.
  - **The crashes:** `cmd_thread` (`fw47-itest-05`), and `rtw_recv` twice (a backpower run, then `warm-20261024-05`). The last, symbolized with its ELF, was in the SDK's `report_survey_event` under `OnProbeRsp`, 11 s after boot, before any download.
  - **Static:** two of the faulting PCs hold valid instructions, so the CPU fetched wrong bytes from flash; a bad jump would fault differently.
  - **Not the cause:** a power cut (one followed a warm give-way); UART back power (relays 3 and 4 isolate it now); the old `qa` image (a fresh build in bank 0 failed too); or our flash leases. Those held IRQs masked for 41–44 ms at most (`masked_max_ms`), none past 100 ms, and the last crash came before any write. The Wi-Fi driver takes no leases (17 per written sector, exactly); both cores hold `PMU_OS`, so nothing sleeps.
  - **Left to test:**
    - the recovery role arms the hooks and binds KM0 before Wi-Fi starts, while the normal role arms later;
    - it starts Wi-Fi at once, without `startup_done`;
    - its traffic is a receive-heavy download;
    - it runs from bank 0's region.

    Each needs a long warm-install loop (about one failure in 40 boots).
  - **Bank 0 now:** `feeder` `262a9f37…` (commit `5755c4f`, with the lease timings), written over UART (`bank0-diag-01`, 229 sectors verified), replacing the stock-installed `qa` `ef76b85e…`.
- **The bring-up firmwares** (`qa`, `optics` and the rest) serve no API and open no MQTT session, so after their install the bench has only the UART confirmation (`wellfed-bench ota` says so).
