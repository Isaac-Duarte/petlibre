# Server board

This board tracks the architecture and build-out of the owner's server (`src/server/`): the crates, their boundaries, and each capability the product needs from them. [FIRMWARE_BOARD.md](FIRMWARE_BOARD.md) tracks the SDK and hardware, and [FEATURE_BOARD.md](FEATURE_BOARD.md) tracks owner-visible behavior. FP18 (server mirror), FP21 (server web UI) and FP22 (device health) stay on the feature board as the acceptance cards; the SV cards here are the engineering that gets them there. The owner's detailed design decisions for the build-out are in [SERVER_SPEC.md](SERVER_SPEC.md). The contracts are in the [API design](docs/api/README.md), the product decisions in [product architecture](docs/firmware/product-architecture.md) and the UI in the [web UI design](docs/web/README.md).

Drafted October 26, 2026, from a read of the four server crates and the docs above (rechecked at `bb244c8`; the server crates were unchanged at `3549cc07`, and the client counts in SV19 are from there), with the owner's decisions from the same day. Every finding here is **static analysis**. No server has met a real feeder yet.

## Using the board

Cards use the FIRMWARE_BOARD workflow (**Planned → Ready → In progress → Done**) and its evidence labels. A card is Ready when its prerequisites are Done. The [foundations](#foundations) come first: every feature card after them adds a module, a table group or a route file, so the code should be shaped for that before the features arrive.

A card never relaxes the feeding-safety rules: every feed goes through the device API, a feed keeps one idempotency key from confirmation to a terminal result, and an uncertain feed is never retried under a new key or over another path. Every path that can request a feed has a test that retries it and proves one feed.

## Run rules (owner, October 26)

- Each card runs the review loop: one implementer agent in its own worktree branched from current `master`, one reviewer agent resumed until it reports nothing blocking (three rounds at most, then the card parks on its branch for the owner). Then the card is rebased on `master`, `cargo fmt --all` and `make check` pass on the result, and it is committed to `master` and pushed.
- One card at a time through the foundations: they edit the same crates, so parallel branches would conflict.
- Cards merge while a firmware run is also merging to `master`: each is rebased on the newest `master` just before its `make check`, and a conflict in `Cargo.toml` or `Cargo.lock` is resolved at that rebase, never by holding the firmware run. The bench has one holder at a time, so SV09 and SV65 wait for it.
- **Sequencing is API first, UI after:** the server API is built across the board, and FP21's screens follow once the cards they need are Done.

### Two paths, one feed

Most owners will run a server, so the app talks to it whenever it is reachable: remote access works, and the audit log names the person. Each owner's or member's phone still keeps its own key on every feeder, and uses it on the LAN when the server is down, for reads and new intents only. The danger is a retry that crosses paths: the server and the phone send different device request ids, so a feed sent directly that timed out, then retried through the server, could feed twice. So an uncertain write never switches path. It is retried on its own path with its own key, or resolved from the feeder's history (a feed by its `Fed` event), never resent on the other.

This costs the server an operation for everything the app does (SV24), and the feeder a client slot per phone (8 slots: the server, the CLI and up to six phones). A phone with an expiring or read-only account holds no key, so the server alone enforces its limits.

## Findings

What the first slice gets right, and where it will not scale as features land.

**Keep:**

- **The layering holds.** `wellfed-server` has no SQL, `wellfed-service` no axum, `wellfed-store` no protocol logic; a handler parses, authorizes, calls one method and maps the result.
- **The feeding-safety core is right.** A command that times out is `outcome_unknown`, never failed (`wellfed-mirror/src/command.rs`, `Command::run`; mapped to `CommandError::Unknown` in `wellfed-service/src/error.rs`). A command whose caller left is dropped unsent. The device request id binds the user, the feeder, the kind of write and the key (`wellfed-service/src/commands.rs`, `write_id`).
- **The mirror is idempotent.** Events are keyed by feeder, epoch and sequence, and the cursor moves in the insert's transaction (`wellfed-store/src/history.rs`, `record_event`).
- **Determinism seams exist:** `Clock` and `Random` are injected, and tests run against the real simulator over TCP.

**Will not scale:**

1. **One `Service` for every domain.** Users, feeders, the per-feeder tasks, the hub and key sealing hang off one struct and one error enum (`wellfed-service/src/lib.rs`). With feeds, plans, pets, foods, intake, releases, installs, audit, alerts, export, retention and rollups to come, it becomes a god object, and every handler's error mapping matches one growing enum. (SV07 moved the per-feeder tasks into `wellfed-mirror` and split the error by domain: `AccountError`, `FeederError`, `CommandError`.)
2. **The store is one 767-line `lib.rs`.** Every table group to come lands in it.
3. **Routes are one file** (`wellfed-server/src/routes.rs`: 8 resources of the design's 25 or so). `If-Match` and `Idempotency-Key` are parsed by helpers, not typed extractors, so each new write repeats them. SV04 fixed both.
4. **Event bodies and sample values are stored only as postcard bytes.** That keeps the mirror raw, but SQL cannot filter, sum or roll them up. Food remaining, intake, charts, anomalies and alerts all need decoded values. (SV10 fixed it for events: typed projections beside the raw rows; samples wait for SV11.)
5. **One command at a time per feeder.** `wellfed_connect::Connection::ask` takes `&mut self` and waits for its answer, and the feeder task runs one command before taking the next. `wellfed-client`'s `Connection` already tracks several pending requests. An install, a trace fetch or stats paging would hold up status reads and feeds. (SV07 fixed the surface: `Mirror::ask` for a short command and `Mirror::operation`, one turn per feeder whose steps take turns with short commands, so a short command waits at most one step; each command still holds the session until its answer, which SV22 changes.) (SV22 pipelines the two lanes: a short command goes out beside a step in flight, the next step waits for the short commands, and each lane keeps one request in flight.)
6. **The server keeps no record of its own writes.** Idempotency rests on the feeder's ring of 32 write ids. The audit log, the UI's uncertain state, the app's [path rule](#two-paths-one-feed) and a retry after the ring has moved all need a server-side record. (SV20 fixed it: the `commands` journal records every write before it is sent, and a retry reads it first.)
7. **No background jobs.** Retention, rollups, session expiry and backups have nowhere to run; session expiry piggybacks on login (`users.rs`, `open_session`). (SV12 fixed it: one supervisor in the binary runs each job on the injected clock, and the expiry job, not login, clears dead sessions.)
8. **Clock leaks.** The hub's epoch and the store's pre-migration backup name read the wall clock directly (`hub.rs`, `Hub::new`; `wellfed-store/src/migrate.rs`, `backup_path`), past the injected `Clock`. (SV03 fixed the store's: `Store::open` takes the time; SV06 the hub's, and a Clippy rule keeps the server crates on the `Clock`.) The feeders' zone is the host's (`main.rs`, `TimeZone::system()`), not a household setting. (SV30 fixed it: the household's zone, stored with it, goes to every feeder as its clock syncs' offsets and its POSIX rule; the host's zone is only offered at setup.)
9. **Dependency pins outside the workspace.** 16 server dependencies are pinned in the crates' own manifests (`axum-extra`, `tower-http`, `tracing`, `sha2`, `argon2`, `tokio-util`, `reqwest` and others), against the API design's rule that shared versions live in `[workspace.dependencies]`.
10. **Tests grow into single files.** `wellfed-service/tests/service.rs` is 721 lines, and each test file builds its own store, clock and simulator. (SV05 fixed both: the test kit builds them, and the tests are a file per domain.)

## Target architecture

Folded into the [API design](docs/api/README.md#crates) (SV01), which is now authoritative, with [SERVER_SPEC.md](SERVER_SPEC.md#crate-layout)'s changes: the hub lives in the service, and the store keeps its single writer connection. A crate per runtime or dependency boundary, a module per domain inside it. A new domain (pets, alerts) is a module and some tables, not a crate, unless it brings its own runtime (tasks), a heavy dependency (`reqwest`) or a consumer outside the server.

```text
src/server/wellfed-api       HTTP bodies, error codes, OpenAPI schemas; a module per resource. Builds for Android
src/server/wellfed-store     SQL only; a module per table group, one Store. Raw rows plus projections
src/server/wellfed-mirror    the per-feeder runtime: connect, sync, ingest and projections, the command lanes, a per-feeder broadcast
src/server/wellfed-releases  fetch, upload and verify releases, the release cache, the install driver
src/server/wellfed-service   the use cases: accounts, household, commands and their journal, pets and food,
                              derived views, alerts, audit, export
src/server/wellfed-server    the binary: config, axum routers per resource, auth, SSE, jobs, the embedded web UI
src/server/wellfed-server-testkit  a temp store, fixed clock and random, the simulator harness, an HTTP client
src/client/wellfed-server-client  a typed Rust client of the HTTP API over wellfed-api: the CLI and the server's own tests
```

Allowed dependencies (each arrow means "may depend on"):

```text
wellfed-server ─► wellfed-service ─┬─► wellfed-mirror ─► wellfed-store ─► wellfed-api ─► wellfed-model
       │                             │          └─► wellfed-connect ─► wellfed-client
       │                             └─► wellfed-releases ─► wellfed-client (Installer), a release verifier
       └─► wellfed-api, wellfed-store (to open it)

wellfed (the CLI) ─► wellfed-server-client ─► wellfed-api
          └─► wellfed-connect (the device API, as today)
```

- **`wellfed-mirror`** owns every task that holds a feeder session. Its surface is small: start and stop a feeder, its link state, `ask` (one answer or unknown), a long-operation lane, and a per-feeder broadcast of typed mirror events. The hub that merges it with command results and alerts is the service's. The service never sees a socket; the mirror never sees a user.
- **`wellfed-store`** stays one crate, so the sqlx offline metadata and the migrations stay in one place, split into `users`, `feeders`, `history`, `samples`, `pets`, `foods` and `refills` (owner data), `commands`, `releases` and `jobs` modules.
- **Derived views** are a service module over the store's projections. They are pure functions of typed rows, with "now" and the household zone passed in, so they are tested without a database.
- **The service's errors split by domain** (`AccountError`, `CommandError`, …), wrapped in its `Error`, as the [Rust standard](docs/development/rust.md) asks of a module with several refusals.
