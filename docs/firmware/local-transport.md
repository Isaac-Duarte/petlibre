# FW08 local health and control transport (design)

Status: Done. Stages A (offline), B and C (bench) passed; the carried items are on the board. Choices marked **decision** are this design's; changes made while building are noted where they apply.

## Goal and non-goals

The replacement firmware reports who it is and how it is doing to the existing local server over Wi-Fi, so the owner no longer needs a UART capture to see build, bank, boot and fault state. The same channel carries a small, fixed set of diagnostic requests.

Non-goals for FW08:
- **No actuation.** Nothing reachable from the transport can dispense, run the motor, change emitters, write settings or flash, or start an update. Feeding requests are FW17 and updates are FW10. Both will need their own review against this channel.
- **No cloud.** The feeder talks only to the server on the isolated hotspot. The bench host's firewall keeps forwarding blocked.
- **No provisioning.** Wi-Fi and transport credentials stay build-time inputs from ignored private files until FW25.
- **No TLS in v1.** See [Authentication and exposure](#authentication-and-exposure).

## Shape

**Decision:** the firmware is an MQTT 3.1.1 client of the server's embedded broker. It opens the connection outbound and listens on no port.

Why this rather than an HTTP server on the feeder:
- The server already runs an authenticated, topic-scoped broker for stock firmware ([local server](../development/local-server.md)). FW08 adds a second, separate role to it instead of a second protocol.
- With no listening socket on the feeder, nothing on the network can make it accept a new connection, and the feeder needs no request router of its own.
- The last will gives the server "went offline" without polling. The broker has retained messages disabled (for the stock role too), so the server keeps the latest health in memory.
- The broker already speaks MQTT 3.1.1; it translates the stock device's legacy 3.1 CONNECT for it.

**Decision:** MQTT encoding and the client state machine live in `petlibre-core` (`no_std`), so they are host-tested against the server's real broker in an integration test. A small C shim in the KM4 port supplies a blocking TCP socket (lwIP sockets, as the FW07 DNS check does). The SDK's Paho `MQTTPacket`/`MQTTClient` stays unused; that keeps first-party protocol code in the Rust workspace, per AGENTS.md.

The client needs only a subset: CONNECT with will, CONNACK, PUBLISH (QoS 0), SUBSCRIBE/SUBACK to one topic, and PINGREQ/PINGRESP. DISCONNECT is encoded but never sent. Incoming PUBLISH is accepted only on the request topic, and only up to a fixed size. Anything else closes the connection.

## Identity, topics and roles

The server is configured for one device. FW08 adds a firmware role beside the existing `device` and `server` roles; it never shares the stock device's credentials or namespace.

| Item | Value |
| --- | --- |
| Client ID | `petlibre-fw-<device_id>` |
| Username | `petlibre-fw` |
| Password | Per device, random 32 bytes, generated by the server and stored only in the private server config and the private firmware credential file |
| Namespace | `petlibre/1/<device_id>/` (the `1` is the topic-layout version) |

| Topic suffix | Publisher | Subscriber | QoS |
| --- | --- | --- | --- |
| `health` | firmware | server | 0 |
| `request` | server | firmware | 0 |
| `reply` | firmware | server | 0 |

Nothing is retained, and wildcard subscriptions in this namespace are refused for every role.

The broker's ACL lets the firmware role publish only `health` and `reply`, and subscribe only to `request`; the server role is the reverse. Neither role can reach the stock `dl/PLAF103/...` topics, and the stock role can't reach these. Stock and replacement firmware never run on the unit at the same time, but the separation holds even if both connected.

The will is a non-retained `health` message with `"online": false`, so the broker reports a lost connection as "offline". The firmware never sends DISCONNECT: each close it makes is a failure, and the server should see it.

## Health message

Compact JSON, one object, at most 512 bytes (576 since FW21 added `clock`), schema `petlibre.health`, version 1. A consumer must ignore unknown fields and refuse an unknown major version. Field values come from data the firmware already has; nothing new is measured.

```json
{"schema":"petlibre.health","v":1,"online":true,"seq":12,"uptime_ms":61234,
 "build":"<startup identity hex64>","bank":1,"reset_flags":"00000000","boot_count":7,
 "outputs":"stopped","faults":[],
 "wifi":{"rssi":-20,"attempt":2,"losses":{"link":0,"dns":1},"last_loss":"dns"},
 "transport":{"connects":1,"last_error":null}}
```

| Field | Source |
| --- | --- |
| `build` | the embedded startup identity, as printed in `PLFW1 start build=` |
| `bank`, `reset_flags` | startup report (FW02) |
| `boot_count` | KM0 backup register 4 (FW06 peer; survives watchdog reset, not power loss) |
| `uptime_ms` | monotonic clock |
| `outputs` | `stopped` only after a fresh stopped-output readback passes; `sensing` when the motor reads back STOP and the emitters are exactly those the [FW13 probe](optical-inputs.md) holds on under supervision; else `unverified` |
| `faults` | latched fault names, for example `watchdog`, `flash_hook`, `stopped_readback`; empty when none |
| `wifi` | the FW07 shim's event counters |
| `transport` | this client's own connect count and last error |

**Decision:** publish on connect, then every 30 s, and immediately when `faults`, `outputs` or a Wi-Fi loss counter changes. The keepalive is 30 s, and the server treats health older than 75 s as stale even if no will arrived.

The UART keeps the same information as `PLMQT1` records, so bench audits work from UART captures as they do today:
- `PLMQT1 start created=<0|1>`
- `PLMQT1 connect n=<n> ok=<0|1> ms=<n>`
- `PLMQT1 ready ms=<n>`
- `PLMQT1 publish seq=<n> bytes=<n> trigger=<connect|period|change|request>`
- `PLMQT1 request op=<health|ping|unsupported|malformed> ok=<0|1>`
- `PLMQT1 closed reason=<name>`
- `PLMQT1 error config`

No record carries the request ID, the broker address or any credential.

The transport connects only while the FW07 shim reports a successful DNS lookup. It closes when the Wi-Fi generation changes (a join or a loss), and waits 1 s after a failure, doubling to 30 s, until a session reaches ready.

## Diagnostic requests

A request is `{"id":"<uuid>","op":"<name>"}`, at most 256 bytes. The reply is `{"id":"<uuid>","op":"<name>","ok":true|false,...}` on `reply`.

v1 allowlist:
- `health`: publish health now, then reply `ok`.
- `ping`: reply `ok` with `uptime_ms`.

- `time` (FW21): set the wall clock; the only request that carries fields and the only one that changes state, so it must be signed (see [Authenticated requests](#authenticated-requests)). See [wall clock](clock.md).

Anything else gets `ok:false`, `error:"unsupported"`, and is logged. Requests carry no arguments in v1. Replays are harmless because both operations are read-only; the ID is only for correlation.

**Decision:** no reboot, no log dump and no settings read in v1. A remote reboot could make a fault hard to see, so it waits for FW11's boot policy. Log streaming needs a size and rate budget.

**Structural no-dispense rule.** The transport's code may depend on the health snapshot and its own socket, nothing else. `cargo xtask check-repository` (crates/tools/xtask, part of `make check`) lists every path that `petlibre-core`'s `transport.rs` and the KM4 `transport.rs` may name. The KM4 driver may name the core transport, the `sdk` socket, clock and config wrappers, `net_status::read` and `health::snapshot`, and nothing else. Glob imports, `unsafe`, externs, module declarations and mutable statics are refused in both files. The health snapshot is built by `health.rs`, which only reads. FW16 will add the matching link check when a motor controller exists.

## Authentication and exposure

- The feeder authenticates to the broker with the per-device firmware password, compared in constant time as the existing roles are.
- The server authenticates to the same broker as its existing server role.
- The traffic is plaintext MQTT on the WPA2-protected bench hotspot, with no route out. Anyone holding the Wi-Fi password could sniff the firmware password and impersonate the feeder or the server on this channel. With the v1 allowlist that exposes health contents and read-only requests, nothing else. **Decision:** accept that for FW08, record it as a carried item, and require TLS (mbedTLS is in the SDK) or a per-message MAC before any channel carries feeding (FW17) or updates (FW10).
- The credential never appears in UART output, the build manifest (hash only, as with Wi-Fi) or tracked files.

The bench host's firewall needs one more input rule for the broker port from the hotspot subnet, for example `iifname "wlan1" ip saddr 10.42.103.0/24 tcp dport 1883 accept`. That is the owner's change, as before. Forwarding stays blocked.

## Authenticated requests

Server-to-firmware requests can carry an HMAC so that a party with only the Wi-Fi and broker passwords can't send them. This section is the wire format and the server's part.

- **Key:** 32 random bytes, shared by the server configuration (`firmware.request_key`) and the firmware build's credential file (`request_key`), each as 64 lowercase hex characters. `petlibre-local firmware-request-key` creates it; see the [local server](../development/local-server.md#request-signing).
- **Nonce:** health from a firmware built with a key has `"nonce":"<16 lowercase hex>"`, a fresh 64-bit value for each MQTT session. Firmware without a key sends no `nonce`.
- **Signed request:** the normal request with `nonce` and `seq` appended and the MAC as the last field, compact JSON with no whitespace:

  ```text
  {"id":"<uuid>","op":"<op>"[,<op fields>],"nonce":"<16 hex>","seq":<n>,"mac":"<64 lowercase hex>"}
  ```

  - `nonce` is the latest health's nonce.
  - `seq` is a plain integer from 1 to 4294967295. It starts at 1 for each new nonce and rises with each request; the firmware refuses any `seq` not above the last one it accepted in the session.
  - `mac` is HMAC-SHA256(key, P), where P is the exact payload bytes before the literal `,"mac":"`: the object up to and including the `seq` value, without the closing brace.
  - Field order is fixed: `id`, `op`, the op's fields, `nonce`, `seq`, `mac`.
- **Size:** a request may be up to 320 bytes (256 before authentication). The largest is a signed `time` request: about 257 bytes in America/Denver at `seq` 1, and under 270 at the largest `seq`.
- **Refusal:** a bad or missing MAC, an unknown nonce or a stale `seq` gets `{"id":"<uuid>","ok":false,"error":"auth"}`.

**Server:** with a key configured, every request the server sends is signed: API `health` and `ping` and the FW21 `time` sync. The per-nonce `seq` counter lives in the server's in-memory replacement tracker and restarts at 1 when the health nonce changes. If the latest health has no nonce, the server sends unsigned requests as before; without a key it never signs. It builds the payload as text in the fixed order rather than through a JSON map, so P is exactly what it MACs. HMAC-SHA256 is implemented over the `sha2` crate already in use (checked against RFC 4231 cases 1, 2 and 6). Health with a malformed `nonce` is rejected and counted like other invalid health. The counter is not persisted: `serve` runs the broker as its child, so a server restart also ends the firmware's MQTT session, and the reconnect brings a new nonce. A tool that sends requests beside a running broker (the `time_jump` example) starts at `seq` 1 and is refused with `auth` if the session already accepted requests.

**Firmware** (`petlibre-core/src/request_auth.rs`, KM4 `transport.rs`):
- **Nonce:** each connect draws a session nonce. It is the HMAC under the key of the ROM generator, the SysTick count, the tick count and the connect count at that moment (`petlibre_entropy` in `example_entry.c`). That is not a vetted random source, but the nonce only has to differ between sessions.
- **Checks:** the MAC is checked in constant time over the prefix, then the nonce and `seq`. Nothing changes on a refusal.
- **What needs a signature:**
  - A request carrying a MAC is refused unless all three checks pass, whatever it asks.
  - A state-changing request, today only `time`, is refused unless it is signed and valid. An image built without a key refuses every state change.
  - `health` and `ping` still work unsigned.
- **Logging:** refusals log `PLMQT1 request op=unauthenticated ok=0`.

**On hardware (October 22, physical):**
- **Startup:** after `petlibre-local firmware-request-key`, an image built with the key reported its nonce in health. It accepted the server's signed `time` sync and a signed API `ping` (`seq` 2).
- **Refusal:** over a bare broker, an unsigned `time` was refused (`error: auth`, the clock unchanged), and a signed one at `seq` 1 was accepted.

## Wi-Fi credentials (FW25)

`{"id":…,"op":"wifi"}` reads which credentials joined this boot (`source`: `build`, `stored` or `fallback`), the stored SSID's CRC-32 (`stored`, or null) and the record generation; never the SSID or passphrase themselves. `"ssid":"<hex>","psk":"<hex>"` (1-32 bytes; 8-63 printable ASCII) stores credentials for the **next boot**, and `"clear":1` returns to the build's. Both must be signed, and requests may be up to 448 bytes for the hex.
- **Store:** `petlibre-core/src/net_store.rs`, two 128-byte records in storage sectors 5 and 6, written by the settings task inside a marked attempt. A power cut at every mutation reopens to the old or the new value and stays writable (host).
- **Join:** before each attempt the C shim takes the build's credentials, and Rust (`amebad/src/network.rs`) substitutes the stored ones. After 5 failed attempts in a row with no success this boot, the build's credentials take over until the next boot. The connect event's value names the source; health reports `wifi.source`.
- **API:** `{"op":"wifi","ssid":"…","psk":"…"}` or `{"op":"wifi","clear":true}`; the server hex-encodes and signs it and never logs the values.
- **Physical (October 22):**
  - **Stored:** storing the hotspot's own credentials, then a cold boot, joined with `source: stored`.
  - **Wrong passphrase:** stored attempts 1 to 5 failed, the build's credentials took over from attempt 6, and the feeder came online on attempt 7 (`source: fallback`).
  - **Recovery:** a signed clear then returned to the build's credentials.
  - **No leak:** neither passphrase appeared in any capture.

## Device settings (FW25)

`{"id":…,"op":"settings"}` reads the device settings: lights, sound, volume, the record generation, and whether NOR may be written. With `"lights":0|1`, `"sound":0|1` or `"volume":0..100` it queues one change, which **must be signed**. The reply reports the current values and `"pending":true`. A second change while one is queued gets `error: busy`, and an unwritable store gets `error: read_only`.
- **Writer:** the firmware's settings task (`petlibre-fw-reference/src/settings.rs`) owns the FW15 store in storage sectors 2 and 3. It starts after the boot is confirmed, arms the flash-lock hooks if the confirmation did not, and only then lets the offer check start, so the two never arm at once. Each save sets the arming attempt marker and clears it after.
- **Transport isolation:** the transport may only call `settings::request`, which queues and reads atomics and never touches flash.
- **Records:** `PLCFG1 start`, `open status=… generation=… lights=… sound=… volume=…`, the arming records, `saved …` and `error stage=unarmed|save status=…`.
- **API:** `POST /api/replacement/request` takes `{"op":"settings"}` or `{"op":"settings","lights":true,"volume":40}`; the server signs it.
- **Physical (October 22):** a signed change from generation 2978 to 2979 (lights on, volume 40) was saved and read back after a cold boot.

## Speaker (FW24)

`{"id":…,"op":"play","tune":"chime|meal|coin|alert|test|twinkle"}` queues one built-in tune; it **must be signed**. The reply is `"ok":true,"tune":…`, or `error: muted` (the `sound` setting is off) or `error: busy` (a tune is playing, or the settings are not loaded yet). An unknown tune is malformed. The transport may only call `audio::request`, which reads the settings and fills a one-slot mailbox. API: `POST /api/replacement/request` with `{"op":"play","tune":"coin"}`. Design and evidence: [audio](audio.md).

## Server side

- **Config:** an optional `firmware` section (client ID, username, password). The config format stays version 1; a config without the section behaves exactly as today.
- **Init:** `petlibre-local firmware-credential --config private/server.json --output private/fw-mqtt.json` adds the section and writes the private file the firmware build reads. A second run is refused rather than rotating silently.
- **Broker:** the firmware role and its ACL (literal topics only).
- **API:** `GET /api/status` gains a `replacement` object: the latest health, its age, stale or online, and the last few request replies. Add `POST /api/replacement/request` with `{"op":"health"|"ping"}`; the server generates the request ID.
- **Compatibility:** stock handling is untouched, and the existing tests keep passing unchanged.

## Firmware build side

The builder (`petlibre-build`) reads `private/fw-mqtt.json` (broker address, port, device ID and password) into an ignored generated header, like the Wi-Fi credentials, and records only its hash in the manifest. A new startup policy `fw08-transport-v1` binds the `PLMQT1` record format both ways, as FW07's policies do.

## Stages and acceptance

**A, offline (done).**
- Core MQTT codec and client state machine. Host tests cover the encodings, malformed and oversized input, keepalive and timeouts, and every reconnect path.
- An integration test against the server's broker: the firmware role can connect, publish health and get a reply; it can't publish or subscribe outside its topics; the stock role can't reach the firmware namespace.
- Server config, credential command, ACL, API and docs.
- The structural no-dispense check.
- The UART auditor for `PLMQT1`.

**B, bench (passed).** One boot on the FW07 bench. Pass criteria:
- The feeder connects within 15 s of its first successful DNS check.
- `/api/status` shows health with the build ID that UART printed.
- Periodic publishes arrive at 30 s (±5 s).
- A `ping` and a `health` request round-trip.
- Nothing resets, and UART shows no credential.

Result (physical, UART plus the server's `/api/status`):
- The feeder connected 0.1 s after its first good DNS lookup: an 8 ms TCP connect, ready 3 ms later.
- It published health six times in 3 minutes: on connect, after a request, and four times on the 30 s period.
- A `ping` and a `health` request sent through the API were answered, with matching IDs.
- The health the server held had the build ID the UART printed, with outputs stopped and no faults.
- Nothing closed, and no credential appears in the UART output.

**C, bench recovery.**
- Restart the server while the feeder runs: the server sees the will or goes stale, then sees a reconnect within 30 s of the broker returning.
- A hotspot outage: reconnect after Wi-Fi rejoins.
- An unsupported request is refused and logged. This is host-tested (driver tests, and the codec against the real broker), because the server's API sends only allowlisted operations and widening it for a test would weaken that guard.
- Full-flash A/B reads across the boot are identical, as in FW07.

Result (physical, UART plus a once-a-second watch of the server's `/api/status`), one boot with a hotspot outage and then a server restart:
- **Hotspot outage (20 s):** the feeder saw its broker connection close, then reported the Wi-Fi loss. It rejoined 42 s after the close and reconnected to the broker immediately after the rejoin.
- **Server stop:** the connection closed. Three refused connects followed, 1, 2 and 4 s apart. The feeder reconnected 15 s after the stop, within 5 s of the server returning, and the server showed fresh health.
- **Integrity:** full 8 MiB flash reads before and after the boot were byte-identical. Nothing reset, and no credential appears in the UART output.

Limit: during the hotspot outage the server kept showing the feeder online for the whole outage. With the hotspot down, the broker gets no close for the feeder's connection; it notices only when the keepalive expires (45 s) or the health goes stale (75 s after the last publish). The feeder reconnected first, so the server never marked it offline. Server-side detection of an access-point outage is therefore bounded by those timeouts, not immediate.

**Done when** A–C pass and the carried items below are on the board (done).

## Carried items (on the board)

- **Plaintext transport and shared Wi-Fi trust**, owned by FW10 and FW17. Either card adds authenticated or encrypted messages before carrying updates or feeding.
- **Credential provisioning without a rebuild**, owned by FW25.
- **Server-side multi-device support**, unowned. The server is single-device by design today.
