# Device-hosted API (FW47)

Status: physical (October 24, 2026), LAN recovery with the owner at the panel. The feeder serves its own Noise-encrypted API over TCP from the firmware's loop task. Every request, the event history and the live samples go over it, and the normal role no longer opens an MQTT session. The wire contract is in [API design](../api/README.md#device-protocol); this page records how the firmware serves it and what has run on the feeder.

## In the firmware

- **One loop task.** The feeder runs two tasks, the button service and the loop ([task slots](../../src/firmware/wellfed/README.md#what-the-sdk-runtime-guarantees)), and `wellfed-fw-feeder`'s `api` module steps the API inside the loop, after the panel's owner. Every socket call is non-blocking (`wellfed_api_*` in `example_entry.c`): the loop takes what is ready and moves on.
- **Sans-IO server.** `wellfed_device_api::Server` holds four session slots. The firmware's driver copies received bytes in and sends what a slot holds; the server never touches a socket, so host tests drive it with `wellfed-client` directly.
- **One handshake operation per pass,** across all slots. While the loop holds the outputs for a feed (from its claim to its release) only IK session handshakes go on, so an enrolled client can open a session during a feed, read the status and cancel it (FW17; until then every handshake waited for the feed). Whether the key is enrolled is known only once the client's first message is read, so any LAN host can start one: building the handshake costs one X25519 and reading that message two. To bound what a stranger costs a feed, a session refused during a feed (unknown key, wrong major, full) is closed without its reply, saving that reply's two X25519s, and after one session handshake is refused or fails during a feed every other waits for the feed's end (an enrolled client opening then may time out and retry after it). Per connection a stranger costs at most 3 X25519s; four strangers filling every slot at once each get their set-up step too, so up to 6 X25519s over 5 operations a feed, still at most 2 an operation. So a client that may want to cancel keeps its session open across the feed (as `wellfed feed` does) rather than connecting to cancel. The timing argument (static and simulation, October 26): an operation costs one or two X25519s (25–28 ms each on the KM4; the worst single operation measured 77 ms with the since-deleted MQTT task preempting, [resource budget](resource-budget.md#handshakes-and-loop-latency)), and the owner's observations must stay within 100 ms of each other while it drives (`max_observation_gap_ms`, and the feedback edges' 100 ms age). The loop steps the owner just before each pass and, when the pass ran a handshake operation during a feed, again at once after it (`Server::handshook`), so the gap is the pass itself, not the pass plus the loop's delay. The virtual feeder completes a three-portion feed with a 70 ms hold every half second (`handshake_sized_holds_during_a_drive_leave_the_feed_to_complete`) and with 80 ms holds back to back, the owner stepped once between each (`back_to_back_handshake_holds_leave_the_feed_to_complete`), and a 150 ms hold ends the feed `ObservationGap`, stopped and durable: overrunning the budget costs a failed feed, never a stop, which stays with the 200 ms motor lease and the supervision timer. `PLOWN1 steps id=… max_gap_ms=… handshakes=…` reports each feed's longest gap on hardware. An invite's join and a LAN recovery still wait for the feed: both end in an enrollment, a store write that would wait for the feed, so the invite is redeemed (and the recovery code taken) only once the key can be written. A handshake held off this way waits; it is not refused, and an invite or recovery window can still expire meanwhile. The hold lasts at most the claim's `FEED_BOUND_MS`, as a join's wait does.
- **Feeds.** `Feed` goes to the feeding owner in the same loop (`feeding::Feeding`) under the next journal id; the answer waits until the owner has reserved it, then names it. When the owner reports the result, the loop logs `PLOWN1 fed …` with what the drive measured, records a `Fed` event and acknowledges the result, so the owner takes the next. One feed at a time: a second is refused `Busy`. A faulted owner refuses `Fault`. A feed is also refused `Busy` while a Wi-Fi join attempt runs (from its scan through association to DHCP) or waits for the outputs: an association holds every task for up to 0.72 s ([scheduling gaps](scheduling-gaps.md#result-october-25-2026-physical)), so feeds and joins take turns (`wellfed_hal::interlock`). Like every refusal it is final for that write id, and nothing moved, so trying again is a new feed the user asks for; the loop logs `PLOWN1 feed portions=… held=…` (1 a join runs, 2 one waits, 3 a storage write ran past the claim's wait). A join that comes while a feed holds the outputs waits in the Wi-Fi task until the owner is at rest with its outputs stopped, and at most `FEED_BOUND_MS` (the owner's own cap on a feed's emitters-on time plus 2 s, about 9 min 40 s for 48 portions); `PLOWN1 interlock …` counts waits and joins forced past that bound. A feed that finds a storage write running (see below) waits for it in the loop, at most `WRITE_WAIT_MS` (3 s: one record's erase and two programs at their whole lease budget, after the writer's 200 ms poll); a write still running, or a client's change still queued for the writer, then refuses it `Busy` (`held=3`). A feed a reset interrupted (power cut, watchdog, fault) is resolved when the owner next opens: the journal records it as uncertain under its own id, the loop records its `Fed` event with outcome `Uncertain`, `completed` 0, reason `Output` (a distinct reason would be a later wire change) and source `Feeder` (the requester is not journaled), and the owner then takes feeds again, from the next id. It is never retried, and its id is never handed out again; a `CancelFeed` for it answers `NotFound`, and its `Fed` event in the history says how it ended. Until that event is recorded, a new feed is refused `Busy` (readiness `Resolving`). A power cut at any point of the resolution leaves it to resolve at the next boot, once; only flash corruption of a committed result beside its own reservation (a bit flip that fails the result's checksum) makes the next boot resolve that feed again, so its id can then carry a second, uncertain `Fed` event after its first. A slot reads one frame per pass and writes again only once its last frame is out, so a flooding client costs its own turn.
- **A feed's write id is remembered from the moment it is queued** (FW17), not when its answer is sent: a client whose session ended before the owner reserved the feed, and that sends the same id on a new session, waits for that same feed's reservation and gets its `Feeding { feed }`; after the feed it gets the same answer. Nothing is queued twice. The window is the boot: ids live in the server's RAM (32 per client key, 4 keys), and the journal keeps the feed's number but not the request id, so after a restart a resent id is a new request. Clients never resend a feed whose answer they did not get (an unanswered feed is uncertain, `Connection` reports it `Unanswered`), and an interrupted feed resolves at boot as uncertain under its own number, so nothing resends across a reboot; making the id durable would change the journal's record and need a bank-0 refresh first.
- **Readiness** (`Capabilities::READINESS`, FW17): one decision says whether a feed can start now (`wellfed_feeder::feeder::feeding::readiness`). It starts from the owner's own reason (`Feeding::blocked`: `Starting` until it opens, `Journal` if the journal failed, `Fault`, `Resolving` an interrupted feed, `Feeding` while one is in flight, `Joining` while a join runs or waits), then adds BLE setup mode (`Setup`: it ends in a restart that would leave a feed uncertain) and an install (`Updating`). A feeder with no owner (the simulator, the `gap-probe` image) is `Unserved`. A session that claims the bit gets `Status` answered `FeederStatus { status, readiness }` (the model's `Status.readiness`); a `Feed` is asked of the owner only while it is `Ready`, and otherwise refused with its reason's refusal (`Fault` for `Journal` and `Fault`, `Unavailable` for `Unserved`, else `Busy`), with the owner's own checks behind it for a feed that lost a race. A change of a lasting reason (`Journal`, `Fault`, `Updating`, `Setup`) is recorded as a `FeedingBlocked { reason }` event, and `FeedingBlocked { reason: None }` once it clears; passing reasons (a feed, a join) only go to the log (`PLFEED1 readiness …`), so they never fill the history. Each boot starts with none recorded. On the pack alone below its floor, or after a brownout until the adapter returns, the owner's reason is `Battery` (behind `Capabilities::POWER`, [power](power.md)); a running feed whose pack falls under the floor ends `Failed`/`Power`. The panel lock is not one either: it holds only the Dispense button.
- **The Dispense button** (FW17) asks for one portion, as stock's does, through the same readiness and the same owner as a client's `Feed`; its `Fed` event says `by: Panel`. A locked panel ignores it, and pairing takes a press that confirms an offer first. The loop logs `PLFEED1 dispense feed=N` or `dispense refused=…`.
- **Feeds are silent** (owner, October 26: feeds play no tune). A feed, by a press or a client, asks nothing of the speaker. The loop still steps the speaker outside setup mode for a client's `play` request, after the owner and the device API, so a tune that is playing, will not open or stalls leaves a feed, its cancel and its `Fed` event as they were (host-tested on the board's platform against the fake codec, `wellfed-fw-feeder/tests/manual_feed.rs`). FW17 played the `meal` tune when a feed was queued until then; an owner-chosen call before a scheduled meal is FP13's.
- **No restart into a feed.** `Reboot` is refused `Busy` while a feed is queued or runs; once accepted, a `Feed` is refused `Busy` until the restart, and the restart itself waits for a feed still in flight at its deadline (a Dispense press in that second). BLE setup mode's closing restart waits for a feed in flight too, so none leaves a feed uncertain.
- **A server never re-asks a feed across a feeder boot.** The id memory lasts one boot, so a resent id after a restart is a new feed. A server feed route that answers `outcome_unknown` and lets its caller retry with the same key must, before re-asking the feeder, compare the feeder's boot count (`Status.boot_count`) with the one it sent under: if the feeder restarted, the feed is uncertain and is resolved from the history's `Fed` events, never sent again.
- **No flash write while the motor may move.** Every flash lease checks that the outputs are stopped, and fails closed when they are not: the lease hook halts and the watchdog resets the board mid-feed. So every store write outside the feed journal (the event ring, settings, the client and key stores, the Wi-Fi store, the seed, the build confirmation and the update stage's records and bank-1 writes) first takes the write turn in `wellfed_hal::interlock`, which it gets only while the loop holds no claim on the outputs. A write that comes during a feed waits: the settings writer leaves it queued and asks again every 200 ms, still answering event reads, and counts itself among the waiting writers, so the next claim lets it go first. It runs once the owner is at rest with its outputs stopped. Only a claim that outlives `FEED_BOUND_MS`, timed from when the writer first saw that same claim (a writer that misses the gap between two feeds starts again on the second), lets a write go ahead with the outputs claimed, counted (`PLOWN1 interlock … writes_forced=`), and only while they read stopped: a write never starts into moving outputs. The update stage never takes that forced path: an update request waits in its mailbox, unanswered, until the outputs are free; an install holds the turn from its first write until it stops, so every feed meanwhile is refused (`held=3`), and a give-way or an activation keeps it until the restart. The confirmation takes the turn before arming the hooks, and the update stage before it sets the attempt marker, so the marker is never left set through a wait. Queued writes complete after the feed in their usual order: the events in the order queued, each mailbox's single change once. The feed journal's own records take no turn: the owner reserves and finishes a feed only after `quiet()` has stopped the outputs, and opens (creating the journal or resolving an interrupted feed) before any feed is claimed. On a trial boot no feed is claimed before the confirmation is written: the owner opens only once the hooks are armed, the confirmation is that boot's first arming (the settings writer starts after it), and it holds the write turn from arming to its write, so a feed cannot push the confirmation towards the trial deadline. `PLOWN1 interlock …` counts `writes_deferred`, `writes_forced`, `write_waited_max_ms` and `feeds_delayed` (claims that waited for a write).
- **A client's store write during a feed is refused `Busy`.** A write would wait for the feed's end, longer than a client waits for its answer (10 s), and a slot waiting on an answer reads no frames, so the client would end the session unsure of the write's fate. So while the outputs are claimed the loop refuses a settings change, a Wi-Fi change and a revocation `Busy` before queueing anything: nothing changed, and the client may send it again after the feed. Reads still answer. An enrollment asks again each pass until the feed ends, as it does when the keys mailbox is taken. A change queued before the claim goes first: the claim also waits, within its `WRITE_WAIT_MS`, while a settings, Wi-Fi or keys change waits in its mailbox, so the writer writes it and the client is answered before the feed starts. A change still in its mailbox at the end of that wait (a stalled writer) refuses the feed `Busy` (`held=3`) instead, so a change is never written after a feed it was queued before. BLE setup's Wi-Fi save, which waits for its own answer, waits out a feed. Since FW17 a session opened during the feed reaches this path too, so the `wellfed` CLI can; the bench's `itest` scenario `feed-writes` (`--feeds`) does from a session opened before the feed (host-tested against the scripted feeder; not yet run on hardware).
- **Sessions are Noise IK** under the feeder's identity: the client's key travels encrypted in the first message, and the feeder checks it against the enrolled clients the settings writer publishes (`wellfed_feeder_runtime::keys::publish_clients`). When the table changes, every session whose key is gone closes.
- **Writes are remembered per client key**: the last 32 write ids and their compact outcome, so a retry after a reconnect gets the first answer. A settings or Wi-Fi write names the generation it was based on and is refused `Stale { current }` when the store has moved. The loop is the only requester since the MQTT path went, so the check and the queueing cannot interleave with another writer.
- **Roles.** An owner does everything. A member, or the server, may feed, change settings and the lock, play, sync the clock, read the time view, list clients and invite members; not Wi-Fi, the time settings, revocation or reboot. An update-signer key never opens a session. A clock sync from an owner may step the clock; a member's or the server's may only narrow it ([clock](clock.md#the-clock)).
- **Time** (`Capabilities::TIME`): `GetTime` answers the time view and `PutTime` queues the zone's rule and the NTP server for the settings writer (storage sectors 27 and 28), answered `Done` once the store holds the settings asked for (or already held them) and refused `NotWritable` when the writer could not write them, with no event. The loop applies a new generation on its next pass and runs the NTP exchange on one more UDP socket ([clock](clock.md#ntp)).
- **Calibration** (`Capabilities::CALIBRATION`, bit 256): `GetCalibration` answers the stored weight of one portion, the bowl mode the build runs and the rotor's phase; `PutCalibration` (owners only) queues a new weight for the settings writer (storage sectors 34 and 35), answered `Done` once stored, `Invalid` outside 1–50 g and `Unverified` for a bowl mode the build was not verified for. The statistics' `Portions` section needs the same bit. No event: the calibration has its own generation ([calibration](calibration.md)).
- **Events.** The loop's event recorder (`wellfed_feeder::feeder::events`) queues records in `wellfed_feeder_runtime::events` (16 in RAM, the last kept for a feed's `Fed` event, since appends wait out a feed and its events pile up meanwhile; overflow is counted and recorded as a `Lost` event). The settings writer appends them to the ring in storage sectors 13–24 (`wellfed_feeder::store::events`: 32-byte records, 1,408 kept at least) and answers the API's reads. It polls every 5 ms while either waits; while a feed holds the outputs an append waits at the head of the queue (above). A ring created empty draws a random epoch from the generator and every record repeats it in bytes 4–7, the high half of the old 64-bit sequence field, so a ring written before epochs reads as epoch 0 and the layout is unchanged. The welcome carries the epoch, and the feeder welcomes no session until the writer has opened the ring and published it. Recorded now: boot, lock changes (panel, idle relock, or which client), settings and Wi-Fi writes with their client, clock syncs, invites redeemed, recovery and revocations.
- **Samples** go only to subscribers: power every 5 s, Wi-Fi signal every 30 s, with `STATS` the statistics' metrics ([below](#statistics)), and with `POWER` the judged supply beside the power sample. A sample not sent before the next of its kind is replaced.
- **Supply** (`Capabilities::POWER`, FW26): `Metric::Supply { adapter, battery, below_floor }` names an unread, stale or implausible reading rather than passing it off as a value; `EventBody::Supply` records the adapter's changes and the pack crossing its floor, at most one a minute; readiness gains `Blocked::Battery`, which a session without the bit reads as `Starting` ([power](power.md)).
- **mDNS.** `wellfed_core::mdns` answers `_wellfed._tcp` on one UDP socket in the loop: PTR, SRV (port 4747), TXT (`v=1`, `id=` the identity key) and A, for host `wellfed-<first 4 key bytes>.local`. It announces twice on every address change and answers legacy unicast queries. The vendor responder (33.5 KB and its own task) stays unlinked.
- **Updates** (`Capabilities::UPDATE`, owner sessions only): `OfferUpdate`, `UpdateChunk`, `UpdateState`, `CancelUpdate`, `EnrollUpdateKey` and `UpdateKeyStatement`, answered `Outcome::Update` or `Refusal::Update`. The loop never verifies a signature: it copies the request into the update mailbox and answers from what the service task's update stage publishes ([OTA design](ota-design.md#updates-over-the-device-api)). An offer is refused `Busy` while a feed is queued or driven, and a feed while an install holds the flash. A chunk is idempotent by its offset, so it is not a remembered write and is not logged one by one. An update key is enrolled only once someone at the feeder presses Dispense; the session's answer waits for it (the client's answer time is longer for this op), and a session that leaves cancels the offer.
- **Debug log** (`Capabilities::LOG`, owner sessions only): `TailLog { after }` streams the record lines the firmware logs, from a RAM tail ([below](#debug-log)).
- **Feed traces** (`Capabilities::TRACES` with `STATS`): `FeedTrace { feed, offset }` reads what a feed's drive measured, a page at a time, from RAM or storage sectors 29-31 ([below](#feed-traces)).
- **Stock backup** (`Capabilities::BACKUP`, bit 512, owner sessions only): `ReadBank1 { offset }` reads bank 1 a page at a time, served only by the bank-0 recovery role, so the installer can keep stock before a promotion overwrites it ([below](#stock-backup)).
- **Invites and recovery** (from FW45). `CreateInvite` mints a secret, which is the PSK of the new client's XXpsk3 handshake. Its third message carries the label, and the key enrolls through the keys mailbox. The recovery window runs FW45's setup exchange (XX plus the code proof) over the stream, so the owner keys the client's code in before it becomes an owner. A LAN neighbour cannot slip in while the window is open, and the window closes at the first offer. Recovery takes no Wi-Fi.

## Debug log

FW56 (host-tested, October 26). An owner can read what the feeder's UART prints without opening the feeder: `wellfed logs` (`--follow` for new lines, `--after N` to resume).

- **The tail.** `wellfed_amebad_sys::log`, which every record line goes through (`wellfed_sdk::log`, the `Record` derive and the runtime's own lines), prints the line as before and then copies it into a 4 KiB RAM ring, `LOG_TAIL` (`wellfed_core::log_tail`): about 70 lines of the usual 56 bytes. The copy happens inside the same scheduler suspension as the print, after it, so the UART sees each line at the same moment as before and tasks never contend for the ring. Vendor C prints (`_rtl_printf`, `DiagPrintf`, the panic record) do not go through `log` and are not in the tail. Nothing is written to flash; the tail starts empty each boot and numbers its lines from 1.
- **Safe from an interrupt, never waiting.** Only an interrupt can find another writer mid-copy (a task logs with the scheduler suspended). It drops its line from the tail (the UART still prints it) and counts it, rather than wait for a writer that cannot run until it returns; the dropped line still takes a number. No interrupt logs today. Readers never block writers: a reader copies a line and then checks the ring's oldest line has not moved past it (a seqlock), starting over a few times at most. A line too long for the ring (over 255 bytes; the record buffer is 192) is counted the same way.
- **Overrun drops the oldest.** A line that needs room drops whole lines from the old end. A session whose cursor fell behind learns how many it missed: each batch's `dropped` counts the numbers after its cursor that the batch does not hold.
- **Batches fit the frame, only when the session has room.** After `TailLog { after }` (answered `Done`; `None` starts from the oldest line kept, and asking again moves the cursor), the session pushes `Log { seq, dropped, text }`: as many whole lines as fit `LOG_TEXT_MAX` (992 bytes), each ending in `\n`, `seq` the last line's number. Like an event or a sample it goes only when the session's last frame is out, after any event and sample waiting, one frame per pass, so a session that cannot keep up costs only its own lines. Text is printable ASCII; any other byte reads `?`. A cursor past the newest line can only be an earlier boot's, and reads from the oldest; one below it cannot be told from this boot's own, so a client resumes with a cursor only within one boot (the status's `boot_count`). Lines dropped after the newest written one show in `dropped` only once the next line is written.
- **Ships in release images.** The `feeder` firmware claims `LOG` in every build, not only behind a debug feature. A shipped bit is served for the life of its major ([rule 5](#evolution)), and here that costs little: the op's contract is text with no schema, so any later build can keep serving it from whatever it logs, and an owner's feeder has no UART wired, so the tail is the only way to see a field fault's lines. Owner-only, and no record carries a key, a secret or a credential (each record type's rule), so the stream shows an owner nothing they could not already change. The other firmwares (`blink`, `bringup`, `qa`) serve no API and build without the `log-tail` feature, so they keep no tail.
- **Cost** (the `feeder` firstboot build against the same build without it, October 26, before FW46 landed; rebased onto FW46 the loop's bound is 5,116 of 8,192 and the other tasks' are unchanged): `.bss` grows by 4,112 bytes (the ring and its state) and flash-resident code by 1,920 bytes; the payload stays 946,176 bytes; the loop's stack bound stays within noise (5,140 → 5,108 of 8,192), since the copy runs in its own 56-byte frame under `log` and a batch reuses the server's buffers. Every task that logs carries that frame; the audited bounds of the others stay within noise too: `wellfed` 2,808 → 2,808 of 4,096, `wellfed-key` 1,272 → 1,248 of 2,048, `wellfed-svc` 11,744 → 11,744 of 16,384, `wellfed-wdg` 1,452 → 1,420 of 2,048. Reading a batch scans at most the ring's headers and copies once, then seals like any frame (about 0.9 ms a kilobyte).

## Evolution

Major version 1 is frozen: every client lives in this repository, and the event epoch (rule 4) was its last change to existing bytes (October 25, before any outside client). From here on:

1. **The prologue never changes.** `wellfed-api-v1` is bound into every handshake. A new major is negotiated in `Hello.major`, and a feeder that does not serve it answers with the typed `OpenRefusal::Version { supported }`, so a client can say which side to update. A changed prologue would instead fail the handshake with no reason. Enforced: `the_prologue_never_changes` (`wellfed-proto/tests/fixtures.rs`) and `a_major_2_hello_gets_the_typed_version_refusal` (`wellfed-client/tests/api.rs`).
2. **Every new op, event body, outcome or refusal is gated by a `Capabilities` bit both sides claim**, as `FEED` gates feeding and `UPDATE` updates. `Op::capability` and `EventBody::capability` name each variant's bit with no wildcard, so a new variant does not compile without its decision. The feeder serves an op only when the session's hello and the feeder both carry its bit (otherwise `Unavailable`), and pushes an event only when the hello carries its bit (otherwise the session's cursor moves past it). Enforced: `a_v1_only_session_never_receives_a_body_outside_v1` records one event of every body, an exhaustive match keeping the list whole.
3. **Existing messages never gain, lose, reorder or retype a field.** Postcard is positional, so an old peer would misread every byte after a new field. New data is a new variant behind a bit. Enforced: `tests/fixtures/v1.txt` pins every v1 message's bytes, and `WELLFED_BLESS=1` only appends fixtures for new variants; it refuses to rewrite a pinned line.
4. **The event history carries an epoch.** `Welcome::Open.epoch` is drawn at random when the ring is created and kept with it. Event numbers count within an epoch, so a cursor from a re-created ring (a storage wipe, which restarts the numbers at 1) is recognized rather than freezing a mirror that waits for numbers it already has. `wellfed-client`'s `Connection::subscribe` resumes after a cursor only in the feeder's current epoch and otherwise starts from the oldest event kept (`Resume::Restarted`). The server keys events and gaps by (feeder, epoch, seq) and keeps an older epoch's history readable (`?epoch=`). Enforced: `a_cursor_resumes_in_its_epoch_and_restarts_from_another`, the event ring's epoch tests, and the store's `a_new_epoch_keeps_its_own_history_and_restarts_the_cursor`.
5. **Clients adapt to the feeder's capabilities indefinitely.** An owner may hold an update forever, so there is no "N and N−1" window: a client claims every bit it knows (`Capabilities::KNOWN`), runs on the intersection the welcome gives it (`Opened::capabilities`), and keeps speaking every older major it ever spoke. A feeder keeps serving every bit it ever shipped within its major.

## Statistics

`Capabilities::STATS` (bit 16), host-tested (October 26). The loop keeps the figures in RAM as it runs (`wellfed_feeder::stats::Keeper`): no task, no wait and no flash write, a few additions per pass. The lifetime totals are the settings writer's, in storage sectors 32–33.

- **`Stats { section }`** answers one section in one frame, for any role that opens a session (`Memory` for owners only). The widest of each is checked against `MESSAGE_MAX` (`the_largest_messages_fit_a_frame`, and the device API's property test through the server).
  - `Counters`: why this boot started (`ResetCause` from the ROM's reset flags: power-on, watchdog, software, brownout, other), this boot's uptime (counted past the millisecond clock's 49.7-day wrap), feeds (and those not done), confirmed portions, panel gestures, sessions, reconnects (link and check losses), DHCP renewals, outages and seconds on battery; the longest and mean handshake (accept to open).
  - `Memory`: the heap's free bytes and low-water mark, and each RTOS task's fewest free stack bytes (up to 16, with `tasks_total` the number the RTOS runs, so a truncated list shows). The walk (`uxTaskGetSystemState` and the name copies, with the scheduler paused) runs at most every 5 s, its result reused meanwhile, and never during a feed: the request is refused `Busy` while one is queued or runs.
  - `Flash`: each storage sector's erases and bank 1's this boot (counted where every erase goes, `storage_erase` and `bank1_erase`), and the event ring's records kept against its capacity.
  - `Power`: the adapter now, its changes and outages, time on battery, the battery's least and most, and its voltage at the end of each of the last 24 hours.
  - `Food`: the food beam's last reading, its empty and refill transitions and feeds since a refill. The beam is read only while the emitters are on, and the feeding owner does not publish it yet (`Feeds::food` answers `None` on the PLAF103), so these stay empty until it does.
  - `Feeds` (with `TRACES` too): this boot's feeds as their traces measured them ([feed traces](#feed-traces)).
- **Lifetime figures** (`Counters::lifetime`, `resets`, `Flash::lifetime`), host-tested (October 26), with no wire change: each is the stored totals plus this boot's figures.
  - **The store** (`wellfed_feeder::store::stats`, sectors 32–33 of the region grown to 48): one 288-byte dual-slot record (`PLFSTA01`) of the ten counts, boots by reset cause and erases of every storage sector (all 48, though the v1 `Erases` lists the first 32) and of bank 1, with the early-save budget. Newest valid wins, so a cut save loses that save only. Its layout covers the region as it is: growing the region again takes a new record version.
  - **At boot** the writer loads it, adds this boot to its reset cause (from the ROM's flags, as `Counters::reset`) and publishes it for the loop (`PLCFG1 stats open status= generation= early= missed=`). The loop hands this boot's counts to the writer every 30 s, beside the signal sample, and again just before it asks for a restart; it never writes.
  - **Saves** take the write turn like every store write, but never one forced past a claim's bound, so they never run while a feed holds the outputs. They come only when nothing else is queued, never per event (`PLCFG1 stats saved generation= early=`):
    - **early**: the boot's own as it starts, so a reset is counted however short the boot, and one in an intentional restart's grace (below). Each takes one of 6 tokens kept in the record; the save that takes the last sets a sticky flag (`missed=1`: a boot may have been missed), and boots after it go uncounted until a settled save gives a token back;
    - **settled**: every hour of a boot's uptime, the first an hour in. Each gives one token back. A power cut loses at most the last hour of a boot.
  - **Wear:** early saves never outnumber settled ones by more than 6, so the store erases at most 6 times plus twice per hour of uptime, whatever the crash pattern: about 17,500 erases a year, 8,800 of each sector, far inside NOR endurance.
  - **A restart's save** happens in the restart's grace: `wellfed_sdk::request_reset` (the device API's reboot, setup's restart) opens it (`supervision::begin_restart_grace`), the watchdog is still fed and writes still run, and the writer saves (an early save) and says it is done, or has nothing to save; the runtime restarts then, or after 2 s (`RESTART_GRACE_MS`) if the save is held, say by a feed. Once the feeding stops no write turn is granted, so no save starts into the reset, where a cut write would leave the arming marker set and the next boot without its stores. An update's activation or give-way restarts at once, without a grace (it holds the write turn until the reset anyway). A supervision stop (a hung task, unverified outputs) saves nothing. Each save counts its own erase. A failed save is not retried that boot.
  - **Lower bounds:** the lifetime counts and `resets` are at least the truth, never more: a power cut loses up to an hour of a boot's counts, and while no token is left short boots go uncounted. The `missed` flag that says so is in the log, not on the wire.
  - **`None`** comes from a build that keeps no totals (one before October 26), and from a store this build cannot write (a newer record version, or a read error).
- **Metrics** every 30 s, beside the signal, to subscribers whose hello claims the bit (`Metric::capability`): `Heap { free, min }`, `Loop { passes, max_us, p99_us }` (the loop's passes since the last, timed on the 32 kHz system timer around the feeding owner's step and the pass, the percentile from buckets an eighth of an octave wide), `Gateway { round_trip_ms }` (the latest answered probe since the last, `None` if none) and `Wifi { channel, ap_changes }`. A session holds one sample of each kind and sends the oldest first, so a kind is replaced only by its own next sample.
- **The Wi-Fi shim** reports two more events (`kind=ap`, `kind=renew` in `PLWIF3`): after each join's DHCP the channel and the BSSID's last four bytes, and a lease renewal, seen as lwIP's lease clock going back while the client is bound (a release on expiry also zeroes it, and is not counted).
- **Records:** `PLAPI1 session … state=open` now ends `handshake_ms=`.
- **Host:** `wellfed stats [--section …]` prints each section as JSON; it asks only a feeder whose welcome claims the bit, since a feeder that predates the op would end the session on it.

## Feed traces

`Capabilities::TRACES` (bit 64), served only beside `STATS` (an op needs both bits), host-tested (October 26). The feeder keeps what each feed's drive measured, poll by poll, in RAM and then in its own storage, so an owner can read it without a UART or a server: `wellfed trace <feed>` (`--json` for the whole trace).

- **Recorded after each owner step, never inside it.** The feeding owner keeps one `Observation` (`wellfed_core::feed::observe`) per poll of a feed being prepared or driven: the current channel (PB1, ADC channel 4), the battery pack in millivolts, the outlet and food beams (read only while the emitters are on), PA18's edge counts and the latest edge's time from the feedback interrupt, and the controller's motor command. The loop takes it once the step is over (`Owner::take_observation`, only from the task that steps the owner) and adds it to the trace (`wellfed_feeder::trace::Recorder`, held in `wellfed_feeder_runtime::traces`), so the trace runs after the step's stop and motor decisions: no task, no wait, no flash, and the motor lease and the supervision timer never depend on it. The poll is the owner's own, so a reading comes about every 30 ms on the PLAF103 (903 polls in a 27.2 s drive), not every 10 ms.
- **Format** (`wellfed_proto::trace`): a body of entries, each timed in milliseconds from the drive's start and coded against the one before: current readings (two bytes at a steady poll), marks (PA18 edges at the interrupt's millisecond, with the level after), beam changes, battery moves of 20 mV or more, and motor command changes (`Drive0`, `Drive1`, `Stop`, which line up with the analyzer's D2 and D3). At most 864 bytes; the whole recorder is under 1 KiB of RAM (a compile-time check).
- **Overflow: decimated, then truncated.** A full body halves its current readings in place (the second of each pair goes; the first reading, a drive's start-up surge, stays) and keeps every second poll's reading from then on (`stride` doubles). Marks, beams, battery and motor entries are always kept; only once they alone fill the body does it end there (`truncated`). A one-portion feed keeps every poll; three portions keep every 4th (about 120 ms); 48 portions every 64th or so, with every mark. The summary never depends on the body.
- **Summary** (`TraceSummary`): the feed's result (requested, completed, outcome, reason) and the owner's own figures, the same that `PLOWN1 fed` logs (drive time, polls, peak and mean current, rising and falling edges, the first edge's time), with beam breaks (a poll that found the outlet beam blocked after finding it clear), reversals (the owner's count of its reverse attempts on a jam, the same `PLOWN1 fed … reversals=` logs; a double bowl's turn between portions is none), the battery just before the drive and its lowest during it, the stride and `truncated`. Current is in stock's scaled unit (`CurrentUnit::Scaled`) until its scaling to milliamps is calibrated; a later build switches the unit without a wire change.
- **Stored once the feed is over.** The loop seals the trace when it records the feed's `Fed` event. The settings writer appends it to the ring under the write turn, so never while a feed claims the outputs, under the arming attempt marker like every store write (`PLCFG1 trace saved feed= seq=`, or `trace error feed=`). A sealed trace counts as a queued write, so the next feed's claim lets it go first (at most `WRITE_WAIT_MS`). The next feed takes the RAM trace back: one that never reached storage is counted (`unsaved`); a feed that starts while the writer is still appending goes untraced rather than wait. A feed a reset interrupted loses its trace with the RAM (its `Fed` event, `Uncertain`, remains).
- **The ring** (`wellfed_feeder::store::traces`, storage sectors 29-31): four 1 KiB slots a sector, each a 96-byte header (`PLTR`, version, the lengths, a sequence number, the summary, a CRC-32 over header and body) programmed first, then the body. A cut before both are in leaves a slot that fails its checksum and is skipped. When the newest sector is full the oldest is erased, so the ring keeps the last 8 to 12 traces, and each sector is erased once every 12 feeds. A power cut at any mutation of an append or of its erase loses at most the trace being written (host test). No build before this one wrote sectors 29-31, so bank 0's build ignores them and no bank-0 refresh is needed.
- **`FeedTrace { feed, offset }`** (op `0x17`) answers `Outcome::FeedTrace` (`0x0b`): `TracePage { summary, stored, offset, total, bytes }` with at most 432 bytes of body, so a three-portion trace is two pages. Any role may read it. The loop answers from the latest feed's trace in RAM, otherwise from the ring through mapped flash (a read takes no lease, and a lease holds every other task off the flash). `Busy` while that feed is still recorded, `NotFound` when neither holds it, `Invalid` for an offset past the body. Each page repeats the summary, and `wellfed_client::trace::Pages` refuses a trace that changed between pages rather than splice two.
- **Statistics:** `Stats { section: Feeds }` (section `5`, both bits) sums this boot's traces (traced feeds, drive time, polls, peak and mean current, edges, beam breaks, reversals), with the ring's fill, the unsaved count and the latest summary.
- **Cost** (the `feeder` firstboot build, October 26, every audit passing): about 1.4 KB of `.bss` (the recorder, under 1 KiB, and the 432-byte page an answer borrows), against `.ram_image2.bss` 61,668 bytes in all; the payload is 995,328 bytes. The loop's stack bound is 5,360 of 8,192, its deepest path still a feed's submission under a session's request, not the trace; `wellfed-svc` stays at 11,744 of 16,384. Recording costs a few comparisons and a two-byte append a poll, and a halving one pass over under a kilobyte; a page read scans twelve slot headers and checks one trace's CRC from mapped flash.
- **Why a bit of its own:** a feeder that serves `STATS` but predates traces cannot decode `FeedTrace` (or the new section), and an undecodable request ends the session, so a client asks only a feeder whose welcome claims both.

## Stock backup

FW43 (host-tested and simulated, October 26; not yet run on the feeder). After stock installs the replacement into bank 0, bank 1 still holds stock with only its marker's first byte zeroed, and promotion would overwrite it. So the installer reads it first and keeps the owner's own copy ([rollback](consumer-installation.md#rollback)).

- **`ReadBank1 { offset }`** (op `0x1a`) answers `Outcome::Bank1` (`0x0d`): `Bank1Page { offset, total, bytes }` with at most `BANK1_PAGE_MAX` (768) bytes, so the bank's 1,376,256 bytes (`BANK1_BYTES`, stock's payload size) are 1,792 pages. Behind `Capabilities::BACKUP` (bit 512): a feeder that predates the op cannot decode it, and an undecodable request ends the session.
- **Who and when.** Owners only (a member or the server is refused `Forbidden`): the copy is the owner's to keep. Read-only and not a remembered write, so any page may be asked again. Served only from bank 0 (`Unavailable` from bank 1, whose own image is the running build); the SDK's read also refuses unless the flash MMU maps bank 0. `Busy` while an install holds the flash, since it rewrites the bank under the read; `Invalid` at or past the bank's end.
- **How.** The loop copies the page through the mapped flash window (`sdk::bank1_read`, a sector at a time; a read takes no lease) into the 768-byte page buffer the trace answers also borrow, grown from 432 bytes. Nothing vouches for the bytes: `wellfed_client::install::StockBackup::from_bank` restores the marker byte, checks the payload against the pinned 1.1.15 hash and rebuilds the vendor's container, whose hash must match its own pin. A page answer is not logged one by one, like an update chunk.
- **Cost** (the `feeder` firstboot build, October 26, every audit passing): the page buffer grows by 336 bytes of `.bss`; payload 1,015,808 bytes; the loop's stack bound is 5,460 of 8,192, its deepest path still a feed's submission.
- **Simulation:** `wellfed-feeder-sim`'s banks serve the read to the bank-0 role; an owner read the whole bank byte for byte over TCP once bank 1 was left as stock leaves it, and bank 1 refused it. The device conformance suite checks both platforms refuse it from bank 1.

## What went away

- **The MQTT offer watch, bank 0's updater and its recovery-role health** (October 25): offers ride the device API, and bank 0 runs the feeder. No build opens an MQTT session; the broker stays for stock.
- **Requests over MQTT.** The firmware's request parser, its reply writers, request signing (`request_auth`) and the health nonce are deleted. The normal role starts no `wellfed-net` task.
- **Confirmation.** FW11 confirmed a trial once the MQTT session was ready. It now confirms on a live link: associated, leased, and its gateway answering (or never having answered this join); no internet is involved ([link liveness](startup-diagnostics.md#link-liveness-without-internet-dns), October 25; until then a DNS lookup of `example.com`). Since offers moved to the API, a build that confirms takes its next offer over the same API.
- **The MQTT transport itself** (October 25): the core's MQTT codec and health writer (`wellfed_core::transport`; the request and reply types the API fills moved to `wellfed_feeder::mailbox`, now `wellfed_device_api::mailbox`, those the SDK's own services carry to `wellfed_core::settings` and `wellfed_core::tone`), the HAL's transport task, the broker credentials and request key as a build input (`private/fw-mqtt.json`, which the builder no longer reads), the version 1 manifest and the server's replacement broker role. The speaker firmware's network audio stream went with the request key, its only key and a feature with no client since `wellfed-local speak` was removed. The startup audit still requires no transport policy and no `PLMQT1` start record. A stock-to-replacement install now closes on the bench's device-API check of the new build on bank 0 (`POST /api/ota/trial/answered`), not on its MQTT health.
